# PeptiCraft 2.0 — Recombinant Fusion Protein Design Platform
## Master Reference Document

---

## About this document

This is the base document for the PeptiCraft platform, version 2.0, contained in the `iGEM-website` repository. It is written to be the most complete available account of the platform — what it is, what data stands behind it, what the biology and the screening do, how the software is built, how it is deployed, and what remains open — so that every other deliverable can be produced from it by condensation, excerpting or re-pointing rather than by returning to the source.

The document is arranged so that each part can be read independently. Terms are defined where they first appear rather than collected into a glossary. Quantitative values are stated with the layer they belong to, because the peptide library, the construct library and the reference library are three different things at three different scales and a number quoted without that context is usually wrong somewhere else.

Two conventions are observed throughout. A value that was never measured is described as not assessed and never as zero; where a field's name does not match its contents, both are stated. Both conventions exist because the platform's own data contract enforces them (section 7.4), and a document describing the system that blurred them would misdescribe it.

---

## 1. Where this work sits

The project occupies three development stages, each with its own repository, and one parallel evidence repository.

**PeptiCraft 1.x** built and refined the screening pipeline itself, on a single scaffold (silk fibroin) and a single functional direction (antioxidant activity). Over four iterations it converged on the architecture that everything later inherited: put cheap work first, treat safety as a veto rather than a score, use each metric once, and derive composite weights from the data rather than configuring them. Its output is a ranked set of fusion constructs and no interface. It is described in full in the PeptiCraft 1.x master reference in the `iGEM-silk` repository.

**The pipeline stage** widened that architecture into a reusable platform. The search space grew to roughly twenty million short peptides, the functional directions grew from one to four, the scaffold library grew from a single silk construct to eight protein clusters drawn from patent records, and four screening funnels were run with their outputs stored in a database. It produces no new predictions after that; its deliverable is the data and the schema that the website reads. Its material appears in this repository as a trimmed copy used only when the pipeline must be run locally.

**PeptiCraft 2.0 — this repository — is the platform.** It adds no new predictive capability. It organises the pipeline's stored results into something a user without protein-engineering training can act on: a pre-computed construct library, a guided builder that assembles a functional peptide, a scaffold and a linker into a specific fusion sequence, a per-candidate evaluation against the standards of a chosen delivery route, and a conversational interface over each candidate's real numbers.

**The evidence repository** holds, for each of the eighteen predictive tools evaluated, its provenance, training data, reproduction record and applicable range, together with the tool-by-tool conclusions that determined which tools could serve as hard gates, which as ranking signals and which only as advisory reports. It is not an input to the platform at runtime; it is the basis on which the platform's readiness states and its refusals are justified.

The single most important continuity across the three stages is methodological. The platform's four governing premises — safety is a verdict and not a score, an unmeasured metric is reported as unmeasured, a ranking-only score is never presented as a probability, and the delivery route changes the screening — are all inherited from the pipeline, and the pipeline inherited three of them from version 1.4 of the 1.x line.

## 2. The problem the platform answers

### 2.1 Three obstacles

Designing a recombinant fusion protein by hand runs into three obstacles that are independent of one another.

**Tool fragmentation.** Producing one functional peptide means facing, simultaneously and separately, a dozen prediction tools. Antioxidant activity comes from one, toxicity from another, haemolysis from a third, immunogenicity from a fourth, thermal stability from a fifth, soluble expression from a sixth, and cell penetration from a seventh. Each accepts a different input format, returns a number on a different scale, and applies a different decision boundary. Using them together means writing the connection layer and handling the failures that duplicate sequences cause. For a team without a computational background this is already a wall, before any biology is discussed.

**Safety treated as a score.** The standard convention folds toxicity, haemolysis and immunogenicity into a weighted total alongside the desired activity. In that arrangement a peptide with an exceptional antioxidant prediction and a clearly unacceptable haemolysis prediction can still finish near the top, because the safety penalty is smaller than the activity advantage. The real problem appears weeks later in a wet-lab run, at the cost of the run.

**Unreadable results.** A prediction tool returns a decimal between zero and one. Receiving 0.64 gives no way to tell whether that means the candidate can advance or is near a danger line, and no way to tell which experiment the number corresponds to.

### 2.2 The platform's three answers

**Integration.** Fifteen-odd tools are collected behind one pipeline. The user does not touch any of them.

**Veto.** Safety is removed from the weighted total and installed as a gate. A candidate that exceeds any gate is eliminated and does not participate in compensation of any kind.

**Explanation.** Every number is presented together with its threshold, its direction, whether it was assessed, and whether it is a gate, followed by a paragraph of prose that states a conclusion. Each generated block cites the response fields it drew on, so a reader can trace a claim back to a value.

### 2.3 Users

Three groups motivated the design, and they share one trait: the product form is clear and the protein-engineering capability is absent.

**Student and competition teams** have a defined theme and a delivery deadline, need a real candidate they can discuss within a few weeks, and have no compute capacity to run eighteen predictors themselves.

**Early-stage researchers** have already chosen an application direction and need a defensible shortlist before committing experiments. They care about whether a candidate's origin is traceable and whether the parameters are transparent.

**Independent formulators and small brands** already hold a product form — a mask, a serum, a hair treatment, an injectable filler — and need to add a functional ingredient defensibly, on a budget that does not stretch to a full computational and verification cycle.

## 3. The product

### 3.1 Shape

The product is a single-page web application, entirely in English, organised as five routes. Three of them are the working surfaces and two are reference surfaces.

**Landing page.** A hero section, four key numbers, three feature cards, five application-route cards, three governing principles, an explanation of the screening rounds, and four direction status cards. All four key numbers are derived from the API rather than written into the page: the search space is the maximum peptide count across directions, the construct total is the sum across directions, and the scaffold count and direction count are the lengths of the respective lists. One phrase in the body text — "about twenty million peptides" — is written rather than derived, and it matches the measured 20,248,885.

**Library browser.** The entry point to what has already been computed. It has three tabs — functional peptides and constructs, scaffolds, linkers — whose counts come from the API. The construct tab offers two kinds of filtering: a tag group by functional direction, and route buttons recording which route a candidate was screened under. Each row shows its rank, direction, status, peptide sequence and length, scaffold name together with a marker for how that binding was established, linker name, a safety verdict dot, the composite score, and the direction's functional score, with a note where that score can only be read as a ranking. Expanding a row fetches the detail and renders it with the same safety-gate panel and tool-score grid the result page uses, which is why the two cannot disagree on a threshold.

**Builder.** The core surface, a five-step guided flow. Step one selects the application route; the interface simultaneously shows which scaffolds that route admits, the three weight tiers, the immunogenicity threshold, and the route's additional non-vetoing checks, and selects the route's first scaffold automatically. Step two selects one or more functional directions; directions with no data cannot be selected, and the interface states separately that directions are independent of one another. Step three confirms the scaffold, from the pool the route admits, filterable by material form, with a matched/all tab pair; the step carries an explicit note that every currently stored construct has a placeholder scaffold binding, so the choice does not narrow the candidate set — which peptides pair with a given scaffold does not change — but it does determine the sequence each candidate is assembled into. Step four confirms the linker, listing every entry in the reference library with its name, residue length, rigidity class, sequence and literature provenance; this step is not narrowed by route, because the linker library has no route dimension yet. Step five returns the result: candidates sorted by composite score, each carrying the fusion sequence assembled from the chosen scaffold and linker and its fusion length, together with counts of how many candidates in the whole matched set cleared every gate, how many sit within 10% of a boundary, and how many were vetoed. From any candidate the user can open the result page, carrying the pair it was built with, and change the pair there to compare.

**Result page.** Where a single candidate is read, organised as four tabs. The construct tab is the primary view: composite score, rank and aggregation propensity at the top; the safety gate panel below; then the sequence in three colour-coded segments — scaffold in blue, linker in green, functional peptide in bold orange, with any segment whose sequence is unavailable drawn in grey as a marker rather than as residues; then a within-direction comparison table and six generated blocks of prose. The peptide tab shows the peptide's origin, length, all nine tool scores, and locally computed sequence properties: molecular weight, net charge, cysteine count, and aromatic and hydrophobic residue fractions. The scaffold tab shows the current binding alongside the alternatives; clicking an alternative re-renders the same candidate on that scaffold immediately, and a scaffold with no sequence is not clickable. The linker tab shows the entry's unit composition and literature provenance. A fixed panel on the right of the page and an input bar beneath it both use the same conversational endpoint, so any figure can be interrogated against that construct's real scores.

**Scaffold detail page.** Expands a single scaffold across five routes: basic information, source and patent, patent sequence variants, which application routes admit it, experimental evidence, regulatory registration status, and the other scaffolds in the library. The page carries an explicit "the following fields are absent from this dataset" region, which lists fields the dataset genuinely lacks as absent rather than rendering them as blank cards — so a reader can distinguish a field that does not exist from a panel that has failed.

### 3.2 A complete walkthrough

Consider a small team building a medical dressing, whose goal is to add antioxidant function to a wound dressing in order to reduce oxidative stress. They do not know which peptide to start from, and they do not know which protein can be formed into a fibrous dressing.

The first action in the builder is selecting the wound-dressing route. Two things then happen without further input. The delivery mode is bound to the route's contact interface, and the user does not participate in that decision. The available scaffolds narrow to the four clusters that route admits: a human-like collagen, a type XVII collagen fragment, a short recombinant silk fibroin and a triple-helix-mimetic recombinant collagen. The interface also states that this route's immunogenicity threshold is tightened to 0.35 against 0.50 for the mask and topical routes, on the ground that a wound barrier is already breached and the construct is in direct contact with tissue fluid.

Step two selects the antioxidant direction. Step three confirms one of the four scaffolds, or leaves all candidates in play. Step four selects a linker, and the interface explains what that choice means: a flexible unit lets the functional peptide swing freely off the scaffold surface, a rigid unit holds it away from the surface, both are legitimate, and which is correct depends on whether the peptide's active site needs unobstructed access to its target. Like the scaffold choice, it changes neither the candidate list nor any score; it changes the sequence assembled in the next step. Step five issues the build, and the page returns the candidates ranked by composite score under that route, each with its assembled sequence in three parts, together with counts of how many cleared every gate, how many sit within 10% of a boundary, and how many were vetoed. Those counts are computed over the entire matched set, so when the page displays a limited number of rows the counts still describe the whole pool.

Opening one candidate, the reading order is: check whether the safety verdict is clear; then read the composite score and the nine scores against their thresholds; then read down the sequence to see how the three parts were joined; then read the generated prose, concentrating on the expression and handling advice and the risk list. If a figure is unclear, the conversational panel accepts a question about it — why a score has that value, whether the candidate still holds under a different route, or how it compares with others under the current one. What leaves the session is three things: the complete construct sequence, the corresponding expression plan, and a list of validations that still have to be performed.

### 3.3 Design decisions and their reasons

**The platform does not ask the user questions the user cannot answer.** A non-specialist cannot decide which scaffold protein is appropriate, and a specialist does not want to be asked at every step. The platform therefore converts scaffold selection from a decision the user makes into a conclusion derived from the product form: the user states the product, the platform derives the scaffold. The same principle applied to a different object yields a different conclusion. Scaffolds are eight named proteins, and choosing among them requires knowing each one's mechanical behaviour and evidence level, so that choice can only be derived. Linkers are not that shape: the real difference between library entries is a single rigidity class, and the trade-off between a flexible and a rigid unit can be understood without protein-engineering training, so a single linker is exposed as a changeable option. The linker shares two properties with the scaffold — both participate in assembly, neither changes the candidate set or any score — and differs in one: it is not derived from the route, so the interface presents the whole library with the first entry selected by default, and a user who changes nothing still gets a usable result. Kept in the background is the multi-site combinatorial enumeration: flexibly and rigidly linked variants across one to five linker positions, sixty-two combinations in total, each filtered in turn. That is pure search work, and the user has neither the means nor the need to adjudicate it.

**The top-level classification reuses the dataset's own labels rather than inventing a parallel set.** The five application routes correspond to five application-tag columns in the scaffold dataset. That is not convenience; it is because three conditions hold simultaneously. Every selectable node admits at least one scaffold, so no node is a dead end. Every scaffold is reachable from at least one node, so nothing in the library is unreachable. And no two nodes admit exactly the same scaffold group, so no node is a redundant entrance that costs the user a decision carrying no information. The measured result is that the five routes admit 2, 4, 2, 4 and 2 protein clusters respectively, all eight clusters are reachable, and no two routes point at the same group. Those three conditions are the standard by which the entrance structure is judged, and they are also the reason an earlier self-designed scenario hierarchy was abandoned: its subcategories admitted identical scaffold groups, so the user could not perceive having filtered anything.

**Delivery mode is derived from the route rather than selected by the user.** This decision is easily misread as interface simplification; the actual reason is the scoring convention. Delivery mode materially changes which candidates rank where and which survive: the injectable and wound routes tighten the immunogenicity threshold to 0.35, so the same candidate that passes under a mask patch may be vetoed outright under either of those two. Allowing the user to select it freely would amount to letting the user decide, without understanding the consequence, which candidates count as acceptable. Binding it to the route leaves it changeable, but only through the meaningful change of altering the product form. The "application technique" — spreading, manual application, spraying, contact with a wound — was accordingly demoted from an independent layer to a descriptive string carried by each route. It filters no scaffolds and participates in no scoring, and as a required user choice it would only have produced a decision carrying no information.

**Safety returns a verdict, not a score.** The safety panel does not present a composite safety figure. It presents each item's measured value, threshold, verdict and assessment status, and rolls those up into one verdict with four possible values: everything clear, at least one item exceeded, nothing exceeded but at least one item inside the 10% boundary zone, and nothing assessed so the verdict cannot be reached. The fourth value exists specifically so that "not measured" is never rendered as "passed". This rule runs through the whole interface.

**"Not assessed" is not zero.** All nine scores are nullable at the data layer, and a null means no measurement exists, which is a different thing from a measured zero. The interface renders a null as not assessed, without a failing badge. The weight of this convention is visible in the coverage numbers: immunogenicity has two independent pathways, one covering 117 constructs and the other 186, and after the overlap there remain 198 constructs for which both are empty. Rendering those as zeros would put nearly two hundred candidates on screen described as immunogenic at zero and therefore entirely safe, when none of them has ever been measured.

**A ranking-only score is not dressed as a probability.** The functional scores for the anti-inflammatory and anti-melanogenic directions come from models that discriminate whether a peptide looks like a known functional peptide, not from measurements of anti-inflammatory or anti-melanogenic activity. The database marks those rows as usable for ordering only and not readable as a probability, so the score carries a ranking marker on both list rows and the score grid, receives no probability colouring, and gets no pass or fail badge.

**A veto reason is generated from the item that actually failed.** A vetoed candidate displays the specific item that exceeded its threshold — toxicity, haemolysis or immunogenicity, as the case may be — rather than a generic safety failure. The three have different next steps, and a generic message causes the user to take the wrong one.

### 3.4 What is genuinely live and what is still provisional

A distinction the platform's own documentation insists on is between values that come from the database and values that are still temporary. This is the material for a design or engineering narrative.

Live throughout: the content of all five pages comes from the database, and every figure in a list or a detail can be traced to a specific table and column. The safety verdict is adjudicated at request time against the thresholds of the selected route. The composite score is recomputed at request time under the route's weight tier, so the same candidate has a different composite under each of the five routes. The six generated analysis blocks are produced by the server from that construct's real scores and thresholds, and every number in them corresponds to a field in the same response. The conversational panel is attached to the same server-side generator and answers from real data rather than returning fixed text.

Provisional, and for different reasons: selecting a scaffold or a linker does not change the candidate peptide set, because all 496 stored constructs carry a placeholder scaffold binding and because every stored construct's linker foreign key points at the first row of the sample table; the interface states this plainly in each case rather than allowing the user to believe the choice had an effect. Both choices do change the sequence assembled from each candidate and the fusion length reported alongside it. The linker library has no route dimension, so all five routes see the same list at step four; the scaffold library has had one from the start. The fusion sequence is incomplete when no scaffold is specified: requesting a single construct's detail marks the scaffold segment as unavailable and the page draws only the two segments that genuinely exist, whereas a sequence obtained by completing all five builder steps is complete, because it is assembled from the scaffold and linker chosen in that session, and the interface labels it as assembled from request parameters rather than produced by the pipeline.

Three rougher interaction points belong in the same account because they affect handling rather than data correctness. The library browser's own search and sort controls were added during the rollout and now cover four filters and three orderings, and paging is real paging rather than an increased page size. The application has no catch-all route, so an unknown address lands on a blank page. And two files remain in the project that are no longer rendered, one a stylesheet attached by the site template and one an older pinned-style file with no reference anywhere in the project.

Two further items are deliberate restraint rather than defects. Two directions carry a pending-signature marker: the anti-inflammatory and anti-melanogenic directions hold data but the pipeline has not signed off on it, and the interface marks their status rather than hiding them or presenting them as equally mature. And material form is an extracted value: a scaffold's material form — lyophilised sponge, self-assembled hydrogel, injectable gel, film, fibre, sheet, solution formulation — is not a field in the dataset but a classification extracted by hand from three prose columns, and although the interface uses it as a filter, the column itself still awaits the team's confirmation.

## 4. Data assets

### 4.1 Three layers

The data is three layers at three scales, and mixing them up destroys the meaning of any statement about it.

**The peptide layer.** Roughly twenty million short peptide sequences and the scores that a dozen predictive tools assigned to each. This is the raw material; every calculation in the screening pipeline happens here; users never see it directly, only its filtered results.

**The construct layer.** 496 assembled constructs, the output of a full screening run: which peptide paired with which scaffold and which linker, the aggregate of nine scores, and whether the safety gates were cleared. This is the layer the product serves from.

**The reference layer.** Small but the most "hard" content in the system: the formal entries for scaffolds and linkers, including real amino-acid sequences, patent and applicant information, and experimental and regulatory evidence. This layer was compiled by hand from real patent records rather than produced by a predictor.

The three layers are joined by foreign keys: the construct layer points at the peptide layer through a peptide identifier, and at the reference layer through scaffold and linker identifiers. One link in that chain is currently broken, in the construct-to-scaffold segment, and section 4.4 explains it.

### 4.2 The peptide layer

The principal table holds 20,248,885 rows and about 8 GB of data. Each row carries the sequence itself, its length, a source identifier, a source version date and an MD5 checksum of the sequence. A unique constraint requires the combination of sequence, source and source version to be unique, which prevents duplicate insertion within a source while allowing different sources to keep their own copies of the same sequence. Lengths in the database run from 1 to 30 residues, the declared range being 1 to 30 and the measured minimum 1 and maximum 30.

Sequences come from ten sources recorded in a manifest table that stores, per source, its version date, file checksum, scan start and end times and row count written. By row count one metagenomic source dominates: 19,154,247 sequences, about 94.6% of the library. That is why the typical sequence in the library is short — metagenomic fragments are already broken. The remaining nine sources contribute roughly 1.1 million sequences between them, including a complete and a reviewed set from a reference proteome database, a clustered set, structure chains, and several earlier dated snapshots. A secondary attribute table exists to carry parent sequence headers, taxonomy, structure identifiers, reading frame and source file offsets; it is measured empty, with no rows at all, so those attributes are currently unavailable as a class.

Prediction scores are stored in one long table keyed on the combination of peptide identifier and tool name, with each row supplying that tool's score for that peptide, a human-readable label of the kind `Non-Toxin`, `Soluble` or `≤40`, and a structured detail field recording the model name, the threshold, the component sub-scores and whether inference ran on a GPU or a CPU. That table measures about 367,717,240 rows and 130 GB, the largest in the database. Coverage is measured as follows: twelve tools cover all 20,248,885 peptides at 100%, namely toxicity, haemolysis, allergenicity, the three antioxidant heads, antibacterial activity, cell penetration, solubility, thermal stability, anti-melanogenic activity, and the MHC class I immunogenicity predictor. The last of these reports 100% because its denominator counts only the 134,888 peptides inside its applicable length range rather than the whole library, and the haemolysis figure rests on a 500,000-peptide sample rather than the whole library.

The second immunogenicity pathway is stored separately, organised by peptide and allele, at an estimated 147.5 million rows and 35 GB across 131 alleles. It retains each peptide's binding rank and binding grade on each allele, which would support finer analysis than a single score, but the product does not use that granularity. Two practical facts attach to it: its table-creation statement cannot be found in the repository of the service that reads it, so its schema provenance needs confirmation from the pipeline maintainers; and it is large enough that even counting its rows exceeds the service's query timeout.

One trap is worth stating explicitly. The aggregation-propensity score is not in the peptide score table. Querying that table for an aggregation tool returns zero rows, because the value is not produced by an external service but computed by the pipeline during assembly, using a residue-scale aggregation table applied to the sequence, and the result is stored only in the construct layer's score field. Any implementation that reads only the peptide score table cannot obtain it.

### 4.3 The construct layer

The construct layer is one core table of 496 rows and 744 kB, one of the smallest business tables in the database and the one the product serves from. Its fields fall into four groups. Identity and classification records the construct identifier, the functional direction, the channel (selected or control) and the status (passed or pending signature). Assembly uses three foreign keys pointing at a peptide, a scaffold and a linker. Results include the rank, the aggregate of nine scores held in a structured field, a delivery score computed under an older convention, and three booleans recording whether haemolysis, MHC class I and MHC class II were assessed. One further historical field records the scenario value at assembly time, in which two spellings of the same concept both occur; the product does not expose it.

The distribution across the four directions is the table's most important structural fact, because it determines each direction's availability in the interface.

| Direction | Selected channel | Control channel | Total | Status |
|---|---|---|---|---|
| antioxidant | 113 | 57 | **170** | all passed |
| antibacterial | 7 | 58 | **65** | all passed |
| anti_inflammatory | 87 | 67 | **154** | all pending signature |
| antimelanin | 83 | 24 | **107** | all pending signature |

Every row belongs to either a selected or a control channel. The control channel is not filler: it holds the lowest-scoring candidates from the same ranking, and it exists to provide a baseline of known-poor activity against which later rounds can confirm that the scoring system is genuinely discriminating rather than sorting noise inside a narrow dynamic range. Control-channel constructs go through the same safety gates and the same scoring as selected ones, so their numbers are comparable.

Scores are heterogeneous by direction, which is the table's second structural feature. The aggregate field contains 26 distinct keys across the table and no row holds all of them. Six keys are shared across the four directions — toxicity, haemolysis, MHC class I immunogenicity, aggregation propensity, allergenicity and cell penetration — and the rest are direction-specific: the antioxidant direction uses its own activity predictor and two branch heads, the antibacterial direction an antibacterial model, the anti-inflammatory direction an anti-inflammatory channel together with the control values from four other channels, and the anti-melanogenic direction a tyrosinase-inhibition model. Understanding this matters, because otherwise rows that carry fewer scores read as incomplete when in fact those scores do not apply. The structurally notable case is immunogenicity: the MHC class I key is present in all 496 rows but holds a real value in only 117 of them; the other 379 are empty, for the reason given in section 6.3.

Two field names that do not match their contents must be known to anyone reading the table. The field named as a full fusion sequence contains, in all 496 rows, a pipe-delimited concatenation of a placeholder scaffold name, a linker and a peptide sequence, and not one row holds a real amino-acid sequence; the assembly script's own comment explains why — both the scaffold and the linker were placeholders, and the script's job was to write the smallest viable combination so that the schema and sample data were complete, with the real binding left to the compute service. The delivery-score field holds scores under four older delivery methods whose keys are not the same coordinate system as the current five application routes, and no invertible mapping exists between them, so the field is retained for inspection but never emitted. One further semantic marker appears on 261 rows with a single value — ranking only, not readable as a probability — and that single value pins the character of the anti-inflammatory and anti-melanogenic scores into the data itself.

### 4.4 The reference layer

**Scaffold data exists at two granularities**, and mixing them produces errors.

The three older tables are at the granularity of individual sequences and records: 27 patent records, one per patent sequence or patent product entry, of which 16 carry a complete amino-acid sequence and 11 carry none, corresponding to applications the patent proposes but for which no sequence is disclosed; 11 groups, which is the experimental-group dimension, clustering the 27 records into 11 groups; and 12 experiment records, one per combination of experimental group and evidence level, recording which experiments were performed, the principal result, where in the source the result appears, and the limitation of the evidence.

The two newer tables are at the granularity of protein clusters, which is the granularity the product works at: 8 rows in the cluster table, one per protein cluster, and 16 rows in the sequence table, one per patent sequence variant, attached beneath its cluster. These two tables come from a 30-column master table compiled by team members, and it is only in that master table that the five application-tag columns exist; the three older tables have none of them. Those five tags are the only place in the dataset that states which application routes exist, and they are the only basis on which the product narrows scaffolds to a route, which is why the newer pair is not a duplication but a necessity.

The eight clusters are reproduced below. The evidence column records the highest tier that can be verified for that cluster, not a measure of how much experimental work has been done.

| Cluster | Applicant | Category | Representative sequence length | Highest evidence | Routes admitted |
|---|---|---|---|---|---|
| Recombinant humanised type III collagen HC8/HC16 | Jinbo | recombinant collagen | 501 | E5 | mask patch, injectable filler |
| COL3A1 functional region, 16 tandem repeats | Jinbo | recombinant collagen | 490 | E5 | mask patch, injectable filler |
| Recombinant human type XVII collagen fragment | Trautec | recombinant collagen | 466 | E5 | hair care, wound dressing |
| Human-like collagen FHLC | Juzi | recombinant collagen | 1071 | E5 | topical film, mask patch, wound dressing |

| Triple-helix-mimetic recombinant human collagen III | Wuhan | recombinant collagen | 225 | E1 | wound dressing |

The grading rule is itself part of the data. **E1** is purified protein or physicochemical or cell-free work; **E2** is cell work; **E3** is animal work; **E4** is human use or a controlled clinical study; **E5** is regulatory review, a controlled clinical study and post-market safety data. Three of the eight clusters reach E5, one reaches E4, and two sit at E2 or below. Both of the highest sit on recombinant collagen, which is consistent with that category already having registered products in the domestic market.

The level is easy to read backwards and must be read as "the highest tier that can be verified". A label of E5 means there is regulatory review or post-market safety data supporting that protein's safety in *some* use; it does not mean the new use the platform proposes has been validated. Conversely a label of E1 does not mean the protein is worthless; it means the publicly verifiable evidence stops at the cell-free tier. Each record carries an evidence-limitation field precisely to record that gap.

The hair-care route is the one where this reading matters most. It appears to be backed by two well-established applicants, but taken apart it is not. The E5 attached to the type XVII collagen fragment comes from that applicant's wound-dressing product, which holds a provincial medical-device registration for non-chronic and post-procedure wound care, and has nothing to do with hair; in this material, hair care appears only as a patent's proposal for follicle repair and scalp care. The spider silk variant reaches only E1, with its stated limitation being predominantly cell-free and ex vivo evidence. The other four application tags each have at least E4 or E5 behind them; this one has no human or regulatory evidence corresponding to the indication it is labelled with. The product's handling is to keep the route and carry an explanatory string in its definition, writing the fact that evidence is still accumulating into the data rather than deleting the entrance or letting it appear as mature as the other four.

Read the table the other way round and the mapping from route to available scaffold is complete. The five routes admit **2, 4, 2, 4 and 2** protein clusters respectively, and no two routes point at exactly the same group, which is why the five routes can use the dataset's existing tags directly rather than requiring a parallel classification.

| Route | Clusters admitted | Scaffolds |
|---|---|---|
| injectable filler | 2 | both Jinbo clusters |
| hair care | 2 | Trautec type XVII, AMSilk eADF4(C16) |
| topical film | 2 | Bolt 18B, Juzi FHLC |
| mask patch | 4 | both Jinbo clusters, Yusen, Juzi |
| wound dressing | 4 | Wuhan, Trautec, Yusen, Juzi |

**Linker data also exists in two sets.** The older table has 6 rows, placeholder entries consisting of three lengths each of two motifs, and every one of the 496 constructs' linker foreign keys points at the first of them, a five-residue `GGGGS`. From the construct table alone, therefore, no linker selection difference is visible. The newer curated table has 15 rows, the formal entries landed from the product design's data source, each carrying a name, sequence, length, rigidity class, unit composition, description and literature provenance, with rigidity presented on a five-step scale from fully flexible to fully rigid. The two sets coexist rather than being merged, in order to preserve the existing foreign key's referent; each linker response carries a source-table marker so it is clear which one it came from, and the decision whether to merge them is deferred until the pipeline re-assembles constructs under real scenarios. The construct table's foreign key is not the only basis for assembly: a caller may specify a linker in the request, in which case the fusion sequence is assembled from that one, the construct's stored value is left alone, and the two provenances are reported separately.

### 4.5 The broken link: construct to scaffold

All 496 constructs point at the same scaffold row, and the real scaffolds live in a different table with an incompatible identifier system. The two sides have no mapping and no overlapping names — the placeholder side uses a few abbreviations for silk and elastin, and the real side uses patent constructs of eight structural proteins — so the placeholder cannot be turned into a real scaffold by changing one identifier. What is missing is an entire correspondence.

The pipeline created the placeholder state because it had no scaffold-selection step: it took the first row of the scaffold table and the first row of the linker table and wrote the construct record from them, and the content written into the fusion-sequence field was the scaffold's *name* treated as a sequence, joined by pipe characters to the linker and the peptide. That path applied to all 496 constructs across all four directions, which is why they point at the same row, and why that row's sequence field holds a literal marker string and reports a length of zero.

A binding strategy has been designed and implemented in the codebase, though not yet written to a production database. Its reasoning is as follows. Team material covers the scaffold side completely — eight clusters, sixteen patent sequences, one representative sequence per cluster, with application tags, evidence levels and experiment records — and does not address the construct side: nothing in it connects any row to a specific peptide or functional direction. The only common key that can join the two sides is therefore the **application route**: a scaffold belongs to several routes through its application tags, and a construct's recorded scenario name resolves to several routes, and scaffolds on the same route as a construct are that construct's candidate scaffolds. This is only valid if the route's meaning is the same on both sides.

The material's own conventions are internally inconsistent in one respect, and the discrepancy is specific. It declares that the master table uses four application tags and that the older scenario and delivery tags are deleted, yet the same material's marker columns still number five, the fifth being hair care, and the repeat-unit and purification-tag variants inherit the parent protein's tags. Recomputed under four tags and without inheritance, the per-route cluster counts are 2, 3, 4 and 1; counted from the material's actual markers, the hit rows number 3, 8, 7 and 5, with hair care hitting 5 rows. The data processing follows the material's declaration — four tags are read, and the hair-care column is read but maps to no route.

Landed so far: the scaffold-read path was corrected after the source directory was renamed, since the import script still pointed at the old location and could not have rebuilt the library; the tag convention was changed to a column-numbered table in which the hair-care column explicitly maps to nothing, with a comment recording that this is the team's declared position rather than an oversight; and a binding script was added which writes the eight clusters into the scaffold table with real representative sequences and lengths, then re-binds each still-placeholder construct by route. The write is keyed by name, so the plan can be generated without a database connection and exported as a directly executable SQL file for the database host to run when it is reachable again.

The binding rule is: a construct's recorded scenario resolves to a route; the route yields candidate scaffolds from the material's application tags; among those, take the one with the highest evidence level; where levels tie, take the one tagged by fewer routes, on the reasoning that a scaffold admitted by one route fits that use better than one admitted by three; where still tied, order by short name so that the result is reproducible. The rule's output is that the antioxidant, antibacterial and anti-inflammatory directions all land on wound dressing and share the Trautec type XVII collagen, while the anti-melanogenic direction lands on mask patch and uses the Jinbo cluster. Three directions sharing one scaffold is a consequence of their functional descriptions all pointing at wound use, not a coincidence of values. The mask-patch and injectable-filler defaults are additionally pinned explicitly to the Jinbo cluster, because both routes have two candidates at the same evidence level, the rule falls to the tandem-repeat construct in a tie, and that is exactly the cluster the material declares as no longer inheriting tags; the pinned choice carries tags under either convention, so the default does not depend on how that question is resolved. Two verification results are worth recording: the whole change was executed against a temporary local instance at production table structure, and every construct's fusion sequence was checked residue by residue to equal scaffold plus linker plus peptide; re-running the same SQL updated zero constructs and left the scaffold row count unchanged, so the operation is idempotent.

The bindings written by this strategy are the platform's per-route default, not a pipeline output — no record shows the pipeline ever made this pairing — and the service already distinguishes the two cases: a binding recorded on the construct reports as verified, while one specified in a request reports as inferred.

### 4.6 Semantic conventions

Every item in this section corresponds to a misreading that has either happened or is easily made. Their common feature is that the data is not wrong, while the conclusion drawn from a naive reading of it is very wrong.

**An empty value is not zero.** All nine scores are nullable, and an empty value means no measurement exists, which is not the same as measuring zero. The library's empty values concentrate in immunogenicity: alongside the 379 empty MHC class I values there are 135 genuine zeros, of which 116 are immunogenicity measured at zero, meaning the model judges the sequence essentially unlikely to be recognised. Rendering the empty values as zeros would put over a hundred candidates on screen described as immunogenic at zero and therefore completely safe, when none has been measured. The response body carries a boolean assessment flag alongside every nullable score precisely so that a caller does not have to guess what an empty value means.

**A very small non-zero value must not be rounded to zero.** The library holds several hundred values that are extremely small but genuinely non-zero, concentrated in the cell-penetration and solubility columns, and rendering them at two decimal places turns all of them into `0.00`, presenting a measurement that carries signal as one that carries none. Score formatting therefore falls back to significant figures when the value is small enough.

**The functional scores of two directions are for ordering only.** The anti-inflammatory and anti-melanogenic scores come from models that discriminate whether a sequence looks like a functional peptide, not whether it suppresses inflammation or inhibits melanin production, and the database marks those rows as ordering-only and not readable as a probability. The product accordingly shows a ranking marker on both the list rows and the score grid for those two directions, applies no probability colouring, and issues no pass or fail badge.

**The MHC class II percentile rank runs in the opposite direction to every other gate.** The tool outputs a percentile rank in which a smaller number means stronger binding, and strong MHC class II binding is the route by which helper T cells are recruited and an immune response is initiated, so this gate is higher-is-better, and passing means the rank is above the strong-binder sub-threshold. Any implementation that writes "above the limit means exceeding" without checking the direction states the opposite conclusion on this gate.

**The immunogenicity threshold varies with the application route.** Toxicity at 0.38 and haemolysis at 0.55 are global; immunogenicity is not. The wound-dressing and injectable-filler routes tighten it to 0.35, mask patch and topical film sit at 0.50, and hair care is relaxed to 0.60. The same construct can therefore pass under one route and be vetoed under another, which is not a data inconsistency but part of what a route means.

**Every stored construct's scaffold binding is a placeholder.** All 496 rows point at the same placeholder record, whose sequence is a marker string of length zero, so no real scaffold can be read from a construct and no complete fusion sequence can be assembled from it. The product's handling is to mark the binding's provenance honestly rather than to invent a plausible-looking sequence.

**The slot named for one function carries another.** Among the nine scores, the slot named for antioxidant activity actually carries **the functional score of whichever direction the row belongs to**, filled by four different predictive tools in the four directions. The slot name is a leftover from the single-direction period, and reading it literally would make three quarters of the library appear empty. The response supplies two further fields giving that score's tool key and display name, to remove the ambiguity.

**The functional-score tool keys are inconsistently spelled.** The four directions draw from four keys mixing hyphens and underscores and mixing upper and lower case, which is not a typographical error but the spelling used when the pipeline wrote them. The keys are passed through as identifiers and mapped to tool names only for display.

**A direction's name in the database differs from the product's earlier name for it.** The library's second direction reads as antibacterial, while earlier product documents called it antimicrobial, which is a broader term; the model behind it does in fact judge antibacterial activity only. The library's value is now used consistently.

**The old delivery scores and the new application routes are not the same coordinate system.** The library's delivery scores are divided by four physical methods — topical, nanocarrier, microneedle, injection — while the product's five routes are divided by contact interface and barrier integrity. The two axes are independent and there is no invertible mapping. The new composite score is recomputed entirely under the route convention, and the old values are retained for inspection without being emitted.

### 4.7 Gaps and open data questions

Four definite absences. First, the construct-to-scaffold binding is entirely placeholder, which is the largest single gap and is addressed by the strategy in section 4.5. Second, the peptide layer's secondary attribute table is empty, so parent sequence, taxonomy and structure-chain provenance are unavailable as a class. Third, 11 scaffold patent records disclose no sequence; they remain valid as evidence that a patent proposes an application, but they cannot participate in sequence assembly. Fourth, the two immunogenicity pathways have not been merged — MHC class I has a value on 117 constructs, MHC class II on 186, at least one of the two on 298, and both empty on 198.

Two coverage points to keep in mind. The peptide library's measured lower bound is one residue, and the library genuinely contains constructs whose peptide is two residues long, while product prose has long used the range three to thirty; the discrepancy does not affect function, but external description should use the library's actual range. And haemolysis prediction covers only a 500,000-peptide sample at library level, so although all 496 constructs have a value, that coverage would become a limitation if the safety gate were ever extended to a larger candidate set.

One qualitatively undecided item is material form. Each scaffold's assigned form is not a field in the dataset but a judgement extracted from three prose columns of product use, potential application and key result. It is the only ruler available for secondary filtering, and all eight clusters have an entry, but the classification itself still requires per-item confirmation by the team, because the reliability of the extraction varies widely between entries — one cluster whose patent text states self-assembling collagen fibre or hydrogel yields an unambiguous classification, while another whose evidence limitation records no material-support or intact-silk-fibre evidence can only be classified as a solution-phase ingredient. The two entries needing the closest review are exactly the ones whose source wording leaves room: one mentions self-assembly, fibrillation and film formation together, so more than one material form applies, and one spans sheet and solution forms while being admitted by three routes, where the classification directly affects how the second filtering level behaves. Two further entries depend on parsing a compound phrase such as injectable lyophilised fibre, and need confirmation as well, since "injectable" describes an administration method rather than a material form and treating it as a form would duplicate the classification.

## 5. Biology and the screening pipeline

### 5.1 Why three segments

A usable recombinant fusion protein is three segments, each with a different biological role, and if one is missing the chain does not hold.

**The functional peptide** produces the activity. It is a short amino-acid chain, and this project's working range is 1 to 30 residues, which falls in what the literature generally calls the short-peptide range. Four reasons support short peptides over complete active proteins. They can be made by solid-phase chemical synthesis, and cost grows steeply with length: a peptide around twenty residues is a routine order, while one of a hundred residues becomes a recombinant expression task. Their small molecular weight gives them markedly better penetration of tissue and cell membranes, which is a requirement for any application that has to reach skin or a wound. They are generally less immunogenic. And they can be introduced by gene fusion without a separate chemical coupling step. The cost in the other direction is that a short peptide alone has almost no structural stability, is degraded quickly by proteases in biological fluid, and supplies no mechanical property at all — which is precisely why a scaffold is needed.

**The scaffold protein** carries the peptide and turns the molecule into a usable material. It is drawn from natural structural proteins, and this library uses three categories: recombinant humanised collagen, silk fibroin, and spider silk. Their common feature is spontaneous formation of a stable higher-order structure: collagen's three chains wind into a triple helix through the geometric constraint of a repeating glycine-any residue-hydroxyproline motif; silk and spider silk pack via a repeating glycine-glycine-any residue unit into β-sheet layers, which is where their exceptional tensile strength and toughness come from. The scaffold determines what physical form the finished fusion protein can take — solution, gel, lyophilised sponge, fibre or sheet — which makes it not a passive carrier but the determinant of the product form. That is the deeper reason the product takes the scaffold choice out of the user's hands and derives it from the application route.

**The linker** is the small segment between them. It carries no biological activity and its role is spatial: it lets the peptide and the scaffold each fold correctly without interfering with the other. Without it, a peptide placed directly on the scaffold surface tends to fail in one of two ways — the peptide is buried by a scaffold domain so that its active site cannot reach its substrate, or the peptide interferes with the scaffold's folding and destroys the mechanical behaviour the scaffold was there to supply. Linkers divide into two mechanical classes. A flexible linker, typically a repeat of `GGGGS`, has essentially no conformational constraint (glycine has no side chain) and adds solubility (serine is small and polar), so its net effect is to leave both ends free to move. A rigid linker, typically based on `EAAAK`, forms a salt bridge between its glutamate and lysine that locks the segment into an α-helix and fixes the distance between the two ends. The two are not interchangeable, and choosing wrongly removes the property the linker was introduced for. The linker is also the only one of the three assembly parts the user selects directly, for the reason given above: flexible versus rigid is a trade-off a use case can answer without protein-engineering knowledge, whereas the scaffold choice requires knowing eight specific proteins, so it can only be derived.

The three parts are coupled, which is the difficulty of the whole exercise. Changing the peptide changes the whole protein's hydrophobicity and charge distribution and therefore its aggregation tendency; changing the scaffold changes the chemical environment the peptide sits in and therefore its apparent activity; changing the linker changes the relative orientation of the two ends. This is a joint selection problem over a combinatorial space, not three independent optimisations. The pipeline's own decomposition — full enumeration over linkers, ranking-based pre-selection over peptides, route-based narrowing over scaffolds — is what turns an intractable full space into three tractable sub-problems.

### 5.2 The four functional directions

Four directions are pre-computed. They are not four arbitrary labels; each corresponds to a different class of biological activity and depends on a different class of predictive model, which is why the four are not equally mature.

**Antioxidant activity** addresses free-radical scavenging. Under oxidative stress a cell produces excess reactive oxygen species, which attack lipids, proteins and nucleic acids and are a shared cause of delayed wound healing and material ageing. The model used outputs two independent branches: one predicts radical-scavenging activity (a "branch head" here means the sub-network within a multi-task model dedicated to one class of output) and the other predicts metal-ion chelation, which suppresses hydroxyl radicals generated by transition-metal catalysis and is the second pathway of the antioxidant mechanism. A support-vector classifier is also present in the library and is used as the basis for slicing the candidate pool when ranking. This is the most mature of the four: the pipeline ran completely and all 170 constructs cleared the safety gates.

**Antibacterial activity** addresses inhibition of bacterial growth. The predominant mechanism is that a cationic antimicrobial peptide adsorbs onto a negatively charged bacterial membrane, and above a threshold concentration inserts into and disrupts the membrane, causing the contents to leak. Such peptides are characteristically net-positively-charged and amphipathic, which is why the top-ranked antibacterial sequences in the library are visibly amphipathic. The model used combines a published antimicrobial framework with protein language model features, and a second channel from a multi-label framework serves as a cross-check. This direction holds only 65 constructs, of which the selected channel holds just 7 — the thinnest selected channel in the library — because the antibacterial model's score distribution is narrow, so few candidates both pass a high percentile cut and satisfy the safety gates.

**Anti-inflammatory activity** addresses suppression of the inflammatory response. The model comes from a multi-label framework, taken through the channel dedicated to anti-inflammatory peptides. A technical limitation must be presented honestly in both the data and the interface: this class of multi-label model discriminates **whether a sequence looks like a known functional peptide**, not **whether it measures anti-inflammatory activity**. Its high score means the sequence sits near known anti-inflammatory peptides in feature space; it does not mean the sequence has been shown experimentally to suppress inflammation. For that reason the library marks this score as usable for ordering only and not readable as a probability, and the product issues no pass or fail badge in this direction. The direction holds 154 constructs, all pending signature.

**Anti-melanogenic activity** addresses inhibition of melanin production and maps directly onto whitening-type functional materials. Its target is usually tyrosinase, the rate-limiting enzyme on the melanin synthesis pathway, so inhibiting its activity reduces melanin output. The model used is a tyrosinase-inhibition peptide predictor with a different technical lineage from the neural networks used in the other three directions, which is one reason it is listed separately. The direction holds 107 constructs, also all pending signature.

The difference in technical lineage across the four has a data consequence: all four functional scores are stored in the same slot, but the tool keys used to retrieve them differ, and each direction additionally has a different number of exclusive tool scores. This is not a design defect; the four directions genuinely use different models on different scales.

### 5.3 Scaffold biology

The eight clusters divide into three categories by biological origin, and the distribution of uses follows a clear pattern.

**Recombinant collagen**, five clusters, comprising a humanised type III collagen and its tandem-repeat variant, a type XVII collagen fragment, and a human-like collagen. Collagen is the principal extracellular matrix component of the dermal layer; its native triple helix gives it both biocompatibility and load-bearing capacity, and it is degraded progressively through the body's collagen metabolism. This category carries most of the library's high-grade evidence: four of its five clusters reach E5, because they correspond to real domestically registered medical-device products, including an injectable collagen filler, a repair dressing, and a lyophilised-fibre product. The product admits them under injectable filler, mask patch and wound dressing.

**Silk fibroin**, one cluster, the short recombinant fragment. Silk fibroin's β-sheet layers give it high strength together with good film-forming and fibre-forming behaviour, and it is both degradable and low in immunogenicity. This cluster's representative sequence is only 62 residues, the shortest in the library, which shows it is a heavily truncated engineered fragment rather than a complete silk heavy chain. Its evidence level is E2 (cell work) and its stated limitation records no evidence of a material support or an intact silk fibre structure, which is why its material form is classified as a solution-phase ingredient. The product admits it under mask patch and wound dressing.

**Spider silk**, two clusters, a recombinant spider silk protein and an engineered variant. Spider silk is among the toughest known natural fibres, its mechanical behaviour coming from the alternation of β-sheet crystalline regions built from highly repetitive short units and amorphous regions. The first has evidence level E4 (human use or a controlled clinical study) and a material form of film and solution. The second reaches only E1, with a stated limitation of predominantly cell-free and ex vivo evidence, and a material form of fibre and film; it is one of the two scaffolds admitted by the hair-care route, and the weakest-evidence scaffold in the library.

Evidence level must be read as "the highest tier that can be verified", not as a completion score. A scaffold labelled E5 has regulatory review or post-market safety data supporting its safety in some application, which does not mean the new use proposed on the platform has been validated. Conversely E1 does not mean the protein is useless; it means publicly verifiable evidence stops at the cell-free tier. The evidence-limitation field records exactly that gap.

### 5.4 Linker enumeration

The linker is handled at two levels. One is specified by the user, and consists of the rigidity class: a flexible unit lets the peptide swing freely on the scaffold surface and a rigid unit holds it away, which changes how much of the peptide the scaffold occludes. This trade-off needs no protein-engineering training, so a single linker is exposed as a changeable option alongside the scaffold as one of the two assembly targets. The other level stays in the background and consists of combinatorial enumeration over multiple sites. This is search work rather than judgement work: the combination space of flexible and rigid units is unfolded completely, placing a flexible or a rigid unit at each of one to five sites, and the full permutation across five sites is 62 combinations (two at one site, four at two, eight at three, sixteen at four and thirty-two at five). The pipeline filters those 62 in turn, and what the user sees is the filtered conclusion rather than a choice inside the combination space. The current state of this round is that only placeholder values were written.

Each enumerated combination has to pass two checks to enter the candidate set. The first is **aggregation propensity**, measured by a residue-scale aggregation score: the tool assigns each amino acid an aggregation-propensity value, slides a window across the sequence and accumulates, and outputs an estimate of the sequence's tendency to form amyloid or nonspecific aggregates, where lower is better and a value above 22 flags an aggregation-prone sequence. Aggregation is the most common cause of failure in recombinant protein expression and purification — once a protein forms inclusion bodies, activity testing is moot — so this filter sits at the enumeration stage and combinations removed by it never reach the result page. The second check is the **three safety gates**, which use the same adjudication as for the whole construct.

The enumeration's outcome is shown honestly on the result page: how many combinations were enumerated, how many were removed for aggregation, and how many were removed by the safety gates. This is not decorative information; it tells the user what filtering pressure the surviving candidates came through, rather than presenting them as dropping out of a black box.

### 5.5 The four screening rounds

The pipeline is a funnel that converges continuously. It was run once per direction, and the responsibilities and measured durations of the rounds are as follows.

**Round one, functional ranking.** The direction's functional predictor scores and sorts the whole 20-million-peptide library. One design detail matters: the cut does not simply take the high end, but simultaneously retains a control channel. The high end goes into selection, and the lowest-scoring batch is kept as a control. The control channel supplies a baseline of known-poor activity, which is how the system demonstrates that the scoring genuinely discriminates rather than sorting inside a narrow dynamic range. This round has the largest computational volume but a manageable duration, on the order of half an hour, because the functional predictor is a batch inference task.

**Round two, safety hard-threshold screening.** Three veto items are checked simultaneously; exceeding any one removes the candidate immediately, and it does not participate in any later weighting. This round is the pipeline's bottleneck: the toxicity predictor's inference is single-threaded, and completing the whole library takes on the order of twenty-four hours without interruption. This round is also where the design's position on safety is most visible — passing is passing, failing removes the candidate from the pool entirely, and there is no compensation mechanism of any kind.

**Round three, developability deep scoring.** Candidates that cleared the safety gates are scored on multiple developability measures and combined into a composite used for ordering. The weighting procedure is set out in section 5.7, and its defining feature is that it uses no manually preset weights. The round takes on the order of five hours.

**Round four, construct enumeration and assembly.** The highest-ranked functional peptides are assembled with a scaffold and a linker into complete constructs and written to the database. This round is what turns "a functional peptide" into "a molecule that can be sent to a laboratory", and it is where the 496 constructs come from. One step in this round is still a placeholder: the scaffold segment carries no real sequence, and the script wrote only the minimal viable combination of peptide, placeholder scaffold and placeholder linker so that the schema and sample data were complete, leaving the real binding to the compute service.

### 5.6 Safety gates and where the thresholds come from

Safety adjudication consists of three veto items and two non-vetoing soft signals. Each has a different threshold provenance, and the difference is marked explicitly in both the data and the interface.

**Toxicity** is predicted with ToxinPred3 at a threshold of 0.38, with lower being better (a lower score means less toxin-like). This value is not the tool's default. The project scored the whole 20-million-peptide library, inspected the distribution, and calibrated 0.38 as the value that suppresses both false negatives and false positives on this distribution; the tool's own default admits a set of candidates this library does not support. This is the one threshold in the whole system that is explicitly a project decision rather than a tool recommendation or a route convention.

**Haemolysis** is predicted with HemoPI2 at a threshold of 0.55, also lower-is-better. Haemolysis is the destruction of red blood cells with release of haemoglobin, and is a risk that any material contacting blood or entering the body must exclude. Note that this tool covers only a 500,000-peptide sample at library level; all 496 constructs have a value, but its coverage is weaker than the other tools'.

**Immunogenicity** consists of two independent pathways, which is the part most easily simplified away. The **MHC class I pathway** is predicted with MHCflurry, which estimates the probability that a peptide is presented on the cell surface by a class I molecule, as a proxy for T-cell immunogenicity — the higher the presentation probability, the more likely the peptide is recognised and cleared by cytotoxic T cells. The tool's own strong-binder boundary is around 0.50, which the platform uses as the general threshold and tightens to 0.35 under the wound-dressing and injectable-filler routes. The **MHC class II pathway** is predicted with NetMHCIIpan, whose percentile rank measures the peptide's presentation by a class II molecule and hence its ability to recruit helper T cells; **a lower rank means stronger binding**, and a rank in the top 2% is the conventional strong-binder boundary. The two pathways measure different things, are not substitutes for one another, and the rank cannot be divided by a hundred to pass as a probability. The product emits them as two separate fields; MHC class I participates in the veto, while MHC class II, because its coverage is incomplete, is reported as a soft signal.

Coverage is the most practical limitation here. MHC class I has a value on only 117 constructs, because the tool applies only to peptides of 5 to 15 residues and the library's peptide length distribution extends well past that. MHC class II has a value on 186. At least one of the two has a value on 298 constructs, and **both are empty on 198**. For those constructs the immunogenicity gate is in the not-assessed state.

**Not being assessed does not eliminate a candidate, and this is an explicit pre-existing rule of the pipeline**, written in the same position in all four direction proposals: a metric eliminates a candidate only when a measurement exists and falls outside the boundary; an absent measurement eliminates nothing but must be reported as not assessed. The product follows the rule strictly, and the interface's rendering of an unassessed gate as not assessed rather than as passed is a direct consequence — presenting an unmeasured item as passed amounts to giving a safety assurance with no basis.

The two **non-vetoing soft signals** also need stating. **B-cell epitope propensity** is predicted with BepiPred-3.0 at a threshold of 0.1512. It measures the likelihood that the peptide is recognised by an antibody, which affects neutralising-antibody risk but does not directly trigger a T-cell response, so it is reported rather than used to veto. **Allergenicity** is predicted with AlgPred2 at a threshold of 0.3. It is an important signal for topical materials and is likewise reported rather than used to veto — a point that must be distinguished in the interface, since marking the whole safety group as veto gates is wrong.

Each threshold carries a provenance marker distinguishing three cases: **from the tool itself** (toxicity and haemolysis), **from the application route's screening profile** (immunogenicity's 0.35, 0.50 and 0.60 tiers), and **from a platform constant** (the MHC class II strong-binder boundary at the 2nd percentile, taken from the tool's conventional usage, where the pipeline originally carried it only as a measurement without a threshold). The distinction has practical value: changing a tool threshold affects every route, whereas changing a route profile affects one.

### 5.7 The composite score

The composite is not a prediction but a derived ordering value, formed by weighting several developability components. Its algorithm comes from the pipeline's third round, and its central design is that **no weight is manually preset**.

Each component is normalised within the candidate pool and oriented so that larger is better throughout, which means components where larger is worse — allergenicity, B-cell epitope propensity, aggregation propensity — are inverted after normalisation. Each component's weight then comes from its **winsorised standard deviation**. The standard deviation measures how spread out a set of values is; "winsorised" means the extreme values are truncated to the 5th and 95th percentiles before the calculation, so that a single outlier cannot dominate a component's weight. The weights are normalised across the components so that they sum to one.

The effect is that **a component with genuine discriminating power in a given pool is automatically up-weighted, and a component with almost none is automatically down-weighted toward zero.** If every candidate in a direction sits near 0.4 on thermal stability, that component cannot discriminate; its standard deviation approaches zero, and its weight follows, rather than occupying a fifth of the composite because someone assigned it 0.2. Conversely, if cell penetration spans a wide range in that pool, its weight rises automatically. This is why the four directions have different weights: they are computed, not configured.

Six components participate: cell penetration, solubility, thermal stability, allergenicity (inverted), B-cell epitope propensity (inverted) and aggregation propensity (inverted). The first three are modulated by the application route's weight tier, whose values are **1.8 for high, 1.0 for medium and 0.4 for low**; the latter three participate at 1.0, preserving the contribution the data gives them without introducing a route difference. **When a component has no measurement, it drops out of the sum rather than entering as zero**, and the remaining weights are renormalised, so the denominator does not distort because of a missing measurement.

None of the six components is a functional activity score, and that is deliberate. It follows from a principle the pipeline established: **each metric is used exactly once, in one place.** The functional score appears only in round one's ordering and is never referenced again. The rule targets a specific and plausible failure mode — if the functional score kept participating in later weighting, it would completely mask scaffold and route suitability, and the pipeline would select the peptide with the highest functional score rather than the peptide that performs best against the current scaffold and route. Those are not the same thing, and the platform needs the latter. The same principle has a second consequence: a candidate with an exceptionally high functional score that fails a safety gate is still eliminated, and receives no compensation for its activity.

One correction to the pipeline's own implementation belongs here, because it changes what the stored numbers mean. The pipeline defined three delivery multipliers over cell penetration, solubility and thermal stability, but computed them by looking up a weight dictionary whose keys did not include the multiplier names. The solubility and thermal-stability multipliers therefore never took effect; only cell penetration received one, and the composite scores under the four delivery methods came out nearly identical. The service keeps the design intent of three modulated components and applies all three multipliers from the route's weight tier, placing the other three components at 1.0. Its composite is therefore not on the same axis as the library's stored delivery scores; those are retained for inspection and not published.

To make the number checkable, every response also returns every normalised component value used, the weight each component received, the multiplier each received, and the size of the pool the normalisation was computed over. Any composite score can be reproduced by hand from a single response, without querying the database again.

### 5.8 Delivery routes: barrier integrity determines immune exposure

The five application routes are not five parallel labels. They are ordered by one physical quantity: **how intact the barrier is at the interface the construct ultimately contacts**. That quantity directly determines the likelihood that the immune system encounters the fusion protein, and therefore how tightly the immunogenicity threshold should be set.

The four barrier states, from weakest to strongest, are: **entry into tissue** (injectable filler, where the barrier is bypassed entirely and the construct enters the dermis or subcutaneous tissue — the only one of the five that genuinely enters the body); **a breached barrier** (wound dressing, applied to an open wound, in direct contact with the wound bed and tissue fluid); **an intact barrier with occlusion** (mask patch, intact skin but used under occlusion, where occlusion raises stratum corneum permeability and therefore raises both penetration and sensitisation risk); **an intact barrier without occlusion** (topical film, spread on the skin surface as a film or a protein layer, with the construct essentially remaining outside the stratum corneum); and **a non-living surface** (hair care, contacting the keratinised, dead hair shaft, which has no blood vessels, lymphatic vessels or immune cells, so the construct never enters the body).

The immunogenicity threshold follows that order: entry into tissue and a breached barrier both take **0.35**; the two intact-barrier routes take **0.50**; the non-living surface is relaxed to **0.60**. The wound-dressing route taking the same strict threshold as injection is the point that needs stating explicitly: the wound barrier is already broken and the construct is in direct contact with tissue fluid, so its immune exposure is of the same order as injection, and treating it as intact skin underestimates the risk.

The three modulated developability components are likewise derived from that physical picture rather than assigned arbitrarily. **Topical film** is applied at ambient temperature, so the thermal-stability requirement is lowest (0.4); it involves neither a needle nor occlusion-enhanced permeation, so membrane crossing is the main bottleneck and cell penetration is required most (1.8); and spreading into a film requires high solubility (1.8). **Mask patch** relies on occlusion to enhance permeation, so its penetration requirement is slightly below the unoccluded topical route and takes the medium tier; film formation and impregnation require high solubility, at 1.8. **Injectable filler** enters tissue directly, so penetration is no longer necessary (0.4), with solubility and thermal stability at the medium tier. **Wound dressing** likewise does not need penetration (0.4). **Hair care** is applied to the hair shaft, so its penetration requirement is lowest (0.4), while solubility is required to be high (1.8) to support shampoo and conditioner formulations.

Beyond weights and thresholds, each route carries a set of **non-vetoing additional checks**, being the process or safety requirements specific to that dosage form: wound dressing requires sterility, biocompatibility and endotoxin control; injectable filler additionally requires injectability, rheological performance and in-vivo safety; mask patch requires an irritation assessment under occlusion; topical film requires film-forming and spreading behaviour; and hair care requires adherence to the hair shaft, wash resistance, and no adverse effect on hair feel. These items are not in the data; they are the experiment list the route must still complete, and the interface presents them as guidance rather than as adjudication.

### 5.9 What is excluded from this version

The pipeline's complete design has eight rounds, of which the product presents the first four. The latter four all concern three-dimensional structure and are explicitly excluded from this version.

The exclusion is on measured grounds rather than a convenience. Round five generates a three-dimensional structure for each construct with a folding predictor; round six computes solvent-accessible surface area and three-dimensional aggregation propensity on that structure; round seven derives a second composite from the structure; and round eight validates a small number of selected constructs with a higher-accuracy model. The problem is in round five: the library's silk-type scaffold sequences are dominated by short glycine-glycine-any residue repeats, and on such highly repetitive sequences, which lack a natural homologous structural template, general-purpose folding predictors return low confidence — a measured mean local distance difference test value of about 0.42, on a scale where 1.00 is perfect and above 0.70 is generally required before a structure is considered trustworthy. Using an untrustworthy structure for subsequent solvent-exposure and aggregation analysis yields numbers with no decision value.

The product's response is therefore to concentrate resources on the first four rounds — making each candidate's sequence, per-item scoring basis and expression plan solid — rather than displaying a structure that cannot be used. One related historical residue also needs clearing: an older version of the interface contained two different things both called the composite score, one being the round-three weighted value described above and the other being round seven's "four tenths solvent-accessible surface area plus four tenths aggregation-propensity correction plus two tenths structural confidence". The latter depends on the products of rounds five and six and is excluded along with the structural track; the composite the product presents refers only to the former.

## 6. System architecture

### 6.1 Overview

The system is three components and one database, with data flowing in one direction. A description of the development form follows; the deployed form, which contains no resident service process and no runtime database access, is set out in section 7.

The user side is a single-page web application built with Vite and running in the browser. In both development and production it communicates only over HTTP against an API prefix, which in development is forwarded by the build tool's proxy to a local backend port and in production is forwarded by the deployment platform. The point of the arrangement is that the frontend contains only relative paths, so neither cross-origin configuration nor a change of backend address is a frontend concern.

In the middle is a FastAPI backend, the only component that touches the database. It does not write, and it does not compute predictions. It does three things: it shapes the remote database's contents into the form the frontend needs; it takes over the responsibilities the pipeline left to a compute service — real scaffold binding, fusion-sequence reconstruction, per-route composite recomputation and safety adjudication; and it generates the interpretive text and the dialogue.

The database is a PostgreSQL 16.15 instance on an Ubuntu workstation, reached over the network. Placing the database on the workstation rather than alongside the service has two reasons: the two largest tables total roughly 165 GB and do not belong in a migrating service, and the models that produced the data mostly require GPUs and already run on that workstation, so keeping the database next to the inference avoids moving data back and forth. The cost is that the whole service depends on network reachability to that machine, which is recorded as a risk rather than designed away.

The technology choices follow the structure. The frontend is Vite 8 with React 19, TypeScript 6 and Tailwind 4, routed with react-router-dom 7, with Lucide for icons and hand-written interactive controls built on Radix's unstyled primitives rather than an off-the-shelf component library. Tailwind's CSS-first configuration is used, with theme variables written directly in the stylesheet. The backend is FastAPI with Pydantic for response models and psycopg 3 as a synchronous database driver. The direct reason for FastAPI is that the response model can be declared in Pydantic, so the interface's field structure can be exported as a schema and compared field by field with the frontend types — of high value in a change driven by the frontend contract. The reason for a synchronous driver rather than an asynchronous one is that the few session settings that must take effect on every connection are more directly expressed with synchronous connection pool semantics, and this project's queries are all primary-key or small-set retrievals, so concurrency pressure is not a bottleneck.

### 6.2 Frontend

The frontend is a single-page application with five pages over five routes. Its code is divided into four blocks, and that division is itself a constraint.

**Data access** is concentrated in one directory and consists of three files: one issuing requests and normalising errors, one binding each backend endpoint to a named function, and one holding the TypeScript mirror of the backend response models. The mirror's field names **retain the backend's snake_case** without camel-case conversion, so that the interface schema and the frontend types can be compared mechanically, and any rename surfaces immediately rather than being absorbed by a naming-conversion layer.

**State and side effects** are handled uniformly by two custom hooks, one for loading a resource and one for performing an action. The loading hook carries a ticket counter internally: each request increments it, and a response whose ticket is no longer current is discarded. This addresses the case where a slow earlier request returns after a fast later one and overwrites it when filters are changed quickly. Errors are normalised into several distinguishable types, so the interface can state a specific cause rather than a uniform failure.

**Shared display components** hold the three panels the result page and library page have in common: the safety gate list, the tool score grid and the generated text block. They were extracted for a concrete reason — threshold drift originated precisely from two separate implementations of these panels.

**Presentation mapping** only translates the identifiers the backend supplies into interface elements: icon names to icon components, group display labels, human-readable weight-tier labels, formatting and adjudication rules, and local computation of sequence properties. One constraint runs across everything: **the frontend performs no threshold comparison and no weighting at all.** The composite score and the safety verdict are computed by the backend and returned with the response; the frontend only presents them. That constraint has three direct benefits: a threshold exists in exactly one place, so the interface and the generated text can no longer state opposite conclusions; the frontend does not have to carry the nine scores and the weight tiers into the browser to compute anything; and a future change to a convention is a backend change only, with no frontend release.

No state management library is used. Each of the five pages owns its own data, pages share no mutable state, and route parameters carry what passes between them. The choice is proportionate to the application's size, but it has one consequence worth noting: the result page's scaffold preview is implemented by rewriting a query parameter, so the browser's forward and back buttons participate in that state.

### 6.3 Backend

The backend is divided into four layers, with hard constraints between them.

**Routes** perform parameter validation, call the service layer and serialise the response; no SQL and no computation appear there. **Services** carry every threshold, weight and business judgement, and write no SQL. **Repositories** perform SQL queries and row-to-dictionary conversion only, with no threshold or convention. **Models** define the response contract, with field names matching the frontend types.

The single purpose of these constraints is **that every threshold exists in exactly one place.** The purpose is not abstract tidiness. An audit on 2026-09-17 recorded three defect classes caused by a copied value drifting: the same safety threshold table written twice, once in each of two pages, under a comment claiming the two shared a definition; the immunogenicity threshold hard-coded globally at 0.50 while the route definitions specified three tiers, with the result that a construct sitting exactly on the tightened threshold was displayed as clearing every gate; and generated prose citing a 0.70 acceptance floor for the antioxidant predictor that existed in no tool metadata, leaving a reader unable to find where the number came from. With thresholds centralised in the service layer, these three classes are structurally impossible rather than merely fixed.

**Reference data is the backend's single source of truth.** The five application routes' definitions (contact interface, barrier tier, immune-exposure description, three weight tiers, immunogenicity threshold, additional checks, application technique), the nine indicators' tool metadata (tool name, what is measured, direction, grouping, threshold and threshold provenance, coverage note, whether it is a veto gate), the pipeline's four retained and four excluded rounds, and the four directions' display information and status derivation rules are all written in one module. Everything in that module is read by the frontend as data, and the frontend keeps no copy of any of it.

The database access layer is a connection pool, and every connection has two settings applied at creation: marked read-only, and given a query timeout. A second group of tuning settings for large tables — sequential and bitmap scans off, forcing index use — is applied **only where needed**. That group helps on the 378-million-row score table and hurts on the 496-row construct table, where a list query with no filter should go sequential and forcing an index only makes it slower. A caller therefore declares it explicitly when accessing a large table, and leaves the query planner alone otherwise.

Error handling distinguishes two failure classes and maps them to different status codes. **The database being unreachable** — network down, authentication failed, connected to the wrong instance — returns 503 rather than 500, on the reasoning that the database is on another machine and unreachability is transient, so a client retry is reasonable; the body carries an error identifier and a troubleshooting note. **A query failing** — the statement itself being wrong or timing out — returns 500. The distinction lets the interface state an accurate cause rather than reporting everything as a server error.

### 6.4 The interface

The backend provides **19 read-only endpoints** in five resource groups, plus one write endpoint for dialogue. This is the development form of the interface, and it is also what the export script draws on — in the static deployment, every file the frontend reads is content one of these endpoints returned.

A second data source exists in the production deployment, returning the same structures and dispatched through the same frontend entry point: the static deployment reads files, while development and any build configured with a remote interface address reads the service. This dispatch is what allows the interface to remain unchanged by the deployment form — the five pages' code is one and the same in both forms.

**Reference data, six endpoints:** a health and database-connectivity check; a single call returning all reference data at once; functional directions; application routes; tool metadata; pipeline rounds; and actual coverage statistics per predictive tool. The all-at-once endpoint carries the heaviest load and is also the most economical: a page that needs directions, routes, tools, evidence levels, material forms and scaffold categories gets all of them in one response, avoiding a waterfall of requests when the page opens.

**Constructs, six endpoints:** a paginated list supporting filtering by direction, route, channel and status; a single-construct detail; the scaffolds available for that construct under that route; the per-tool score rows for the construct's peptide; the construct's generated text blocks; and the conversational endpoint. List endpoints uniformly return an array of items plus a total, a page size and an offset, so the frontend can display a total without a second counting request.

**Build, one endpoint**, the only endpoint on the interface that performs a combination rather than reporting a stored quantity. It accepts an application route, one or more functional directions, a scaffold and a linker, and returns the candidates under that screening sorted by composite score, with each assembling a fusion sequence. The two assembly targets act independently and either may be omitted, in which case that part falls back to the value stored on the construct row; neither enters the candidate adjudication, and both only affect the assembled sequence and the reported fusion length. Its definition of the candidate set differs from the construct list's in that it takes the selected channel: the control channel is the negative-control arm, and ranking control markers into the candidate list makes both unreadable. Sorting covers all candidates before any slicing by offset and page size, because a record's composite depends only on its own direction's weight pool, and that pool is read independently of the request and cached per direction, so sorting the whole set first is the correct order rather than a matter of convenience — and it is what gives the offset meaning at all. The safety-verdict counts likewise cover the entire matched set rather than the returned page.

**Scaffolds, three endpoints, and linkers, two:** list and detail, with scaffolds additionally offering which constructs use a given scaffold. A scaffold's list and detail are deliberately different shapes — the list omits sequences and patent variants, the detail includes them — so that the list can return all eight entries at once without carrying long sequences.

### 6.5 Data-contract decisions

**A null value must carry a marker.** All nine scores are nullable in the response model, and every null is accompanied by a boolean assessment flag. This removes the need for a caller to distinguish a missing field from a zero value, both of which are null in JSON, and therefore removes any possibility of reading a not-assessed item as a zero.

**The composite travels with its route, and is reproducible.** A single construct's response carries a map indexed by route, keyed to the five route identifiers, each entry containing that route's three modulated component values, the composite, and every intermediate quantity needed to reproduce it — each component's normalised value, the weight it received and the multiplier it received. One response is therefore enough to recompute the composite by hand, without re-querying the database or reading the source.

**The safety conclusion is a structure rather than a sentence.** The response is an object containing the route's immunogenicity threshold, an overall verdict, an array of per-gate detail, the list of unassessed gate keys, and the list of vetoed gate keys. Each gate's detail carries the indicator name, tool name, measured value, threshold, threshold provenance, pass or fail, whether it is borderline, whether it is a veto gate, and which side counts as exceeding. The last field is necessary because MHC class II is the one gate where lower is worse, and any presentation logic that writes "above the limit means exceeding" without checking it states the opposite conclusion there.

**A score's readable character follows its data.** Every score carries a semantic marker in the response, distinguishing readable-as-probability from ordering-only. The marker is present not only in detail views but on list rows, because three of the four directions derive their ordering from a model and one of those is explicitly not a probability. Without the marker on list rows, a ranking position would be displayed as a confidence.

**Generated text carries its sources.** The analysis text is generated in six fixed blocks: safety interpretation; functional peptide origin and composition; linker and assembly; expression and handling; within-direction comparison; and the risk list. Each block carries, besides its prose, a list of source entries naming the response field paths it cites; and the whole response carries a generator marker stating whether the current text is template-generated or model-generated. The marker's purpose is to let the frontend label the text's origin honestly rather than presenting template copy as model output. The generation capability is abstracted as a protocol rather than a function, so connecting a language model later means adding an implementation and switching the registration, with the routes and the response models unchanged.

**Dialogue and analysis share one generator.** The conversational endpoint accepts a question and the construct's context and returns an answer together with a set of suggested follow-up questions. The current implementation gives deterministic answers to recognised question types and an extensible prompt for unrecognised ones; the configuration reserves a place for a generator and a model name, and if the generator configuration points at a model implementation that has not been registered, the service prints a warning at start-up and continues with the template implementation.

## 7. Deployment

### 7.1 The change that was made

The deployment form changed fundamentally during the rollout. Previously a Python service had to run continuously and connect to a PostgreSQL instance on a school workstation, so every interface call crossed the network to that machine. That dependency chain became unavailable — the machine is school property outside the project's control and is now offline. The goal was therefore to make the project run completely with **no backend process and no database access**, moving everything the service previously computed at runtime into a one-off export step.

The resulting form is: data is exported once, before deployment, into static files which the frontend reads directly; and only the conversational feature, which by nature cannot be pre-generated because it must handle free-form questions, is handled by an edge function on the deployment platform that forwards to a language model, with the model's key existing only in that function's environment variables and never reaching the browser.

One premise behind the direction deserves stating. The export's output is not the database's tables converted raw into JSON; it is **a call to the backend's own interface functions, storing whatever they return**. The reason is that every threshold, weight and adjudication in this project is concentrated in one place in the service layer, and the 2026-09-17 audit recorded the same safety threshold copied into four places, one of which conflicted with the route definitions and caused a construct sitting on the tightened threshold to be displayed as clearing every check. An export script that bypassed the service layer and assembled output with its own SQL would be a fifth copy of the same class of defect, and it would ship silently. Every byte of the export is therefore the service's own output, and the static files are identical to the interface responses — which is the only basis on which these files can be considered trustworthy enough to publish.

### 7.2 The static layer

The frontend's static data source sits alongside the existing data-access layer and is dispatched by the same entry point; the five pages' code was not modified. The layer has one inviolable constraint: **it duplicates no threshold, weight or adjudication in the browser.** It does two things only — take one page from an already-sorted list, and concatenate three already-exported amino-acid sequences into a fusion sequence. The first contains no convention; the second is string concatenation. Because the composite score varies with the route and the safety verdict varies with the route's immunogenicity threshold, both are computed once per route during export and stored, rather than being recomputed in the browser.

Three rules govern its behaviour and each corresponds to a failure that would otherwise be silent. **Return values have three states**, expressed as a covered flag plus a payload, with identifier-keyed branches marked accordingly: "this export does not cover that path" falls through to the network, while "this export covers that path but the record is not in it" raises a not-found directly. Merging those two into a single null would send a missing record on the static deployment into the single-page application's route fallback, return a fragment of HTML, and be reported as an invalid response rather than a missing record. **Assembly is by name, not by identifier**, and when no linker identifier is supplied the layer must fall back to the linker recorded on that construct, whose omission produces a sequence-level discrepancy visible as fifty-nine residues against fifty-four. And **assembly must write out both a scaffold object and a linker object**, not merely their names, because the construct detail page's header, the Summary card's scaffold and linker rows, the eligible-scaffolds highlight and the linker tab all read those two objects; writing only the names leaves the page stating "scaffold unassigned" above the real sequence, and the defect appears only in the pure static deployment.

The construct detail's six generated analysis blocks are exported **per construct**, with the prose continuing to describe the stored record even when the request carries a scaffold or linker identifier; the page therefore flags this explicitly. The static layer must not attempt to rewrite the analysis text for a request-time pairing.

### 7.3 The local fallback

The remote database is an instance on a workstation reached through a network tunnel, and the workstation is not always powered on. When the database is unreachable the entire service, and with it the interface, fails — which is exactly when development needs it most. The service therefore carries a local fallback: a small SQLite file answering the same queries. The repositories are not duplicated; each PostgreSQL construct a repository actually uses is translated into its SQLite equivalent in one place.

The fallback is controlled by a configuration value taking three states. The default probes the remote database before the first data access and switches to the local file if the probe fails, recording the reason. A second state connects only to the remote and never falls back, and is what deployment uses, so that a database failure is not quietly masked. A third reads only the local file and never touches the remote, and is what tests and offline development use. A connection lost mid-run is covered too: if a probe succeeds and the connection later fails, the service switches to the local file in the same way, and returning to the remote requires restarting the process.

The local file is generated from a fixture script and built on demand if missing, or rebuilt manually. It holds four hand-made constructs whose purpose is to make every code branch reachable in a single run: one carries a placeholder scaffold binding and must not emit a fusion sequence; another carries a binding with a real sequence and must emit a complete fusion sequence, and the two together give the composite weighting pool two observations to compute a spread from; two further constructs cover a second direction, one of them on the control channel, which is what verifies that the builder ranks selected-channel candidates only. Because the second direction then has a single selected-channel record, its composite score is empty as expected, which incidentally covers the builder's null ordering. One of the constructs also records the sample table's second linker, distinct from the other three, so that "when no linker is specified, each row falls back to its own stored value" is an assertable fact rather than a statement. The fixture's declared lengths agree with the sequences beside them, because a declared length that disagrees with its own sequence produces false failures whose cause looks like a code defect. These four constructs are fixture data, not pipeline output, and must not be quoted as a result.

The fallback never happens silently. The service prints a warning at start-up; the health endpoint's backend field states which side is supplying data and, when it is the local file, adds the fallback reason and an explanatory note, with the server field showing the SQLite version rather than the PostgreSQL version. Whether an environment is running real data or fixture data is read from those fields, and not inferred from the values, because the numeric assertions elsewhere in this document hold only against the remote database.

### 7.4 The production deployment and its boundaries

The platform is live. The deployment target is a Cloudflare Pages project, and the production address is https://pepticraft.pages.dev. Deployment is a three-step chain: export the data from the real database, build the frontend, and upload the built output. The build tool used for the upload is not part of the repository and is not installed into the frontend project, so the repository stays clean.

One operational trap is worth recording because it has already cost time: the deployment tool's stored authorisation can expire, and in a non-interactive environment it refuses to use the interactive credentials and requires a long-lived API token instead. When the stored authorisation has expired there are exactly two ways forward — a human completing a fresh authorisation in a browser, or supplying an API token with the appropriate permission. One value in the project's notes that looks like a credential is in fact the account identifier and will not work as a token.

Several properties of the deployed system are consequences of its form and should be known to anyone using it. **The data is a snapshot**: every number on the site comes from the database as it stood at export time and does not update itself, so after new constructs are added the data must be exported and the site redeployed. This is a definition of the form rather than a defect, but it means that the question "is the data current" is answered by "when was it last exported" rather than by the system guaranteeing it. **Re-running predictions is outside the system's capability**: the scores are dead data computed offline and stored, and re-running any predictor is pipeline work rather than a matter for the deployment or the interface. **Conversation history has an upper bound**: the interface sends the whole conversation to the backend, and only the most recent turns reach the model, which bounds the request size at the cost of the model forgetting the earliest questions after many turns. And **the conversational endpoint currently has neither authentication nor rate limiting**: question length and single-message length are bounded, but request frequency is not, and that should be configured at the platform rather than relied on at the application layer.

## 8. Development record

### 8.1 The four cycles

The platform went through four build-test-learn cycles, each of which changed a structural decision rather than a line of code.

**Cycle one: the static-data layer was removed.** The five pages originally rendered a hard-coded dataset, and the engineering description already claimed search, filtering and sorting when only filtering existed. The decision was to delete the static data module and its type definitions outright rather than migrate them, so that no page could quietly keep rendering a constant. Every value on every page now traces to a table column, and the frontend's TypeScript mirror deliberately retains the backend's snake_case field names so that the schema and the types can be compared mechanically with no naming-conversion layer in which a rename could hide.

**Cycle two: thresholds were pulled out of the frontend into one place.** The 2026-09-17 audit's three defect classes are described in section 6.3. The response was a hard layering constraint — routes validate and serialise, services hold every threshold and weight, repositories write SQL and nothing else, models define the contract — together with the rule that the frontend performs no threshold comparison and no weighting. A threshold now exists in one place, and changing a convention is a backend change.

**Cycle three: the build moved from the browser to the server.** The builder originally fetched a direction's construct list and sorted it in the browser. Three properties of the correct answer were violated by that arrangement: a row's composite score depends only on its own direction's weight pool, which is read independently of the request and cached per direction, so sorting a page in the browser produces scores that move when the request narrows; ranking must cover the entire matched set before any slicing, which is what makes an offset meaningful at all; and candidates must come from the selected channel only, since the control channel is the negative-control arm. With a single server endpoint returning the full ranking, the counts cover the matched set rather than the page, and candidates whose composite cannot be computed sort last rather than participating as zeros. A fourth property came out of the same work: each row carries its own binding status, so a single response can contain rows with a full fusion sequence and rows without one.

**Cycle four: two inconsistencies were found and fixed.** When no route was specified, the immunogenicity gate was skipped entirely — the safety verdict took the route parameter directly, and with it empty the per-route gate was never added to the gate list, so the response came back clear while the unassessed gate appeared in neither the gate list nor the unassessed list, reading as a pass. The composite score had always defaulted to the first route when none was given; the two now share one default. Separately, the linker detail view declared and rendered unit composition and priority reason while the query never selected those two columns, so every linker detail returned an empty composition.

The pattern across all four is the same: each cycle removed a class of defect by changing where a decision lives, rather than by patching the instance that surfaced.

### 8.2 Three defects of the deployment change

Three further defects belong to the record because they are all of the kind that looks correct and is not, and each is a direct consequence of the deployment form changing.

**A static file silently shadows the live service.** The export directory sits under the frontend's asset directory, and the development build tool returns any static file in preference to the proxy. A developer working locally therefore sees the previous export's snapshot rather than the running database's current content; more seriously, a production build configured with a remote interface address is also shadowed by the snapshot, and the interface cannot tell. The fix is a switch whose resolution order is: an explicit setting first, then the static layer standing down when a remote interface address is configured, and only then the development-environment test. Development therefore still goes to the live service, and the static path can be forced with an environment variable when it needs validating.

**The export's list rows and the search columns disagreed.** Construct-list search covers four columns — peptide sequence, source, accession and source version — but the exported row originally carried only the sequence. The consequence is that on the deployed site a search by accession returns rows from the service and none from the static site, and neither answer looks wrong on its own. The exported row now carries all four, with a test guarding the contract.

**Numbers were written differently on the two paths.** The service writes every number in the fact block with Python's format strings, and the edge function writes the same numbers with JavaScript. Rounding agrees, but the notation differs in two places: Python switches to scientific notation below 1e-4 or at or above 1e6, while JavaScript's default conversion does not switch at those points. The consequence is that a number the model cites cannot be found on the page — and "every number the model cites can be found on the page" is the entire reason the fact block exists. The fix is for the edge function to implement the same notation rules explicitly, with both outputs checked against one shared case table; the table deliberately includes the intervals of each notation, because a notation switch written incorrectly inside the fixed-notation range would not surface in any check.

One further fix belongs to the same class: when a query specifies only a linker and no scaffold, the static layer must fall back to the linker recorded on that construct, or a sequence-level discrepancy goes unnoticed — on the fixture this appears as fifty-nine residues against fifty-four.

### 8.3 Verification

Testing runs in three layers, and a failure in each means something different: a data-layer failure means the mapping is broken, an interface-layer failure means the contract has drifted, and an interface-presentation failure means the rendering and the data disagree.

**The backend suite** runs offline, needing neither a database nor a resident service. It stands at 115 tests, of which 113 pass and 2 are skipped; the skips are because the fixture data happens not to satisfy the tested condition — one of them requires a record with an empty rank field, and all four fixture constructs have ranks — which is a test precondition rather than a defect. Frontend type checking covers three projects, the third of which covers the edge function specifically, because that file is the only TypeScript in the repository that runs in production without running in a browser and had never been checked by the build.

**The static data layer's walkthrough** runs without any backend in Service, covering what the other two layers cannot because they both assume a service is available while the static deployment has none. It serves the export directory over HTTP and reads it with the frontend's own data layer. One assertion compares the sequence the interface assembles with the service's sample, residue by residue, confirming the static layer and the service layer assemble identical results; another confirms that every read the page makes comes from a file, failing if any read reaches the network. The suite stood at 82 assertions when the rollout record was written and has since grown to 91.

**The two browser-free walkthroughs** render the real application in a DOM emulation, walk the builder through its five steps with real clicks, and point the application's relative API requests at a genuinely running service — so what they assert is the real response as the component renders it, not a fixture written to satisfy the assertion. The builder walkthrough runs 33 assertions and the library-search walkthrough 25. They can answer questions about logic and markup; they cannot answer questions about layout, because the DOM emulation has no layout engine.

**A manual page-by-page walkthrough** with both processes running checks that the landing page's counts match the interface, that the library's fields and filters are populated from real data, that every builder choice actually reaches the result, that the result page's nine scores, safety verdict and sequence segments are complete, and that fields the dataset genuinely lacks are listed as unavailable rather than rendered as empty cards.

**The minimum self-check sequence after a change** is: read the health endpoint to confirm the database is reachable and the database name is correct; fetch the reference data and confirm the direction counts are 170, 65, 154 and 107 with two directions ready and two pending; fetch one construct's detail and confirm the nine scores, the five per-route composite values, the safety gate detail and the three sequence segments are all present; and then open the frontend and walk the pages.

One further consistency check covers the fact block, the prompts and the edge function, all of which exist in two languages. The fact block the model sees is written in Python on the service and in TypeScript in the edge function, and the two cannot share code, so three properties are each guarded by a test: the prompts are identical word for word, the fact block's sections and field names are identical, and every number is written identically. The number-notation rule described in section 8.2 is the reason the third exists.

The three-dimensional rounds, five through eight, are explicitly out of scope. ### 9.2 What remains

Three items gate a fully finished deployment.

**The exported data must be regenerated whenever the source data changes**, since the deployed site is a snapshot. Once the scaffold binding is back-filled into the production database, the export must be re-run and the site redeployed.

**The model key must be configured and the path exercised once for real.** The edge function needs three environment variables — interface address, key and model name — configured in the platform's environment settings, with the key never entering version control. Deployment works without them, with the conversation degrading to template answers and saying so, which is a supported state rather than a failure. Once configured, a live round should be run to confirm the numbers the model cites agree with the page and that the timeout and error degradation paths work. All three test layers currently use injected calls and issue no real network requests, so the true end-to-end behaviour of that path remains unverified.

**The linker library needs a route dimension.** Each of the fifteen curated entries carries a name, sequence, rigidity class, unit composition and literature provenance, but none states which application route it suits, whereas the scaffold library has had that dimension from the start. The consequence is that selecting a linker cannot be narrowed to the current route, so the builder offers the same list under all five routes. Filling the gap requires judging each of the fifteen by purpose rather than by structure, which is a team task rather than an inference. Worth confirming at the same time is the original source of those fifteen curated entries: they were landed from the product design's data source, and after that design source was deleted along with the frontend's static data layer, the library's current entries are the only surviving copy.

### 9.3 Known limitations

**Nothing here is evidence of activity.** Every number on the platform is a prediction from a model trained on other data. A high composite score means a construct looks developable under models with known biases; it does not mean the peptide scavenges free radicals, kills bacteria, suppresses inflammation or inhibits tyrosinase. The platform's contribution is to make the predictions legible and to keep unsafe candidates out, not to replace the assay.

**The models are not equally trustworthy**, and although the interface states which is which, it cannot make them equal. Two directions are work-in-progress and labelled as such in the data, in the interface and in the interface's response. The anti-inflammatory models are blocked on a benchmark whose negative examples are random fragments rather than confirmed non-anti-inflammatory functional peptides, which rewards the shortcut "is this a functional peptide" instead of the intended question; one of the two has a further problem of overlap between its training and test material. The tyrosinase-inhibition predictor, rebuilt from a different source, is absent from the production database, so the anti-melanogenic direction falls back to a predictor with no enrichment power on this library, and the radical-scavenging predictor's distribution is squeezed into too narrow a band to rank on. For two of the four directions the honest statement is that the platform produces a ranked shortlist for wet-lab validation rather than a set of leads.

**Coverage interacts with the veto logic in a way that is easy to miss.** The immunogenicity gate is a veto gate, and it is unassessed for 198 of the 496 constructs, and assessed by only one of its two pathways for many more. A gate that was not evaluated eliminates nothing — that is the explicit rule — so a construct can be reported as clearing every gate it was measured on while a gate that could have excluded it never ran. The interface reports this as an indeterminate verdict rather than a clear one, which is the correct handling, but the underlying fact is that the safety case for the long-peptide majority rests on toxicity, haemolysis and developability alone.

**The composite score is a ranking value with no absolute meaning**, and its weights differ between directions and between runs over time. It is reproducible, since the response carries everything needed to recompute it, but two composite scores from different directions are not comparable quantities, and a composite from before a weighting-convention change is not comparable to one from after.

**Two predictors are unusable as hard gates on this material, one is missing where it was expected, and one direction has an unanticipated length ceiling.** The three thresholds that are not the project's own are explained in section 5.6. Beyond those: the B-cell epitope predictor had no rows in the database when the antioxidant direction ran, and the data-driven weighting handled that correctly by driving its weight to zero, which means the antioxidant composite contains no epitope contribution — a fact that must be named as an artefact of which tools were loaded rather than reported as a modelling result. The epitope predictor also overflows badly on short sequences, calling most of the library an epitope, so its continuous score is used for relative ranking and its absolute value is not trusted. The allergenicity predictor's third-party specificity is low and it labels roughly a third of a 20-million-peptide library as allergenic, which is why it is reported and never used as a gate. And the anti-inflammatory direction's model effectively stops around 25 residues, because its training set does, so the direction's top-ranked candidates concentrate at 21 to 25 residues by constraint rather than by merit, and a stratified bucket covering 26 to 30 residues is empty.

**The peptide library's length range in product prose differs from the library's own.** The library's measured lower bound is one residue and it genuinely contains two-residue constructs, while long-standing product description uses three to thirty. The discrepancy does not affect function, but external description should use the library's actual range. Separately, haemolysis prediction covers only a 500,000-peptide sample at library level, which is why it came out at 100% coverage on the 496 constructs but would be a limitation if the gate were extended to a larger candidate set.

**Two smaller limitations belong in the same list.** The sequence-level secondary attributes — parent sequence, taxonomy, structure chain, reading frame, source offset — are unavailable because the table that would hold them is empty, so no feature requiring provenance back to a source record can be offered. And the remote database is a single point of dependency in the development environment: the address is reached through a tunnel, and if either end is down the service is unavailable, which the local fallback and the interface's error distinction make diagnosable but do not remove.

### 9.4 Security and privacy

The software's own security posture is simple and follows directly from the architecture. The backend is read-only against the database: every connection is marked read-only and no code path writes. The single write endpoint is the conversational one, and it writes nothing — it is read-only in effect and is named for the HTTP verb rather than for a mutation. There is no authentication and no user account system, because the platform collects no personal data, stores no session state, and has nothing to protect beyond a read-only view of a research database. The service holds no secrets in the repository; the database password comes from the environment.

Privacy has one substantive dimension and it is favourable. All of the predictive services run as local HTTP services on the project's own workstation, and no peptide sequence is submitted to a third-party API at any point. The sequences in the library come from public biological databases and from patent records, so there is no personal-data question in the input either. The generated text has a configured language-model provider slot, currently set to the template implementation, and the marker in every response states which produced the text, so template-rendered prose is never passed off as model output. Should a model backend be connected, the disclosure obligation attaches at the point of connection rather than now.

## 10. Open decisions

The following are not technical choices but product and convention decisions that require a determination from the team. They were recorded in an earlier round and none has been resolved by the change of deployment form.

**The construct-to-scaffold binding rule** is the most substantive. All 496 constructs point at one placeholder record whose sequence is a marker string of length zero, so no real fusion sequence can be emitted for any construct. The real scaffolds are in the curated library, which uses a separate identifier system with no overlapping names. Closing the gap requires deciding which functional direction pairs with which scaffold, and that rule is a product judgement rather than an implementation detail. The strategy and its defaults are described in section 4.5 and are implemented in code but not yet written to the production database.

**Whether the pending-signature directions are displayed prominently or hidden by default.** The anti-inflammatory and anti-melanogenic directions hold complete data but no signature, and the anti-inflammatory direction's own design document states it must not be presented as ready. The product emits the status truthfully, but whether the interface presents those constructs as candidates with a prominent marker or hides them by default is a product decision. One complication: those two directions have rank fields with values, so presenting by rank without the marker could mislead.

**The composite weighting convention needs alignment with the pipeline maintainers.** The service includes solubility and thermal stability among the route-modulated components, on the ground that the product defines three weight tiers for every route and that two of the three tiers would otherwise be idle. That convention is not identical to the pipeline's existing implementation, which modulates only one component because its multiplier keys did not match. Until the two conventions are unified, the service's composite and a pipeline recomputation will not agree. The convention itself has also not been confirmed with the pipeline's owner.

**Whether the veto set has three items or four.** The service implements three (toxicity, haemolysis, immunogenicity), following the pipeline's explicitly three-item second round and the analysis module's own counting logic, while an earlier requirements document recorded four and an older interface mentioned aggregation propensity as a veto item. The interface presents the item count the service declares, and changing the number is a change to one definition in the service layer.

**Whether the two immunogenicity pathways are merged, and by what rule.** MHC class I and class II are independent pathways, and the current arrangement emits them side by side rather than merging them into a single immunogenicity value. Coverage is 117 and 186 respectively, with 198 constructs empty on both. Whether to merge, and on what basis, requires a reasoned decision that the interface layer is not the right place to make.

**Material form requires per-item confirmation.** The classification of each scaffold's material form was extracted from prose rather than being a dataset field, and although all eight clusters have an entry, two entries leave room and need review, as described in section 4.7.

**One further sourcing item needs confirming with the data maintainers.** The library records several model keys for the anti-inflammatory and anti-melanogenic directions that have no corresponding row in the current database, which shows a divergence between the direction proposals and the models finally stored. This is why those two directions' constructs remain pending signature: the data exists, but the pipeline has not signed off on it.

### 11.3 Data invariants

Each of the following corresponds to an error that has occurred or is easy to make, and each should be treated as an assertion when the related code is changed.

1. All nine scores are nullable, and a null is not a zero. Every null is accompanied by an assessment flag, and the interface renders it as not assessed rather than as 0.00, issuing no failing badge. Across the library, MHC class I immunogenicity is empty on 379 rows and holds a value on 117.
2. A very small non-zero value must not be rendered as 0.00. Several hundred such values exist, concentrated in cell penetration and solubility, and formatting falls back to significant figures.
3. A `ranking_only` score must not be presented as a probability. Every construct in the anti-inflammatory and anti-melanogenic directions has this semantics, and the marker is present on list rows as well as detail views.
4. The MHC class II direction is the reverse of every other gate. Passing requires the percentile rank to be above the sub-threshold. Any presentation code that writes "above the limit means exceeding" states the opposite conclusion on this gate, which is currently a soft signal and does not veto.
5. The immunogenicity threshold varies by route and must not be hard-coded. Read the response's threshold field or the route configuration rather than using the literal 0.50.
6. All 496 constructs' scaffold bindings are currently placeholders, but the service must not assume this will always hold. Whether a binding can be used for assembly is decided by whether the linked row has a real amino-acid sequence: with one, the binding is verified and the complete fusion sequence is emitted; with only a marker string or an empty sequence, it is placeholder and the fusion sequence is refused. The test lives in one place, shared between assembly and binding reporting. A scaffold identifier supplied in the request marks the binding inferred and takes precedence over the stored binding. The construct's scaffold foreign key points at one table, while the curated library is a different table with a different numbering system.
7. The construct score field is heterogeneous by direction: 26 keys across the table, no row holding all of them, 6 shared and the rest direction-specific. Treating a missing key as incomplete data is wrong.
8. The construct delivery-score field uses an old four-key convention with no invertible mapping to the five application routes. It is not emitted, and is returned only as an archived value in the peptide detail.
9. The construct full-sequence field is a label string, not an amino-acid sequence, and must not be emitted directly.
10. The construct linker foreign key points at the sample table's first row on every construct, so no linker selection difference is visible from the construct table; the formal entries are in the curated library and the response distinguishes them by a source-table field. Both the builder and the construct detail can accept an explicit linker, in which case the fusion sequence uses it and the construct's stored value is unchanged. Resolving the construct's own linker must query the sample table only, never the curated library first: the foreign key points at the sample table, and if the curated library happened to contain an entry numbered with a matching integer, querying it first would shadow the row the construct actually points at. The two tables' column names differ in two places, and the normalisation is concentrated in one place shared by both read paths.
11. Aggregation propensity is not in the peptide score table. Querying it by tool name returns zero rows; it exists only in the construct score field, computed by the pipeline during assembly.
12. Thermal stability and solubility are in the peptide score table only. Reading the construct table alone would suggest neither metric was ever run, whereas each has a row for every one of the 20,248,885 peptides and a value for all 496 constructs.
13. The control channel is a control group. Its rows are real and carry complete scores; their purpose is to supply a baseline rather than to serve as candidates.
14. A direction's status is derived from the data and must not be hard-coded in the frontend. `ready` requires constructs in a passed state in that direction, which is why the anti-inflammatory and anti-melanogenic directions are `wip` rather than `empty`.

### 11.4 Interface summary

All endpoints are prefixed with the API path. All are read-only GET operations except the conversational endpoint. Paginated endpoints uniformly return items, total, limit and offset.

**Reference data:** health and database connectivity; all reference data in one call; functional directions; application routes; tool metadata; pipeline rounds; per-tool coverage statistics.

**Constructs:** paginated list with filtering by direction, channel, status and route; single detail, with optional route, scaffold and linker parameters; the scaffolds available for a construct; the per-tool score rows for the construct's peptide; the six generated text blocks; and the conversational endpoint, which takes the construct identifier in the request body, the question in a message field, and an optional route along with a history field that is accepted but currently ignored.

**Build:** the single combinatorial endpoint, taking one or more directions, an optional route, optional scaffold and linker, and paging parameters, returning the ranked candidates with assembled sequences plus the matched-set counts.

**Scaffolds:** list, with optional route and category filters; detail, including sequence variants, experiments, regulatory registration and the unavailable-fields list; and the constructs using a given scaffold, which currently always returns an empty array because every binding is a placeholder.

**Linkers:** list, exposing both tables merged with a source-table marker per row; and detail, including unit composition and literature provenance.

Construct identifiers are exposed in the form `con_0001`; the service layer extracts the numeric part by pattern and maps it back to the database primary key, returning 400 for a malformed value and 404 for one that is not found. An unknown route or direction identifier also returns 400 with the legal values listed in the detail.

Error semantics: the database being unreachable returns 503 with a specific error identifier and a troubleshooting note; a failed query returns 500.
