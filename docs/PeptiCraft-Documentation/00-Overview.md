# PeptiCraft Documentation Set Overview

This document is the entry point to the whole documentation set. It sets out what the project does, which materials this set is composed of, what question each of them answers, for whom each is written, and the true state of the project as of October 2026.

## What the project does

PeptiCraft is a web platform for recombinant fusion protein design. It moves the entire design chain — from a biologically active short peptide to a fusion protein sequence that can be sent into the laboratory — into a browser. To grasp the scale of this undertaking, it is first necessary to understand that a multifunctional fusion protein is assembled from three segments: the **functional peptide** (a peptide is a short chain of amino acids joined together; the length range of interest for this project is 1 to 30 residues, and a functional peptide is a short chain carrying biological activity such as antioxidant, antimicrobial, or anti-inflammatory activity); the **scaffold** (a scaffold is a natural structural protein such as recombinant collagen, silk fibroin, or spider silk protein, responsible for providing mechanical strength, film-forming or fiber-forming capability, and determining what dosage form can ultimately be made); and a short **linker** joining them (a linker is likewise built from amino acids, and its role is to let the functional regions at both ends fold correctly without interfering with each other).

The conventional approach tries the three separately: run predictions, search the literature, and send samples to wet-lab experiments, a round of which takes weeks to months, and every adjustment must be repeated from the start. The platform's approach gathers the three into a single reproducible computational pipeline, and makes one critical change of convention regarding safety — from "a score within the weighted total" to "a hard threshold with a veto". A peptide with a high antioxidant score but a clearly excessive hemolytic index could, under the weighted convention, pull the total up with its high scores and stay on the candidate list, with the real trouble surfacing only at the wet-lab stage; after the change to a hard threshold, any single out-of-limit item is eliminated immediately and takes no part in weighted compensation.

The platform serves teams that have no protein-engineering training but genuinely need to obtain concrete candidate molecules. The user does not need to know which protein to use, only to state clearly what form of product is intended; the platform works backward to which scaffold should be used and which linker should be paired with it, and hands over the candidates already computed together with item-by-item explanations of safety and expressibility. Technically it is a single-page web application, and the way data is obtained split into two forms in October: during development it reads a read-only backend service connected to a database; in formal deployment it reads static files exported once by that service, requiring no backend process.

## What each of the seven documents answers

The material is organized as "an overview plus four topical documents, with one development handoff technical reference and one release progress document attached". The four topical documents correspond to the four classes of fact the project needs to state clearly: what the product looks like, what data is at hand, what is happening biologically, and how far the code implementation has advanced. The first four are mainly continuous narrative, written for the project lead and team leads, and reading them in full yields an understanding of the whole project without consulting the code; the fifth is a different kind of material, aimed at engineering staff or AI Agents who take over development later, and consists mainly of precise field names, API paths, and value conventions; the seventh is aimed at those who need to judge "whether release is possible now, and what is still missing".

*01 Product Form and User Experience* answers what the platform looks like in the eyes of the user. It describes the responsibility of each of the five pages, the walkthrough path of one complete use, and the reasoning behind several design decisions that affect the experience — why the user is not allowed to choose the scaffold, why the delivery method is derived from the scenario rather than checked by the user, and why "not evaluated" cannot be displayed as a zero score.

*02 Data Assets and Data Shape* answers what data is at hand and what that data looks like. It covers three layers of data: a peptide library on the scale of twenty million entries together with its per-tool prediction scores, 496 constructs already computed, and two reference libraries for scaffolds and linkers; it also sets out the semantic conventions of the data themselves and the known gaps.

*03 Biological Logic and Screening Pipeline* answers how these data were computed and what the biological basis of each step is. It decomposes the four-round screening pipeline round by round, explaining what each prediction tool measures, where each threshold comes from, why the weighting scheme is determined by the data themselves, and how the five delivery routes change the immunogenicity threshold through barrier integrity.

*04 Technical Architecture and Development Progress* answers how the code is organized and how far it has reached. It describes the frontend and backend layering, the complete path by which data flows from the database to the browser, the API surface and error semantics, and takes stock of completed, in-progress, and not-yet-started work by layer, finally listing items awaiting confirmation and risks.

*05 Development Handoff Technical Reference* is where all the precise identifiers appearing in the first four documents are consolidated and pinned down: the endpoint list, enum values, the mapping between tool keys and display names, database semantic invariants, startup and debugging steps, and which file should be modified for a given class of requirement.

*06 Release Progress and Remaining Work* answers how far the project currently is from release. It explains the status of the October change of deployment from "a resident service plus a remote database" to "static files plus edge functions", the size estimate and the verification method, lists the three items that must be completed before release, and the new boundaries brought by the deployment form itself — data becomes a snapshot, re-running predictions is outside the system's capability, and the chat endpoint currently has no rate limiting.

The four topical documents do not retell one another, yet each stands on its own: reading any one of them alone yields an understanding of its subject without first reading the others. Terms appearing in the text are explained in place where they are first used, with no separate glossary; cross-document references serve only to explain the division of material and do not carry the chain of understanding of the main text.

## Current state snapshot

The state of the project in October 2026 is as follows. The figures on the data side come from measurements against the remote database on September 18; the figures on the service and deployment side come from measurements on October 10.

The data side has taken shape. The peptide library holds **20,248,885** peptide sequences of length 1 to 30 residues, from 10 data sources; of these, 12 prediction tools have achieved 100% coverage of the full library, and the two immunogenicity-related tools cover it only partially because they apply only to specific length ranges. The construct library holds **496** constructs distributed across four functional directions: 170 antioxidant, 65 antimicrobial, 154 anti-inflammatory, and 107 anti-melanogenic. The scaffold reference library covers **8 protein clusters and 16 patented sequence variants**, drawn from real patents of applicants such as Jinbo, Trautec, Giant Biogene, Yusong, Wuhan (Collagen (Wuhan) Biotechnology), Bolt Threads, and AMSilk. The linker reference library holds **15** entries with literature provenance.

The service side is connected end to end, and the deployment form was changed in October. The FastAPI backend provides **19 read-only endpoints**, covering five classes of resource: reference data, builds, constructs, scaffolds, and linkers; all five frontend pages have been converted to asynchronous data fetching, and no hard-coded data rendered by a page remains in the project. The real data path can be traversed completely in the local development environment: the build endpoint determines the candidate set by application route and functional direction, then assembles fusion sequences one by one using the scaffold and linker specified in the request, and the construct detail response simultaneously carries the nine scores, the composite score recomputed per route, the safety conclusion determined per route, the segmented sequence, and six passages of interpretation text generated by the server.

The previous deployment form required a Python service to run resident and connect to the database on that school workstation. That machine is not under the project's control and is already offline, so in October the project switched to **static deployment plus edge functions**: before deployment, data is exported once into static files and read directly by the frontend, and only chat is forwarded to a large model by an edge function on the deployment platform, with the key never entering the browser. The export calls the backend service's own endpoint functions rather than separately implementing queries and decisions, so the static files agree with the API responses. The status of this change, the size estimate, and the work remaining before release are recorded in *06 Release Progress and Remaining Work*.

The parts not yet complete are equally clear. **The export has already been run against the real database**: it was exported on 2026-10-15 against the local database, the output covers all 496 constructs, `source_backend` is recorded as `postgres`, and no sample banner appears in the interface; this export has been committed to the repository, so teammates need not repeat it after cloning. The scaffold binding of all 496 constructs is **entirely placeholder values**; the name in that scaffold row of the database is a marker string rather than an amino acid sequence, so the fusion sequence is currently not output in full, and the interface marks this truthfully rather than fabricating it; the two directions anti-inflammatory and anti-melanogenic have the status **pending sign-off** in the library, with the data present but not confirmed by the pipeline, and the interface retains the marker; the fifth to eighth rounds concerning three-dimensional structure are **outside the scope of this version**; of the two dimensions delivery method and material form, material form is a manual classification extracted from prose and still awaits team confirmation.

## Disposal of the old material

Before this documentation set was established, three earlier materials existed under `docs/`. They were written during the design reasoning stage and before backend work began; their conclusions have been absorbed by the implementation, while several of their figures and judgments have been disproved by later development, so all three are retired from active use as a whole. The valid content they carried has been merged into this documentation set in the manner described below and is no longer kept separately.

The former **backend service requirements and technical plan** was a proposal document from before the backend rework began, dealing with the API contract design reasoning and the database status check for "switching the frontend from static fake data to the real data path". The mapping relations it fixed are now established fact, described in *02 Data Assets and Data Shape* and *05 Development Handoff Technical Reference*; several files in the service directory it planned were never built (path definitions, the peptide repository, the health-check route, an independent analysis route, and so on), and following it to recognize directories would go to the wrong place, with the actual structure taking *05 Development Handoff Technical Reference* as authoritative; the three-layer verification approach it proposed still has value and has been merged into the self-check section of *05 Development Handoff Technical Reference*.

The former **scenario and delivery system** dealt with how the five application routes are derived from the application labels of the scaffold dataset. The three criteria it gave, together with the two conclusions that "the application technique, originally presented as an independent layer, should be downgraded to descriptive text", were merged into the interaction decisions section of *01 Product Form and User Experience*; the prose evidence about material form in the original material was merged into the gaps section of *02 Data Assets and Data Shape*; the remaining parts were design reasoning already covered by the implementation and are no longer kept separately.

The former **product narrative draft** was introductory text aimed at the general public; its product positioning, user profiles, and usage walkthrough have corresponding accurate versions in *01 Product Form and User Experience*. It additionally recorded one pipeline principle — the functional score is used only once — which was added into the weighting section of *03 Biological Logic and Screening Pipeline*; the weight table in the same draft, which listed the four old delivery methods, belongs to a convention superseded by the five application routes and was not adopted.

## Two reference boundaries that still merit attention

**The pipeline side still keeps its own documentation, which is not part of this documentation set.** Under `iGEM-platform-main/` there are proposals for each of the four directions together with tool status notes, an overview of results, and a platform setup plan; these are materials of the data and pipeline team, describing the behaviour of the prediction tools themselves and the measured results of screening, and they differ from this documentation set in granularity and purpose. Where this documentation set needs tool-level detail, their conclusions are authoritative, but their content is not copied, nor are they maintained as part of the platform documentation.

**Two statements in the old material cannot be verified and need confirmation before being reused.** First, the architectural scale of "sixteen core services plus three auxiliary services": in the pipeline-side client configuration only eleven prediction services invoked by port can be found, with two further classes implemented inside the database and inside the code, and the total does not match the statement above; this documentation set therefore describes only "several prediction services invoked in the form of local HTTP services" without giving a specific count. Second, the four functional directions were said to each converge to about two hundred and fifty constructs, but measurement gives four mutually unequal numbers, 170, 65, 154, and 107, the difference coming from different model score distributions across the four directions rather than from unfinished runs. Both statements are written in the old material, and in subsequent external statements the measured results of this documentation set should be authoritative.
