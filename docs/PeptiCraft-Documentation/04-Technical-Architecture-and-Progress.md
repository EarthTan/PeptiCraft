# 04 Technical Architecture and Development Progress

## 1. Architecture Overview

The entire system consists of three parts plus one database, and data flows in one direction only. It should be stated first that this overview describes the **development form**: the formal deployment no longer contains a resident service process or runtime database access; the relationship between the two, and the details of the deployment form itself, are recorded in *06 Release Progress and Remaining Work*, and the rest of this section's description of the service and the database holds equally for the development and export stages.

The user side is a single-page web application built by Vite and running in the browser at runtime. Whether in development or in formal operation, it requests only an API prefix beginning with `/api`, over HTTP. In the development environment this prefix is forwarded by the build tool's proxy to the local backend port, and in the formal environment the deployment platform performs the same forwarding — the purpose of this step is to ensure that only relative paths appear in the frontend code, so that changes to cross-origin configuration and backend addresses require no frontend edits.

In the middle is a FastAPI backend service, the only part of the system that touches the database. It does not write data, only reads; it does not compute predictions, only assembles and adjudicates. It carries three kinds of work: outputting the real contents of the remote database in the shape the frontend requires; taking over the responsibilities that were originally left as placeholders by the pipeline and explicitly reserved in comments for the compute service, namely the binding of real scaffolds, the reconstruction of fusion sequences, and the recomputation of the composite score and safety determination by application route; and providing generation capability for the interpretive passages and the conversation on the interface.

Finally is the database, a PostgreSQL 16.15 instance on an Ubuntu workstation, accessed over a network address. The database is placed on the workstation rather than on the same machine as the service process for two reasons: the two largest tables in the library total about 165 GB, which is not suitable for migrating together with the service; and most of the predictive models that generated this data need GPUs and already run on that workstation, so keeping the database and the inference together avoids repeatedly moving data. The cost is that the availability of the whole service depends on network connectivity to that workstation, a point listed as a risk in Section 8 below.

The technology selection follows this structure. The frontend is Vite 8 with React 19, TypeScript 6 and Tailwind 4, with react-router-dom 7 for routing and Lucide for icons, and the basic interactive controls are hand-written on top of Radix's unstyled primitives rather than imported from a finished component library; styling uses Tailwind's CSS-first configuration, with theme variables written directly in the stylesheet. The backend is FastAPI with Pydantic for response models and psycopg 3 as the synchronous database driver. The immediate reason for choosing FastAPI is that response models can be declared with Pydantic, so that the field structure of the API can be exported automatically as a schema and checked field by field against the frontend types, which is of high value in a refactor in which the frontend contract drives the backend; the reason for choosing a synchronous driver rather than an asynchronous one is that the few session settings that must take effect on every connection are expressed more directly with synchronous connection-pool semantics, and because the API queries in this project are all retrievals by primary key or small sets, so concurrency pressure is not a bottleneck.

## 2. Front-End Architecture

The frontend is a single-page application with five pages corresponding to five routes: the landing page, the peptide library browser, the builder, the results page and the scaffold detail page. The code is divided into four blocks by responsibility, and this division is itself a constraint.

**Data-fetching layer** is concentrated in one directory and composed of three files: one responsible for issuing requests and normalizing errors, one binding each backend endpoint to a named function, and one holding the TypeScript mirror of the backend response models. The field names in the mirror types **retain the backend's snake_case naming verbatim**, with no camelCase conversion — the purpose being that the API schema and the frontend types can be compared mechanically, so that any renaming is exposed immediately by the comparison, without a layer of naming-conversion mental mapping.

**State and side effects** are handled uniformly through two custom hooks, serving the two scenarios of "loading a piece of data" and "performing an action" respectively. The loading hook contains a ticket mechanism internally: the ticket is incremented each time a request is issued, and when a response arrives it is discarded if its ticket is no longer the latest — this mechanism solves the problem that, when filter conditions are switched quickly, a slow request issued earlier returns later and overwrites the result of a fast request issued after it. Errors are normalized into a few distinguishable types, on the basis of which the interface gives different failure causes rather than a uniform error message.

**Shared presentation components** holds the three panels used by both the results page and the peptide library page: the safety-gate list, the tool-score grid and the interpretive text block. The reason they were extracted and shared is concrete — the root cause of threshold drift was that these two places once each had their own implementation.

**Presentation-layer mapping** is responsible only for translating the identifiers supplied by the backend into interface elements: icon names to icon components, display labels for groups, human-readable Chinese labels for the weight tiers, the rules for determination and formatting, and local computation of sequence properties. One constraint runs throughout: **the frontend performs no threshold comparisons and no weighting arithmetic**. The composite score and the safety determination are computed by the backend and returned with the response, and the frontend only presents them. This constraint has three direct benefits: thresholds exist in only one place, so the interface and the interpretive text can no longer give opposite conclusions; the frontend need not move the nine scores and the weight tiers into the browser for arithmetic; and future changes to conventions require changes only in the backend, with no redeployment of the frontend.

As for state management, the project imports no state library at all. Each of the five pages holds its own data, the pages share no mutable state, and route parameters carry the responsibility of passing values between pages. This choice is commensurate with the size of the application, but there is one consequence to note: the scaffold preview on the results page is implemented by rewriting query parameters, so the browser's forward and back buttons participate in the state at this one point.

## 3. Back-End Architecture

The backend is divided into four layers by responsibility, and the constraints between layers are hard.

**The routing layer** only validates parameters, calls the service layer and serializes responses; no SQL and no computation appear in it. **The service layer** carries all thresholds, weights and business judgements, and does not write SQL directly. **The repository layer** only performs SQL queries and row-to-dictionary conversion, and contains no thresholds or conventions. **The model layer** defines the response contract, with field names matching the frontend types.

The sole purpose of these constraints is **to make every threshold exist in only one place**. This purpose is not abstract tidiness — a review on 17 September 2026 recorded three classes of defect caused by copies drifting apart: the same safety threshold table had been written once in each of two pages, with comments still claiming that the two shared a definition; the immunogenicity threshold was hard-coded globally to 0.50 while the route definitions specified three tiers of 0.35, 0.50 and 0.60, with the result that a construct lying exactly on the tightened threshold was shown as passing all gates; and the generated interpretive text cited an acceptance floor of 0.70 that did not exist at all in the tool metadata, leaving readers unable to find the source of the number. After thresholds were centralized in the service layer, these three classes of defect became structurally impossible.

**Reference data is the single source of truth for the entire backend.** The definitions of the five application routes (contact interface, barrier level, immune-exposure description, the three weight tiers, immunogenicity threshold, additional checks, application method), the tool metadata of the nine metrics (tool name, what is measured, direction, grouping, threshold and threshold provenance, coverage note, whether a veto gate), the pipeline description of four retained and four excluded rounds, and the presentation information and status-derivation rules of the four functional directions are all written in one module. Everything appearing in this module is read by the frontend as data, and the frontend keeps no copy of any of it.

The database access layer is a connection pool, with two settings applied uniformly to each connection at creation: the connection is marked read-only, and a query timeout is set. There is another group of tuning settings for large tables **applied only when needed**: sequential and bitmap scans are disabled, forcing the use of an index. This group benefits that score table of 378 million rows but harms the construct table of only 496 rows — for a small table of a few hundred rows, an unfiltered list query ought to use a sequential scan, and forcing an index only makes it slower. The caller therefore declares explicitly when accessing large tables, and other queries leave the query planner alone.

Error handling distinguishes two classes of failure and maps them to different status codes. **Database unreachable** (network down, authentication failure, or connection to the wrong instance) returns 503 rather than 500, on the grounds that the database is on another machine and unreachability is a transient fault for which client retry is reasonable; the response body carries an error identifier and a troubleshooting hint. **Query failure** (the statement itself is faulty, or times out) returns 500. This distinction lets the frontend give an accurate failure cause rather than calling every failure a "server error".

## 4. API Surface

The backend provides **19 read-only endpoints**, grouped by resource into five groups, plus one write endpoint for conversation. This set of endpoints is the API surface of the development form and also the basis on which the export scripts produce their output — under static deployment, every file the frontend reads is content that these endpoints once returned.

The formal deployment has an additional static data source that coexists with the above endpoints and returns the same structures. The two are dispatched by the same entry point in the frontend: the static deployment reads files, while development and builds configured with a remote API address read the service. The existence of this dispatch layer means that the API surface need not change for the deployment form, and the code of the five pages is one and the same under both forms.

The reference-data group has six: the health check and database connectivity, the one-time retrieval of all reference data, the retrieval of the functional directions separately, the retrieval of application routes, the retrieval of tool metadata, the retrieval of pipeline rounds, and the actual coverage statistics of each predictive tool. Of these, the endpoint that retrieves all reference data at once carries the heaviest load and is also the most convenient — the directions, routes, tools, evidence grades, material forms and scaffold categories needed by a page are all obtained in a single call, avoiding a waterfall of requests when the page opens.

The construct group has six: the paginated list (supporting filtering by direction, route, channel and status), the single-construct detail, the list of scaffolds selectable for that construct under that route, the per-tool score detail of the peptide used by that construct, the interpretive text blocks for that construct, and the conversation. The list endpoint returns a uniform four-part structure of "an array of items plus total count, page size and offset", so that the frontend can display the total directly without issuing a separate count request.

The build group has one endpoint, the only endpoint on the entire API surface that performs combination rather than reporting stored state: it accepts an application route, a number of functional directions, one scaffold and one linker, and returns the candidates under that screening sorted by composite score, assembling the fusion sequence for each one. The two assembly targets take effect independently and either may be omitted, in which case that part falls back to the one recorded in the construct archive; neither enters into the adjudication of candidates, and they affect only the assembled sequence and the fusion length reported in the response. Its definition of the candidate set differs from that of the construct list — it takes the top channel, because the bottom channel is the negative-control arm, and including control markers among the candidates would make both hard to read. Ranking covers all candidates before slicing by offset and count: a record's composite score depends only on the weight pool of its direction, and the pool is read independently of the request and cached per direction, so ranking the full set first is the correct order and is what gives the offset meaning. The computed safety-verdict counts likewise cover the entire matching set rather than the returned page.

The scaffold group has three and the linker group two: list and detail, with the scaffold additionally having "which constructs use this scaffold". The scaffold list and detail are two different shapes — the list omits sequences and patent variants, the detail includes them; the distinction is deliberate, so that the list can return all eight entries at once without carrying long sequences.

## 5. Several Design Decisions of the Data Contract

**Null values must carry a marker.** All nine scores are nullable in the response models, and every null is accompanied by a boolean "assessed" marker. This way the caller need not distinguish "field missing" from "value is zero", which both appear as empty in JSON, and there is no possibility of misreading an unassessed metric as a zero score.

**The composite score follows the route and is reproducible.** The response for a single construct carries a map indexed by route, with keys corresponding one-to-one to the identifiers of the five routes, each entry containing the three modulated components recomputed under that route, the composite score, and all intermediate quantities used for reproduction — the normalized value of each component, the weight it received and the multiplier it received. One response is thus sufficient for the composite score to be recomputed by hand, without re-querying the database or reading code.

**The safety conclusion is a structure, not a sentence.** The safety-determination response is an object containing the immunogenicity threshold for the route, the overall verdict, an array of per-gate details, a list of the keys of unassessed gates, and a list of the keys of vetoed gates. Each gate's detail carries the metric name, tool name, measured value, threshold, threshold provenance, pass or fail, whether it sits on the line, whether it is a veto gate, and which side counts as exceeding the limit. This last field is necessary because MHC-II is the only gate where "lower is worse", and any presentation logic that writes "above the limit means exceeding it" without checking this field will get the conclusion backwards for it.

**The readability of scores follows the data.** Every score carries a semantic marker in the response, whose value distinguishes "readable as a probability" from "usable for ranking only". The marker is not only in the detail but also on list rows, because three of the four directions derive their ranking from a model and one of them is explicitly not a probability. If list rows did not carry the marker, ranking position would be presented as confidence.

**Generated text carries provenance.** The interpretive text is generated in a fixed structure of six blocks: safety interpretation, functional-peptide source and composition, linker and assembly, expression and processing, within-direction cross-comparison, and risk list. Each block carries, in addition to its body text, a list of sources naming the response field paths cited by that block; the whole response also carries a generator marker indicating whether the current output is template-generated or model-generated. The purpose of this marker is to let the frontend label the text's origin faithfully, rather than presenting template copy as model output. The generation capability is abstracted as a protocol rather than a function, so that when a large model is integrated in future, a new implementation is added and the registration switched, with no change to the routing layer or the response models.

**Conversation and interpretation share the same generator.** The conversation endpoint receives a question and the context of the construct, and returns an answer together with a set of suggested follow-up questions. The current implementation gives deterministic answers to known question types and returns an extensible prompt for unknown ones; the configuration reserves places for the generator and the model name, and at service start-up, if the generator configuration points to a model implementation that is not yet registered, a warning is printed and the template implementation continues to be used.

## 6. Local Development and Running

Development start-up consists of two commands: the backend starts a local HTTP service in module form from the service directory, listening on port 8000 by default; the frontend starts the development server from the application directory, listening on port 5173 by default and proxying `/api` to 8000. The frontend project has three further scripts: type-checking plus bundling, previewing the build output, and static checking. The backend service does not enable code hot reload at start-up, so the process must be restarted manually after changes to backend code; if restarting reports that the port is in use, the process occupying the port must first be found and terminated before starting again.

**There is a trap in the database connection that must be written into the configuration.** On the development machine, another PostgreSQL instance listens on port 5432 at the local address, but that is a different system that does not contain the roles used by this project, and a connection to it fails immediately with role-does-not-exist. Several default connection strings in the project are written with the local address, since that default was intended for the workstation itself; running on the development machine without an override **silently lands on the wrong instance**, and the error message looks like a configuration problem rather than a connection to the wrong machine. The service's connection configuration must therefore point explicitly at the remote address and include a switch that forbids fallback to the local address.

Changes to the database structure are delivered with the service as standalone SQL scripts, numbered along the pipeline's sequence to avoid confusion, and the creation scripts for the two new tables can be executed repeatedly. The data-import script reads local spreadsheet files and uses "update on conflict" writes, so it too can be executed repeatedly. Together the two make the entire data-preparation process replayable: even on a completely new machine, the reference layer can be rebuilt from the spreadsheet files in the repository.

## 7. Development Progress

Progress is inventoried across five layers, whose completeness differs widely and which are meaningful only when considered separately.

**The data layer is the most complete of the layers.** The peptide library of twenty million entries and the per-tool scores of twelve tools are fully in place, with coverage of 100%; the nine scores, safety markers and parameters of the 496 constructs are complete; the scaffold reference library was imported from a compiled table of 30 columns, with all 8 protein clusters and 16 patent sequence variants carrying real amino-acid sequences; the linker reference library has 15 entries with literature sources. The data layer's gaps are concentrated in three places: the construct-to-scaffold bindings are all placeholders; the peptide library's secondary-attribute table is empty; and the material-form column is a derived value rather than an original field.

**The pipeline layer has run all four directions.** Constructs in the antioxidant and antimicrobial directions have the status passed, while all constructs in the anti-inflammatory and anti-melanogenic directions are pending sign-off — the data is in the library, but the pipeline has not signed off on this batch, and the interface retains this marker. The fifth to eighth rounds relating to three-dimensional structure are explicitly excluded from this version. It should be noted that the pipeline itself and the predictive-model services that generate this data are not in this repository; what this repository holds is the pipeline's table-creation scripts, run scripts and result files. The models themselves are in another code repository and are invoked over a local HTTP service, each service occupying a fixed port.

**The backend service layer is fully usable.** All 19 read-only endpoints are implemented and running, with the nine scores, the composite score recomputed by route, the structured safety determination, the segmented sequence, the two resources of scaffold and linker, the six generated interpretive blocks and the conversation all connected. Measured in the local environment, an end-to-end run succeeds: the construct-detail response carries at once the nine scores, the recomputed results for each of the five routes, the safety conclusion determined under the selected route, the three colour-marked sequence segments, and the list of scaffolds selectable for that construct under the current route. A 503 with a troubleshooting hint is returned when the database is unreachable, and this path has also been verified — a query timeout correctly triggers this branch.

**The frontend layer has completed the switch from static data to real data.** The content of all five pages comes from the database, and the entire set of static data modules and their type definitions that existed in the project has been deleted, so that no hard-coded data is rendered by any page. The builder completes its selections in five steps, and the final step issues one real computation request to the build endpoint, with ranking, statistics and assembly all performed on the server. The peptide library browser already has search and sort controls, covering the four filters of direction, channel, status and route and three sorts, and pagination is true pagination rather than an increase in the per-request count. Three things remain in temporary form: neither scaffold selection nor linker selection narrows the candidate set, because the former is a placeholder value and the latter samples the first row of the sample table in every construct; the fusion sequence omits the scaffold segment when no scaffold is specified, outputting only the two real segments of linker and functional peptide; and the linker library has not yet been narrowed by application route, with all five routes receiving the same list. The frontend has an additional static data source as of October, coexisting with the backend chain above, and the order of determination and the division of labour are recorded in *06 Release Progress and Remaining Work*.

**The deployment layer underwent a change of form in this round, but the formal release has not yet been executed.** The previous form required the Python service to run resident and connect to the remote database, and that dependency is no longer available, so the form has been changed to static files plus edge functions: data is exported once before deployment, the frontend reads files directly, and chat is forwarded to a large model by an edge function. The export scripts, data layer, edge functions, deployment configuration and deployment documentation are all in place and verified; what has not yet been done is producing the export files from the real database, configuring the model key, and actually uploading. Completion status and remaining work are recorded in *06 Release Progress and Remaining Work*.

## 8. Open Items and Risks

**The scaffold binding is an inferred value rather than pipeline output, and this is the most substantive current risk.** The scaffold foreign keys of all 496 constructs point to a placeholder record, and real bindings do not exist. The product's chosen handling is to mark the binding's provenance faithfully: by default no scaffold is fabricated and no fusion sequence is output, with only the two segments that genuinely exist output; when the caller explicitly specifies a real scaffold, assembly follows that scaffold and the binding provenance is marked "inferred on request" with an accompanying note. The interface therefore needs to avoid presenting an inferred scaffold as a verified choice, and this marker exists both on list rows and in the detail view.

**How to present the pending-sign-off directions requires a team decision.** The anti-inflammatory and anti-melanogenic directions have data in the library but no settled status, and the design document for the anti-inflammatory direction itself states that it cannot be presented as "ready". The product outputs the status as it is, but whether the interface should show these as candidates with a prominent marker or hide them by default is a product decision rather than an implementation decision. One related question: the ranking fields for these two directions have values but no settled status, so presenting them by rank may mislead.

**The weighting convention of the composite score needs to be aligned with the pipeline maintainers.** The server brought solubility and thermal stability into the route-modulated components, on the grounds that the product defines these three weight tiers for each route and these two metrics had never been used, leaving two-thirds of the three-tier weighting idle. This convention is not fully consistent with the existing implementation in the pipeline (the pipeline modulates only one component, because the multiplier keys do not match), so until the two conventions are unified, the composite score output by the server will not agree with the result recomputed by the pipeline. Moreover, this convention itself has not been confirmed with the pipeline owner.

**Whether there are three veto gates or four needs confirmation.** The server implements three (toxicity, hemolysis, immunogenicity), on the basis of the three checks explicitly defined in the second round of the pipeline and the interpretation module's own counting logic; an early requirements document, however, described a four-item summary, and the old interface also mentioned aggregation propensity as a veto item. The current interface presents the markers declared by the server faithfully, and changing the number of gates requires only one definition in the service layer.

**The two immunogenicity pathways have not been merged.** MHC-I and MHC-II are two independent pathways, and the current approach outputs them side by side rather than merging them into a single immunogenicity value; moreover MHC-I covers only 117 constructs and MHC-II 186, with 198 having neither. Whether to merge, and by what rule, requires an evidence-based judgement and is not suitable for the API layer to decide on its own.

**Remote connection is a single point of dependency, and this has been lifted by the change of deployment form in October.** Previously the backend depended entirely on network connectivity to that workstation, whose address is reached over a mesh tunnel, and if the tunnel broke at either end, between the development machine and the workstation, the service was unavailable; the API layer distinguished "database unreachable" from "query failure" so that the interface could give an accurate failure cause, but that only made the fault readable and did not change the dependency itself. The formal deployment now contains no runtime database access, so the risk no longer holds under the deployment form; the development environment is still affected by it, and the fixture fallback path and the data-source banner are therefore retained. A new boundary that replaces it is that **data becomes a snapshot**: the numbers on the site come from the database at the moment of export and do not update themselves, so after new constructs are added the data must be exported and redeployed.

**Two sources of convention need to be confirmed with the data side.** The material-form column is a manual classification extracted from prose; all eight clusters are filled in, but two still leave room for doubt, and the team needs to confirm them one by one. In addition, the MHC-II strong-binder boundary takes the tool's customary usage (the top 2% of the ranking), whereas the pipeline originally carried it only as a measured value with no threshold set; this threshold was introduced by the server and belongs to a platform constant rather than to the tool or the route.
