# 01 产品形态与用户体验

## 一、产品要为谁解决什么

PeptiCraft 处理的是一个具体的断层。想要做出「有生物功能的蛋白材料」的人，卡住的地方从来不是缺一个灵感，而是三个各自独立的障碍。

第一个障碍是**工具碎片化**。设计一条功能肽要同时面对一串互相独立的预测工具：抗氧化活性看 AnOxPePred，毒性看 ToxinPred3，溶血（红细胞被破坏的程度）看 HemoPI2，免疫原性（预测这段序列会不会被免疫系统识别成外来物、从而引发抗体或 T 细胞反应）看 MHCflurry，热稳定性看 TemStaPro，可溶性表达看 SoDoPE，细胞穿透能力（指肽能否自行穿过细胞膜，决定了外用涂抹时能不能真的进入皮肤）看 pLM4CPPs。这些工具的输入格式、输出量纲、判定阈值各不相同，要自己写脚本把它们串起来，还要处理重复序列导致的失败样本。对没有计算背景的团队，这本身就是一道过不去的门槛。

第二个障碍是**安全性被错误地当成了分数**。常规做法把毒性、溶血、免疫原性折进一个加权总分里排序，于是抗氧化分极高的肽即便溶血指标明显超标，也能靠高分把总分拉起来、继续留在候选列表里。真正的问题要等到湿实验才暴露，而一轮湿实验的代价是几周时间和一笔预算。第三个障碍是**结果不可读**。预测工具交出来的是一堆 0 到 1 之间的小数，没有参照系。拿到 0.64 这个数，无法判断它意味着可以推进还是接近危险，更不知道这个分数背后对应哪项实验。

平台对这三个障碍给出的回答分别是**集成、否决、解释**。集成是把十几个工具收进同一条管线，用户不接触任何一个；否决是把安全从加权项改为硬门槛，任何一项越限立即淘汰；解释是让每个数字都带着阈值、方向和判定一起出现，并附上一段可以读出结论的说明。

用户画像由此分成三类，共同点是终端产品形态清楚、蛋白质工程能力缺失。**学生与竞赛团队**有明确的项目主题和交付节点，需要用有限时间得到一个真实可讨论的候选分子，且没有跑动这些模型的算力。**早期研究者**往往已经确定应用方向，需要在正式启动实验之前先拿到一组有理论依据的候选，用来说服自己这条路值得走，他们关心候选的来源是否可追溯、参数是否透明。**独立创新者与小品牌研发**手里有产品形态——面膜、精华、护发膜、可注射填充剂——需要把「加一点功能成分」这件事做得有据可依，预算不允许他们为一次尝试付出整套计算与验证成本。

## 二、产品形态：一个单页应用的五条路径

产品是一个单页 Web 应用，界面全英文，由五条路径组成，其中三条是主要工作面。

**落地页**承担说明平台是什么的职责。它自上而下依次给出主视觉、四个关键数字、三个功能模块卡片、五条应用路径卡片、三条核心原则、筛选管线的轮次说明，以及四个功能方向的状态卡片。其中四个关键数字全部从接口派生而非写死：搜索空间取各方向工具覆盖肽数的最大值，构造总数取各方向构造数之和，骨架数与方向数分别取骨架列表与方向列表的长度。页面正文里仍有一处硬编码文案写着「大约两千万条肽」，这个数量级与实测的 20,248,885 条一致，但它是文案而不是取数。

**肽库浏览器**是查看已完成工作的入口。它分三个页签：功能肽与构建体、骨架蛋白、连接片段，页签上的计数来自接口返回的总数。构建体页签提供两类筛选——按功能方向的标签组、以及「在哪种路径下筛过」的路径按钮——同时展示每一条的排名、方向、状态、肽序列与长度、骨架名与其绑定来源标记、连接片段名、安全裁决色点、综合分，以及该方向的功能分；功能分旁会标注它是否只能用于排序。展开某一条时页面才去取详情，并用同一套安全门面板与工具分数网格渲染，这套面板与结果页共用同一个组件，因此两处的阈值与判定不会漂移。

**构建器**是产品的核心，按五步引导用户走完选择。第一步选应用路径，界面同时列出该路径收哪些骨架、三个权重档的取值、免疫原性门槛，以及该路径额外的非否决检查项；选定路径后会自动选中该路径下第一条骨架。第二步按功能方向多选，状态为空的方向不可选，界面对方向之间相互独立这件事另作说明。第三步确认骨架，候选来自所选路径，可按材料形态进一步过滤，界面分「匹配」与「全部」两个页签；这一步有一条明确提示，说明当前所有构造的骨架绑定都是占位值，选骨架不会缩小候选集——同一个骨架由哪些肽来配并不因此改变——但它决定每条候选被装配成的序列。第四步确认连接片段，列出参考库里的全部条目，每条带名称、残基长度、刚性档位、序列与文献出处；这一步不按路径收窄，因为连接片段库还没有与应用路径建立对应关系。第五步给出结果，按综合分降序列出候选，每条候选都带着用所选骨架与连接片段装配出的融合序列与融合长度，并统计各类安全裁决的数量；统计覆盖该筛选下的全部候选，而不只是页面显示的那一部分。从结果里的任意一条候选都可以跳进结果页，跳转带上它当时用的那对骨架与连接片段，到了那个页面还能换成别的重新比对。五步走完到看到候选，用户做的是五次点击。

**结果页**是读取单条候选的地方，围绕四个页签组织。构建体页签是主视图：顶部是综合分、排名与聚集倾向三块指标，往下是安全门面板，再往下是分段着色的序列——骨架为蓝色、连接片段为绿色、功能肽为橙色，功能肽段加粗，序列未知的那一段以灰色显示标注而不是画出残基——然后是本方向内的横向对比表与六段解读文本。功能肽页签展示肽的来源、长度、逐工具的九项分数，以及一段由本地计算的序列属性（分子量、净电荷、半胱氨酸数、芳香族与疏水性残基比例）。骨架页签展示当前绑定与备选骨架，点击备选可以即时改变查询参数重新看这条候选；没有序列的骨架不可点。连接片段页签展示该片段的单元构成与文献出处。页面右侧另有一个固定的对话侧栏，底部另有一条输入条，两者共用同一个对话接口，对任一指标提问都能得到基于该构造真实分数的回答。

**骨架详情页**沿五条路径展开单个骨架的全貌：基本信息、来源与专利、专利序列变体、被哪些应用路径收用、实验证据、监管注册情况，以及库中的其他骨架。页面上有一处显式的「以下字段在本数据集里不存在」提示区，把数据集确实没有的字段列为空而不渲染成空白卡片——这样读者能区分「没有这个数据」和「这块出了故障」。

## 三、一次完整使用的走查

设想一个做医用敷料的小团队，目标是在创面敷料里加入抗氧化功能以减轻氧化应激，他们不知道抗氧化能力该从哪条肽来，也不知道哪种蛋白适合做成纤维状敷料。

进入构建器的第一个动作是选应用路径「创面敷料」。选完之后有两件事由平台自动完成：给药方式被绑定到该路径的接触界面，用户不参与；可用的骨架被收窄到该路径收用的四条——巨子 FHLC、创健 COL17、羽森 SF-4/SF-10、武汉 TRHCIII-1。同时界面告诉用户，这条路径的免疫原性门槛被收紧到 0.35，比面膜贴片与涂敷成膜的 0.50 更严，理由是创面屏障已经破损、构造物直接接触组织液。

第二步勾选抗氧化方向。第三步在四条骨架里确认一条，或者留着全部候选进入下一步。第四步挑一条连接片段，界面在这里解释这个选择的含义：柔性单元让功能肽在骨架表面自由摆动，刚性单元把它撑离表面，两种都正当，用哪一种取决于功能肽是否需要不受遮挡地够到目标。与骨架一样，它不改变候选名单与任何一项分数，改变的是下一步拼出来的序列。第五步点构建，页面返回该筛选下按综合分排序的候选列表，每条候选都带一段骨架、连接片段、功能肽三段拼好的融合序列，并给出这些候选里有多少条安全裁决完全通过、多少条压线、多少条被否决。这些计数按该筛选下的全部候选统计，因此页面截断到前若干条时，这几个数字仍然描述整个候选集合。

选中一条候选进入结果页之后，用户的阅读顺序是：先看顶部安全裁决是否全部通过；再看综合分与九项分数各自的阈值判定；然后把序列往下拉，看清骨架、连接片段、功能肽三段是怎么拼起来的；最后读解读文本，重点看表达与处理建议和风险提示。如果对某个指标有疑问，直接在右侧对话栏追问，可以问某个分数为什么是这个值、换一条应用路径这条候选还成不成立、或者让它在选定路径下对比几条候选的取舍。最终要带走的是三样东西：完整构建体序列、对应的表达方案，以及一份需要补做的验证清单。

## 四、几条影响体验的设计决定

**不让用户回答自己不知道的问题。** 非专业用户根本回答不了「该用哪种骨架蛋白」，专业用户也不愿意每一步都被问一遍。平台因此把骨架选择从一个需要用户决策的问题改成由场景推导的结论：用户选产品形态，平台反推骨架。同样一条原则用在不同对象上，结论并不相同。骨架是八个有名有姓的蛋白，判断它需要对每个蛋白的力学性质与证据等级有了解，因此它只能由场景反推。连接片段不是这个形状：库里条目之间真正的差别是刚性这一档，柔性单元让功能肽在骨架表面自由摆动，刚性单元把它撑离表面，这个取舍不需要蛋白质工程训练就能理解，所以单条连接片段被开放成一个可以改的选项。它与骨架有两点一致——都进装配、都不改候选名单与分数；另有一点不同——它不由场景推导，界面把整个库列出来，默认停在第一条，用户不动它就得到一个可用的结果。留在后台的是多站点上的组合枚举，也就是在一到五个连接位点上穷举柔性单元与刚性单元的组合再逐条过滤，这是一件纯粹的搜索工作，用户既无从判断也无需判断。

**一级分类直接沿用数据集里已有的标签，不另造一套。** 五条应用路径对应骨架数据集里的五个应用标签列，这不是省事，而是因为这三个条件同时成立：每个可选节点至少能筛出一个骨架，否则用户会点到一个空集；每个骨架至少能被一个节点筛到，否则它在库里根本不可达；任意两个节点不能筛出完全相同的骨架组，否则其中一个就是冗余入口，用户在两个名字之间做了一次没有信息量的选择。实测五条路径分别筛出 2、4、2、4、2 个蛋白簇，八个簇全部可达，没有任何两条路径指向同一组骨架。这三个条件构成了评价入口结构是否成立的标准，也解释了为什么早期那套自造的场景层级最终被放弃——它的子类之间筛出的骨架完全相同，用户做完选择感知不到自己筛掉了什么。

**给药方式由场景派生，不由用户勾选。** 这个决定容易被误读成交互简化，实际原因是评分口径：给药方式会实质改变候选的排序与存留，进入组织的注射填充与屏障已破的创面敷料两条路径把免疫原性门槛收紧到 0.35，同一条候选在面膜贴片下标为合格、在这两条路径下可能直接被否决。如果让用户随手勾选，就等于让用户在不理解后果的情况下决定哪些候选算合格。把它绑定到场景上之后，用户仍然能改变它，但只能通过改变产品形态这个有意义的方式。原本作为独立一层呈现的「施加手法」——涂布、手工涂抹、喷涂、接触创面之类——相应降级成路径自带的一串描述性说明，它既不筛骨架也不参与打分，作为必选项只会让用户做一次没有信息量的选择。

**安全不给分数，给裁决。** 安全面板呈现的不是一个综合安全分，而是逐项的实测值、阈值、判定与是否已评估，最后汇总成一个总裁决。裁决有四个取值而不是两个：全部通过、至少一项越限被否决、没有越限但有一项落在阈值 10% 以内的压线区、以及一项都没评估因而无法判定。最后一个取值的存在是为了避免把「没测过」呈现成「通过」——这条规则贯穿整个界面。

**「未评估」不等于零。** 九项分数在数据层全部可空，空缺表示该项没有测量值，与「真实测到零分」是两回事。界面上空缺渲染成未评估而不是 0.00，也不配上不通过的徽章。这条约定的分量从覆盖面上就能看出来：免疫原性有两条互相独立的通路，一条覆盖 117 条构造、另一条覆盖 186 条，交叠之后仍有 **198 条两者皆空**。如果把这些渲染成 0 分，界面上会出现近两百条「免疫原性为零、完全安全」的候选，而事实上它们从未被测过。

**只可排序的分数不装成概率。** 抗炎与抗黑素沉积两个方向的功能分来自判别「像不像功能肽」的模型，而不是测量抗炎或抗黑色素活性，数据库在这些行上明确标注了该分数只可用于排序、不可当作概率读取。因此这两个方向的分数在列表行与工具网格上都带排序标记，不上概率配色，也不给通过或不通过的徽章。

**失败原因按实际越限项生成。** 被否决的候选在列表里显示的不是一句笼统的「安全性未通过」，而是实际越限的那一项——可能是毒性，可能是溶血，也可能是免疫原性。三者的处理建议并不相同，笼统呈现会让用户做错下一步。

## 五、当前用户体验的真实完成度

需要明确区分界面上哪些内容是真实数据、哪些还是临时形态，这是一份技术交接材料必须交代的事。

已经真实接通的部分范围很广：五个页面的内容全部来自数据库，列表与详情里的每一个数值都能追到具体的表与字段；安全裁决按所选路径的门槛现场判定；综合分按路径的权重档现场重算，同一条候选在五条路径下的综合分会不同；六段解读文本由服务端读取该构造的真实分数与阈值生成，每个数字都能在同一份响应里找到对应字段；对话栏也已经接到同一个服务端生成器上，返回的是基于真实数据的回答而不是固定文案。

仍是临时形态的部分也有几处，且性质不同。**选择骨架与选择连接片段都不改变候选肽的集合**，因为 496 条构造的骨架绑定全部是占位值、连接片段外键又都指向样例表的第一行，界面各用一条提示如实说明了这一点，而不是让用户以为自己的选择起了作用。这两项改变的是每条候选被装配成的序列与界面报出的融合长度。**连接片段库尚未与应用路径建立对应关系**，五条路径在第 4 步拿到的是同一份列表；骨架早已按路径收窄，连接片段要等库里补出这个维度才能跟上。**融合序列在没有指定骨架时不完整输出**：调用单条构造的详情时骨架那一段标记为序列不可用，页面只画出连接片段与功能肽两段真实存在的部分；而从构建器里走完五步拿到的结果序列是完整的，因为它以用户当场选定的骨架与连接片段拼接，界面标明这是按请求参数装配、不是管线产出。

还有几处属于交互层面的粗糙点，不影响数据正确性但影响使用手感：肽库浏览器目前只有筛选而没有搜索框与排序控件，与工程说明文档里「支持搜索、筛选与排序」的描述不符；列表的「显示更多」只增加单次请求的条数而不做真正的分页，构造总数较多时这一处会明显偏慢；应用只有五条显式路径而没有兜底路由，访问不存在的地址会落到空白页；工程里还留着两个不再被渲染的文件，一份是建站时模板附带的样式表，一份是旧的置顶样式文件，后者全工程没有任何引用点。

界面上另有两处刻意的克制，属于设计而非缺陷。**两个方向带待签字标记**：抗炎与抗黑素沉积在库里有数据但管线尚未确认，界面用状态标记把它们与已就绪的两个方向区分开，而不是隐藏或伪装成同等成熟。**材料形态是提取值**：骨架的材料形态（冻干海绵、自组装水凝胶、注射凝胶、成膜、纤维、膜片、溶液型配方）不是数据集里的字段，而是从产品用途与关键结果两段散文里人工提取的归类，界面用它做筛选，但这一列本身仍待团队最终确认。
