# 02 Data Assets and Data Shape

## 1. Overall layout of the data

The project's data is not a single table but a three-layer structure; the three layers differ completely in granularity and purpose, and discussing them together loses meaning.

The lowest layer is the **peptide layer**, on the order of twenty million entries, holding the short peptide sequences themselves, 1 to 30 residues long, together with the scores a dozen or so prediction tools give each peptide. This layer is the raw material; all computation of the screening pipeline happens here, and the user does not see it directly, only the screening results. The middle layer is the **construct layer**, 496 entries, holding the results converged after one round of screening has run: which peptide pairs with which scaffold and which linker, what the aggregate of the nine scores is, and whether the safety gate passed. This layer is where the product is directly supplied with data. The top layer is the **reference layer**, small in scale but the most "solid" in content, holding the formal entries for scaffold proteins and linkers, including real amino acid sequences, patent and application information, and experimental and regulatory evidence — this layer comes from real patent data compiled entry by entry by team members and is not a prediction product.

The three layers are linked by foreign keys: the construct layer points to the peptide layer through the peptide ID, and to the reference layer through the scaffold ID and the linker ID. This linkage currently has one break, falling on the construct-to-scaffold segment, which will be described separately below.

## 2. Peptide layer: twenty million short peptides and their per-tool scores

The main body of the peptide layer is a table named `peptides`, measured at **20,248,885 rows**, with data files of about 8 GB. The key fields of each row are the sequence itself (at most 30 residues, measured minimum length 1, database layer permitting 1 to 30), the length, the source identifier, the source version date, and the MD5 checksum of the sequence. The table has a unique constraint requiring the combination "sequence + source + source version" to be unique, which guarantees that the same sequence within one source is not inserted twice, while allowing different sources to each keep their own copy.

The sequences come from 10 data sources, and the source manifest is itself a table (`dataset_manifest`, 10 rows, all with status complete, recording each source's version date, file checksum, scan start and end times, and rows written). By entry count, **the metagenomic source `legacy_mgy_2022` alone accounts for 19,154,247 entries, about 94.6% of the total**, which is also why typical sequence lengths in the library skew short — metagenomic fragments are broken short sequences to begin with. The other nine sources total about 1.1 million entries, including the complete set and the reviewed set of UniProt, the UniRef90 cluster set, PDB structural chains, and several historical snapshots of earlier years. The library also has a `peptide_metadata` table for carrying secondary attributes of sequences (parent sequence header, taxonomic information, PDB ID and chain ID, reading frame, source file offset, and so on), measured as **an empty table**, with not a single row, so these classes of attributes are currently unavailable as a whole.

Prediction scores are stored in a typical long table. The primary key of `peptide_enrichment` is the combination of the two fields "peptide ID + tool name"; each row gives the tool's score for that peptide, a readable label (a verdict word such as `Non-Toxin`, `Soluble`, or `≤40`), and a detail field of JSON structure (recording the model name, threshold, composition of sub-scores, and whether the inference device is GPU or CPU). This table is measured at about **378 million rows and 130 GB**, the largest in the entire database. The measured coverage of the peptide library is as follows: **twelve tools achieve 100% coverage over all 20,248,885 peptides**, namely toxicity, hemolysis, allergenicity, the three antioxidant heads, antimicrobial, cell penetration, solubility, thermal stability, anti-melanin, and the MHC-I prediction tool for immunogenicity — the last of these shows 100% coverage because its denominator counts only the 134,888 peptides within the applicable length range rather than the whole library.

The data of the other immunogenicity pathway is stored separately in the `netmhc_score` table, organized by "peptide + allele", estimated at **147.5 million rows and 35 GB**, covering 131 alleles. This table retains each peptide's binding rank and binding level across HLA alleles, which in theory can support finer analysis than a single score, but the current product does not use this granularity. There are two further practical facts related to this table: its CREATE TABLE statement cannot be found in this repository, and the source of the table structure needs to be confirmed with the pipeline maintainers; and its data volume is so large that even counting rows exceeds the query timeout set on the server side.

One place that is easy to fall into is that **the aggregation propensity score is not in `peptide_enrichment`**. Searching the library for `aggrescan` by tool name returns zero rows, because it is not an external prediction service but is computed on the spot by the pipeline during the assembly stage from the peptide sequence using the residue-scale AGGRESCAN table, with the result landing only in the construct-layer scores. This means that any implementation that reads only `peptide_enrichment` cannot obtain the aggregation propensity score.

## 3. Construct layer: 496 screening results

The construct layer has only one core table, `constructs`, with **496 rows and 744 kB**; it is one of the smallest business tables in the whole database, yet it is the main table through which the product is supplied with data. The fields of each row fall into four groups. The identity and classification group records the construct ID, functional direction (four values), channel (primary selection or control), and status (passed or pending sign-off). The assembly group uses three foreign keys pointing to peptide, scaffold, and linker. The results group includes the rank, the aggregate of the nine scores (stored in one JSON-structured field), the delivery score computed under the old convention, and three boolean markers recording whether hemolysis, MHC-I, and MHC-II were evaluated. There is also a historical field recording the scenario value at assembly time, in which two spelling variants of the same concept exist, and the product does not expose this field.

The distribution across the four directions is the most important structural fact of this table, because it directly determines the availability of each direction in the interface:

| Functional direction | Primary channel | Control channel | Total | Status |
|---|---|---|---|---|
| `antioxidant` antioxidant | 113 | 57 | **170** | all pass |
| `antibacterial` antimicrobial | 7 | 58 | **65** | all pass |
| `anti_inflammatory` anti-inflammatory | 87 | 67 | **154** | all pending sign-off |
| `antimelanin` anti-melanogenic | 83 | 24 | **107** | all pending sign-off |

Every row in the table is divided into two channels, primary and control. **The control channel is not padding**: it retains the batch of candidates with the lowest scores from the same ranking round, whose role is to provide a baseline of "known to have very poor activity" for the subsequent rounds, used to confirm that the scoring system is really distinguishing good from bad rather than performing meaningless ranking within a very small dynamic range. Control-channel constructs likewise go through the complete safety gate and scoring process, so their scores are comparable.

**Scores are heterogeneous by direction** is the second key feature of this table. The aggregate of the nine scores is stored in one JSON-structured field; across the whole table 26 keys appear, but no single row possesses all of them. The four directions share only six — toxicity, hemolysis, immunogenicity MHC-I, aggregation propensity, allergenicity, and cell penetration — and the rest are direction-specific: the antioxidant direction uses its own antioxidant activity tool and two branch heads, the antimicrobial direction uses an antimicrobial model, the anti-inflammatory direction uses the anti-inflammatory channel plus the control values of four other channels, and the anti-melanin direction uses a tyrosinase inhibition model. Understanding this matters, otherwise one would think that "some constructs are missing several scores", when in fact those scores simply do not apply to them. Structurally more noteworthy is immunogenicity: the MHC-I key exists in all 496 rows, but **only 117 rows have a real value**, the other 379 being null, for reasons set out in section 5 below.

The construct layer has two further cases where field names do not match actual content, a piece of historical legacy that must be known. The field `full_sequence` should, by its name, be the complete fusion protein sequence, but the measured content of all 496 rows is a pipe-joined string of three segments of the form "placeholder scaffold name, linker, peptide sequence", and not one row is a real amino acid sequence — the assembly script's comments explain why: scaffold and linker were both placeholder values at the time, and the script was only responsible for landing the minimally viable combination in the database so that the table structure and sample data were complete, leaving the real bindings to the compute service. The field `delivery_scores` holds scores under the four old delivery methods; its keys and the current five application routes are not the same coordinate system, and no reversible mapping exists between the two, so this field is retained for reference but not output externally. Another semantic marker field appears on 261 rows, with only one value — "rankable only, not to be read as a probability" — and this single value pins the nature of the scores of the anti-inflammatory and anti-melanin directions into the data.

## 4. Reference layer: scaffolds and linkers

### Three granularities of scaffold data

Scaffold data exists in the library as two parallel structures whose granularity and provenance both differ; mixing them leads to error.

The three older tables are at **sequence-record granularity**: `scaffold_patent_records` has 27 rows, one row corresponding to one patent sequence record or one patent product entry, of which 16 rows carry a complete amino acid sequence and 11 rows have no sequence (entries for applications proposed by a patent but whose sequences were not disclosed); `scaffold_groups` has 11 rows, at the experimental-group dimension, grouping the 27 records into 11 groups; `scaffold_experiments` has 12 rows, the experimental detail, one row corresponding to one "experimental group × evidence grade" combination, recording which experiments were actually done, the main results, where the results sit in the original text, and the limitations of the evidence.

The more recently imported tables are at **protein-cluster granularity**, consistent with the granularity at which the product works: `scaffold_library` has 8 rows, one row per protein cluster; `scaffold_library_sequences` has 16 rows, one row per patented sequence variant, attached under a cluster. These two tables come from a 30-column master table compiled by team members, and **the five application label columns exist only in this master table**; none of the three older tables has them. These five labels are the only place in the dataset that states "which application routes exist", and the only basis on which the product narrows scaffolds to a given route, so this new set of tables is not duplicated construction but indispensable.

The measured composition of the eight protein clusters is as follows. The evidence grade column records the highest evidence level that can be verified for that cluster, not a statement that "all experiments have been completed".

| Protein cluster | Applicant | Category | Representative sequence length | Highest evidence | Application routes accepted |
|---|---|---|---|---|---|
| Recombinant humanized type III collagen HC8/HC16 | Jinbo | recombinant collagen | 501 | E5 | mask patch, injectable filling |
| COL3A1 functional domain 16-tandem collagen | Jinbo | recombinant collagen | 490 | E5 | mask patch, injectable filling |
| Recombinant human type XVII collagen fragment | Trautec | recombinant collagen | 466 | E5 | hair care, wound dressing |
| Human-like collagen FHLC | Giant Biogene | recombinant collagen | 1071 | E5 | film-forming coating, mask patch, wound dressing |
| Short recombinant silk fibroin SF-4/SF-10 | Yusong | silk | 62 | E2 | mask patch, wound dressing |
| Recombinant spider silk protein 18B | Bolt Threads | spider silk | 945 | E4 | film-forming coating |
| Engineered spider silk protein eADF4(C16) | AMSilk | spider silk | 560 | E1 | hair care |
| Triple-helix-like recombinant human collagen III | Wuhan (Collagen (Wuhan) Biotechnology) | recombinant collagen | 225 | E1 | wound dressing |

The grading rules of the evidence grade are themselves data: **E1** is purified protein or physicochemical, cell-free experiments; **E2** is cell experiments; **E3** is animal experiments; **E4** is human use or controlled clinical studies; **E5** is regulatory review, controlled clinical trials, and post-market safety data. Of the eight clusters, three reach E5, one E4, and two E2 and below. The two highest both fall on recombinant collagen, consistent with the fact that this category already has registered products in China.

**The role of this grade is easily read backwards, and it needs to be used as "the highest level that can be verified".** A mark of E5 means that regulatory review or post-market safety data supports the safety of this protein **for a certain** use, not that the new use for which it is employed on the platform has also been validated; a mark of E1 likewise does not mean the protein is without value, only that the publicly verifiable evidence stops at the cell-free level. The evidence-limitation field attached to each record in the library exists precisely to record such gaps.

**The grade of the hair care route is the one most in need of being read by this convention.** On its surface it carries two capable institutions, but on closer inspection this is not so: Trautec's E5 comes from its wound dressing product, which obtained provincial-level medical device registration, with a registered scope covering non-chronic wounds and post-aesthetic wound care, unrelated to hair care; hair care appears in that material only as a patent-proposed idea of follicle repair and scalp care. AMSilk's eADF4(C16) reaches only E1, with the evidence limitation stating that the evidence is mainly cell-free and ex vivo. The other four of the five application labels are each backed by at least E4 or E5; only this one lacks human or regulatory evidence corresponding to the labeled indication. The product's treatment of this one is to retain the route and carry a note within its definition, writing the fact that "evidence is still accumulating" into the data, rather than deleting the entry or making it look as mature as the other four.

Turning this table around by application route gives the complete mapping of "which scaffolds will be obtained by selecting this route" in the product interface: the five routes filter out **2, 4, 2, 4, and 2** protein clusters respectively, and no two routes point to exactly the same set of scaffolds — which is also why the five routes can directly reuse the ready-made labels in the dataset without inventing another classification.

| Application route | Protein clusters filtered | Scaffolds received |
|---|---|---|
| injectable filling | 2 | two Jinbo clusters |
| hair care | 2 | Trautec COL17, AMSilk eADF4(C16) |
| film-forming coating | 2 | Bolt 18B, Giant Biogene FHLC |
| mask patch | 4 | two Jinbo clusters, Yusong, Giant Biogene |
| wound dressing | 4 | Wuhan, Trautec, Yusong, Giant Biogene |

### Linkers

Linkers likewise have two sets of data. The older `linkers` table in the library has only 6 rows, placeholder entries of the two motifs `GGGGS` and `EAAAK` at three lengths each, and **the linker foreign keys of all 496 constructs point to the first of these rows**, which is a `GGGGS` pentapeptide. This means that no linker selection difference can be seen from the construct table itself. The newly imported `linker_library` table has 15 rows, formal entries landed from the data source of the product design draft, each with a name, sequence, length, rigidity level, composition of composite units (for example "two flexible units, one rigid unit"), description, and literature provenance, with rigidity presented in five tiers from fully flexible to fully rigid. The two data sets coexist without being merged in order to preserve the pointing semantics of the existing foreign keys; each linker's response carries a provenance marker stating which table it comes from, and whether to merge will be decided after the pipeline re-assembles the constructs by real scenario. The foreign key stored in the construct table is not the only basis at assembly time: the product allows the caller to specify a different linker in the request, after which the fusion sequence is spliced with that entry, the construct's own archived value stays unchanged, and the provenance of the two is labeled separately in the response.

## 5. Data semantic conventions

Each item in this section corresponds to a misreading that has already occurred or is very likely to occur. Their common feature is that the data itself is not wrong, yet the conclusions produced by misreading can be wildly wrong.

**A null is not equal to zero.** All nine scores are nullable at the data layer; a null means "no measurement value", which is a different matter from "truly measured as zero". Nulls across the whole library are concentrated on immunogenicity: besides the 379 nulls in MHC-I, there are another 135 real zeros, of which 116 are immunogenicity genuinely measured as 0 (that is, the model judges recognition to be almost impossible). If these nulls were uniformly rendered as a score of zero, more than a hundred candidates reading "immunogenicity zero, fully safe" would appear in the interface, when they have never been measured. The response body, in addition to nulls, carries a boolean marker stating whether the item was evaluated, precisely so that the caller need not guess at the meaning of a null.

**Very small non-zero values must not be rounded to zero.** Across the whole library there are more than three hundred scores that are numerically tiny but genuinely non-zero (concentrated in cell penetration and solubility); rendering to two decimal places would turn them all into `0.00`, presenting a measurement with signal as one without signal. Score formatting falls back to significant-figure notation when the value is sufficiently small.

**The functional scores of two directions can be used only for ranking.** The scores of anti-inflammatory and anti-melanogenic come from a model that discriminates whether something "looks like a functional peptide", not whether it is "anti-inflammatory or anti-melanogenic"; the database marks on these rows that they are rankable only and must not be read as probabilities. The product gives a ranking marker on both the list rows and the score grid for these two directions, uses no probability coloring, and gives no pass or fail badge.

**The percentile-rank direction of MHC-II is opposite to that of all other gates.** NetMHCIIpan outputs a percentile rank, and **the smaller the value, the stronger the binding**, while strong MHC-II binding is exactly the pathway that recruits helper T cells and triggers an immune response. Therefore this gate is "higher is better" — the passing condition is a rank above the strong-binder threshold. Any implementation that writes "above the limit is out of limit" without checking the direction will state the opposite conclusion for this gate.

**The immunogenicity threshold varies with the application route.** Toxicity 0.38 and hemolysis 0.55 are global values; immunogenicity is not: wound dressing and injectable filling tighten it to 0.35, mask patch and film-forming coating are 0.50, and hair care loosens it to 0.60. The same construct may pass under one route and be vetoed under another; this is not data inconsistency but part of the route convention.

**The scaffold binding of constructs is entirely placeholder values.** The scaffold foreign keys of all 496 rows point to the same placeholder record, whose stored content is a marker string rather than an amino acid sequence, with a length of zero. Therefore no real scaffold can be read from a construct, nor a complete fusion sequence assembled. The product's handling of this matter is to label the binding provenance truthfully rather than fabricate a plausible-looking sequence.

**The slot name of the functional score in the API does not match its content.** Of the nine scores, the slot named "antioxidant" actually carries **that direction's own functional score**, with the four directions filling in four different prediction tools. This slot name is a leftover from the single-direction period; read literally, three quarters of the library would appear empty. Two further fields in the response give the tool key and the display name of that score, avoiding ambiguity.

**The spelling of the functional score's tool keys is not uniform.** The four directions take values from four keys, `anoxpepred-frs`, `amp-esm`, `imfp_lg_AIP`, and `tipred`, mixing hyphens and underscores; this is not a typo but the original spelling at the time the pipeline wrote them. These keys are passed through as identifiers verbatim and are mapped to tool names only at display time.

**The direction name in the library differs from the product's old name.** The value of the second direction in the library is "antimicrobial", while the product's early documentation wrote "anti-microbial", a broader term, whereas the model behind it indeed judges only antimicrobial activity. The value in the library is now adopted uniformly.

**The old delivery scores and the new application routes are not the same coordinate system.** The delivery scores in the library are divided by four physical means — "topical, nanocarrier, microneedle, injection" — while the product's five routes are divided by contact interface and barrier integrity; the two axes are independent and no reversible mapping exists. The new composite score is recomputed entirely by the route convention, and the old values are retained for reference but not output.

## 6. Data gaps and items awaiting confirmation

The known gaps at the data layer fall into two classes, one being definite absences and the other qualitative open questions.

**There are four definite absences.** First, the construct-to-scaffold binding is entirely placeholder, the largest current data gap, whose filling depends on the pipeline re-assembling once by real scenario. Second, the peptide library's secondary-attribute table is empty, so information such as parent sequence, taxonomy, and PDB source chain is currently unavailable as a whole. Third, 11 patent records in the scaffold data have no disclosed sequence; they remain valid as evidence that "the patent proposed this application", but cannot participate in sequence assembly. Fourth, the data of the two immunogenicity pathways has not been merged — MHC-I has values in 117 rows and MHC-II in 186 rows, 298 rows have at least one of the two, and 198 rows have both empty.

**Two points about coverage need attention.** The measured lower bound of peptide length in the library is 1 residue, and constructs of only 2 residues indeed exist in the library (for example an entry whose sequence is "glycine-leucine"), whereas product narratives have long used the range "3 to 30 residues"; this deviation does not affect function, but external descriptions should take the library's actual range as authoritative. In addition, hemolysis prediction covers only a sample of five hundred thousand at the whole-library level; although all 496 constructs have values, this coverage would become a limitation if the safety gate is extended to a larger candidate set in the future.

**The one qualitative open item is material form.** The classification group of each scaffold — "lyophilized sponge, self-assembling hydrogel, injectable gel, film-forming, fiber, membrane sheet, solution formulation" — is not a field in the dataset but a judgment extracted from three prose passages: product use, potential application, and key results. It is the only usable ruler for secondary filtering, and all eight clusters have been filled in, but the classification itself still requires item-by-item team confirmation.

The original wording on which the extraction is based and the classification results are as follows. The reliability of the judgment varies greatly within this column, which is precisely why review is needed.

| Protein cluster | Formulation wording in the prose | Classification |
|---|---|---|
| Jinbo HC8/HC16 | lyophilized fiber, injectable gel | lyophilized sponge, injectable gel |
| Jinbo 16-tandem | injectable lyophilized fiber dermal filler, injectable gel, repair solution or dressing | lyophilized sponge, injectable gel, solution |
| Wuhan TRHCIII-1 | self-assembling collagen fiber or hydrogel | self-assembling hydrogel |
| Trautec COL17 | recombinant collagen lyophilized fiber | lyophilized sponge |
| Yusong SF-4/SF-10 | cosmetic raw material, skin care formulation candidate | solution formulation |
| Bolt 18B | film-forming barrier, powder, cream | film-forming, solution |
| AMSilk eADF4(C16) | salt- or acid-base-induced self-assembly, fiberization into film, cuticle coating | fiber, film-forming |
| Giant Biogene FHLC | medical dressing and mask, liquid dressing, essence | membrane sheet, solution |

Two kinds of wording give very definite judgments. The Wuhan entry is the cleanest in wording in the whole table — "self-assembling collagen fiber or hydrogel" is written directly in the patent-proposed application, and the key results also record phosphate-buffer-induced self-assembly and fiber morphology, so the classification is unambiguous. The Yusong entry is clearly definite in the opposite direction: its evidence limitation states that there is no evidence of material carrier or complete silk fibroin fiber structure, so it can only be classified as a solution-formulation raw material, not as fiber or film-forming.

The two entries needing particular review are AMSilk and Giant Biogene, whose original wording itself leaves room: AMSilk mentions three routes at once — self-assembly, fiberization, and film-forming — corresponding to more than one material form; Giant Biogene's "medical dressing and mask, liquid dressing, essence" spans two forms, membrane sheet and solution, and it is adopted by three application routes at once, so form attribution will directly affect the performance of the second screening layer. Two further entries' classifications depend on parsing composite wording of the "injectable lyophilized fiber" type and also need team confirmation — "injectable" describes the application method rather than the material form, and treating it as a form would cause duplication in classification.

**There is one further convention that needs to be aligned with the pipeline maintainers.** Several records in the library mention that the anti-inflammatory and anti-melanin directions used certain model keys, and these keys have no corresponding rows in the current database, indicating a discrepancy between the direction proposals and the model versions finally landed in the database. The constructs of anti-inflammatory and anti-melanin are therefore still marked as pending sign-off: the data is there, but the pipeline has not signed off on this batch of data.
