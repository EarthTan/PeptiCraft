# 04 技术架构与开发进度

## 一、架构全景

整个系统由三个部分加一个数据库组成，数据的流向是单向的。

用户侧是一个单页 Web 应用，由 Vite 构建，运行时在浏览器里跑。无论开发还是正式运行，它都只通过 HTTP 请求一个以 `/api` 开头的接口前缀。开发环境下这个前缀由构建工具的代理转发到本地的后端端口，正式环境下由部署平台做同样的转发——这一步的作用是让前端代码里只出现相对路径，跨域配置与后端地址的变更都不需要改前端。

中间是一个 FastAPI 后端服务，它是整个系统里唯一接触数据库的部分。它不写数据，只读；不计算预测，只装配与判定。它承担三类工作：把远程数据库里的真实内容按前端需要的形状输出；承接原本由管线占位、注释里明确留给计算服务的职责，也就是真实骨架的绑定、融合序列的还原、按应用路径重算综合分与安全判定；以及为界面上那几段解读文本与对话提供生成能力。

最后是数据库，一台 Ubuntu 工作站上的 PostgreSQL 16.15 实例，通过网络地址访问。把数据库放在工作站而不是放进服务进程的同一台机器，原因有两个：库里最大的两张表合计约 165 GB，不适合跟着服务迁移；而生成这些数据的预测模型大多需要 GPU，本来就运行在那台工作站上，让库与推理挨在一起可以避免反复搬运数据。代价是整个服务的可用性依赖于到这台工作站的网络连通性，这一点在后面第八节作为风险列出。

技术选型按这一结构展开。前端是 Vite 8 加 React 19、TypeScript 6、Tailwind 4，路由用 react-router-dom 7，图标用 Lucide，基础交互控件在 Radix 的无样式原语之上手写，而不是引入成品的组件库；样式采用 Tailwind 的 CSS 优先配置，主题变量直接写在样式表里。后端是 FastAPI 配 Pydantic 做响应模型、psycopg 3 做同步数据库驱动。选 FastAPI 的直接理由是响应模型可以由 Pydantic 声明，接口的字段结构因此可以自动导出成 schema 与前端类型逐字段核对，这在一次「前端契约驱动后端」的改造里价值很高；选同步驱动而不是异步，是因为需要在每个连接上生效的几条会话设置用同步连接池语义更直接，而本项目的接口查询都是按主键或小集合检索，并发压力不构成瓶颈。

## 二、前端架构

前端是五个页面对应五条路径的单页应用：落地页、肽库浏览器、构建器、结果页、骨架详情页。代码按职责分成四块，这个划分方式本身是一条约束。

**取数层**集中在一个目录下，由三个文件组成：一个负责发请求并做错误归一，一个把每个后端端点绑定成一个具名函数，一个保存后端响应模型的 TypeScript 镜像。镜像类型里的字段名**原样保留后端的蛇形命名**，不做驼峰转换——这样做是为了让接口的 schema 与前端类型可以机械比对，任何一处改名都会在比对时立刻暴露，而不需要经过一层命名转换的心智映射。

**状态与副作用**通过两个自定义钩子统一处理，分别服务于「加载一份数据」与「执行一次动作」两种场景。加载钩子内部带一个票号机制，每次发起请求时递增票号，响应回来时如果票号已经不是最新的就丢弃——这个机制解决的是快速切换筛选条件时，先发出的慢请求后回来、覆盖掉后发出的快请求结果的问题。错误被归一成几种可区分的类型，界面上据此给出不同的失败原因而不是统一的报错。

**共享展示组件**放的是结果页与肽库页共用的三块面板：安全门列表、工具分数网格、解读文本块。它们被抽出来共用的原因很具体——阈值漂移的根因就是这两处曾经各写一份实现。

**展示层映射**只负责把后端给的标识符翻译成界面元素：图标名到图标组件、分组的显示标签、权重档的中文可读标签、判定与格式化的规则、序列属性的本地计算。这里有一条贯穿全局的约束：**前端不做任何阈值比较与加权运算**。综合分与安全判定都由后端算好随响应返回，前端只负责呈现。这条约束有三个直接收益：阈值只存在一处，不会再出现界面与解读文本给出相反结论的情况；前端不必把九项分数与权重档一起搬到浏览器里算；将来调整口径只改后端，前端不需要重新发布。

状态管理方面工程里没有引入任何状态库。五个页面各自持有自己的数据，页面之间不共享可变状态，路由参数承担页面间的传参职责。这个选择与应用的规模相称，但有一个后果需要注意：结果页的骨架预览是通过改写查询参数实现的，因此浏览器的前进后退会参与这一处的状态。

## 三、后端架构

后端按职责分四层，层与层之间的约束是硬性的。

**路由层**只做参数校验、调用服务层、序列化响应，不出现任何 SQL 与计算。**服务层**承载全部阈值、权重与业务判断，不直接写 SQL。**仓储层**只做 SQL 查询与行到字典的转换，不含任何阈值或口径。**模型层**定义响应契约，字段名与前端类型一致。

这套约束的唯一目的是**让每一个阈值只存在一处**。这个目的不是抽象的整洁性——2026 年 9 月 17 日的审查里记录了三类由副本漂移造成的缺陷：同一个安全阈值表在两个页面各写一份，注释还声称两者共用定义；免疫原性门槛被全局写死成 0.50，而路径定义里写的是 0.35、0.50、0.60 三档，结果一条恰好压在收紧阈值上的构造被显示成通过了所有门；生成的解读文本引用了一个 0.70 的接受下限，而工具元数据里根本没有这个阈值，读者无法找到这个数字的出处。把阈值集中到服务层之后，这三类缺陷在结构上不可能再发生。

**参考数据是整个后端唯一的事实来源。** 五条应用路径的定义（接触界面、屏障层级、免疫暴露描述、三个权重档、免疫原性门槛、额外检查项、应用手法）、九个指标的工具元数据（工具名、测量对象、方向、分组、阈值与阈值来源、覆盖说明、是否否决门）、四轮保留与四轮排除的管线说明、四个功能方向的展示信息与状态推导规则，全部写在一个模块里。这个模块里出现的一切被前端当作数据读取，前端不保留任何一份副本。

数据库访问层是一个连接池，每个连接在创建时统一施加两项设置：连接标记为只读，以及一个查询超时。另有一组针对大表的调优设置**只在需要时施加**：把顺序扫描与位图扫描关闭，强制走索引。这组设置对那张 3.78 亿行的分数表有益，对只有 496 行的构造表却有害——对一张几百行的小表，不做过滤的列表查询本来就该走顺序扫描，强制走索引只会更慢。因此调用方在访问大表时显式声明，其余查询不动查询计划器。

错误处理区分两类失败并映射成不同的状态码。**数据库不可达**（网络不通、认证失败、连到了错误实例）返回 503 而不是 500，理由是数据库在另一台机器上、不可达属于暂时性故障，客户端重试是合理的；响应体里带一个错误标识与一段排查提示。**查询失败**（语句本身出错或超时）返回 500。这个区分让前端能给出准确的失败原因，而不是把所有失败都说成「服务器错误」。

## 四、接口面

后端提供 **19 个只读端点**，按资源分五组，另有一个用于对话的写端点。

参考数据组六个：健康检查与数据库连通性、一次性取回全部参考数据、分别取功能方向、取应用路径、取工具元数据、取管线轮次、以及各预测工具的实际覆盖统计。其中一次性取回参考数据这一个端点承担的负载最重，也最省事——一个页面上要用的方向、路径、工具、证据等级、材料形态、骨架分类全部一次拿到，避免了页面打开时的瀑布式请求。

构造组六个：分页列表（支持按方向、路径、通道、状态筛选）、单条详情、该构造在该路径下可选的骨架列表、该构造所用肽的逐工具分数明细、该构造的解读文本块、以及对话。列表接口统一返回「条目数组加总数、单次条数、偏移量」四件结构，前端因此可以直接显示总数而不用另发一次计数请求。

构建组一个，是整个接口面上唯一做组合而不是报存量的端点：它接收应用路径、若干功能方向、一条骨架与一条连接片段，返回该筛选下按综合分排序的候选，并逐条装配出融合序列。两个装配目标各自独立生效，都可以省略，省略时该零件回落到构造存档里记录的那一条；两者都不进入候选的裁定，只影响拼出来的序列与响应里报出的融合长度。它对候选集合的界定与构造列表不同——取的是顶部通道，因为底部通道是阴性对照臂，把对照标记排进候选里会让两者都难读。排序覆盖全部候选之后才按偏移量与条数切分：一条记录的综合分只取决于它所在方向的权重池，而池是独立于请求读取并按方向缓存的，先排全量才是正确顺序，也才让偏移量有了意义。统计出的安全裁决计数同样覆盖整个匹配集合，而不是返回的那一页。

骨架组三个与连接片段组两个：列表与详情，骨架另有「哪些构造用了这个骨架」。骨架的列表与详情是两个不同的形状——列表里不带序列与专利变体，详情里带；这个区分是刻意的，列表要能一次返回全部八个条目而不携带大段序列。

## 五、数据契约的几条设计决定

**空值必须带标记。** 九项分数在响应模型里全部可空，并且每一处空值都配有布尔形式的「是否已评估」标记。这样调用方不需要区分「字段缺失」与「值为零」这两种在 JSON 里都表现为空的情况，也就不存在把未评估误读成零分的可能。

**综合分随路径，并且可复现。** 单条构造的响应里带一个按路径索引的映射，键与五条路径的标识符一一对应，每一条包含该路径下重算的三个受调制分量、综合分、以及用于复现的全部中间量——每个分量的归一化值、得到的权重、得到的乘数。这样一份响应就足以让人手工复算出综合分，不需要重新查库或读代码。

**安全结论是结构而不是一句话。** 安全判定的响应是一个对象，包含该路径的免疫原性门槛、总裁决、逐门明细数组、未评估门的键列表、被否决的门的键列表。每个门的明细里带指标名、工具名、实测值、阈值、阈值来源、通过与否、是否压线、是否否决门、以及哪一侧算越限。最后这一个字段是必要的，因为 MHC-II 是唯一一个「越低越差」的门，任何不检查该字段就写下「高于限值即越限」的呈现逻辑都会在它上面把结论说反。

**分数的可读性质跟着数据走。** 每个分数在响应里都带一个语义标记，取值区分「可作概率读取」与「只可排序」。这个标记不只在详情里，列表行上也带，因为四个方向里有三个的排序依据来自模型，其中一个明确不是概率。列表行上不带这个标记，就会出现把排序位置当作置信度展示的情况。

**生成的文本带出处。** 解读文本按固定结构生成六块：安全解读、功能肽来源与组成、连接片段与装配、表达与处理、方向内横向对比、风险清单。每一块除了正文之外还带一个出处列表，列出该块引用的响应字段路径；同时整个响应带一个生成器标记，说明当前是模板生成还是模型生成。这个标记的作用是让前端能如实标注文本来源，而不是把模板文案呈现成模型输出。生成能力被抽象成一个协议而不是一个函数，将来接入大模型时新增一个实现并切换注册即可，路由层与响应模型不变。

**对话与解读共用同一套生成器。** 对话端点接收一条问题与该构造的上下文，返回回答与一组建议追问。当前实现对已知的问题类型给出确定性回答，未知问题返回可扩展的提示；配置项里预留了生成器与模型名的位置，服务启动时如果发现生成器配置指向尚未注册的模型实现，会打印一条警告并继续使用模板实现。

## 六、本地开发与运行

开发时的启动方式是两条命令：后端在服务目录下以模块形式启动一个本地 HTTP 服务，默认监听 8000 端口；前端在应用目录下启动开发服务器，默认监听 5173 端口，并把 `/api` 代理到 8000。前端工程另有类型检查加打包、预览构建产物、以及静态检查三条脚本。后端服务启动时不开启代码热重载，因此改动后端代码之后必须手动重启进程；如果重启时提示端口被占用，需要先找出占用该端口的进程并结束它再启动。

**数据库连接上有一个必须写进配置的陷阱。** 开发机上本机地址的 5432 端口上另有一套 PostgreSQL 实例在监听，但那是另一套系统，里面没有本项目使用的角色，连接会直接报角色不存在。而项目里几处默认连接串写的都是本机地址，那份默认值在设计时是给工作站自己用的；在开发机上不加覆盖地运行会**静默落到错误的实例上**，报错信息看起来像配置问题而不像连错机器。因此服务的连接配置必须显式指向远程地址，并且带一个禁止回落到本机地址的开关。

数据库结构的变更以独立的 SQL 脚本形式随服务一起交付，编号沿用了管线侧的序列以免混淆，两张新表的建表脚本可以重复执行。数据导入脚本读本地的表格文件，使用「冲突则更新」的写入方式，因此同样可以重复执行。两者相加使得整个数据准备过程是可重放的：哪怕在一台全新的机器上，也能从仓库里的表格文件把参考层重建出来。

## 七、开发进度

进度按五层盘点，各层的完成度差异很大，分开看才有意义。

**数据层是完成度最高的一层。** 两千万条肽库与十二个工具的逐工具分数已经全量就位，覆盖率为 100%；496 条构造的九项分数、安全标记、参数完整；骨架参考库从一份 30 列的整理表导入，8 个蛋白簇与 16 条专利序列变体全部带真实氨基酸序列；连接片段参考库 15 条带文献出处。数据层的缺口集中在三处：构造到骨架的绑定全部为占位；肽库的次级属性表为空；材料形态这一列是提取值而非原始字段。

**管线层已经跑完四个方向。** 抗氧化与抗菌两个方向的构造状态为已通过，抗炎与抗黑素沉积两个方向的构造全部处于待签字状态——数据在库里，但管线没有对这批数据签字确认，界面上保留这个标记。三维结构相关的第五到第八轮明确排除在本版本之外。需要说明的是，管线本身与生成这些数据的预测模型服务不在本仓库里，本仓库保存的是管线的建表脚本、运行脚本与结果文件；模型本体在另一个代码库里，通过本地 HTTP 服务被调用，各服务占用固定端口。

**后端服务层已经完整可用。** 19 个只读端点全部实现并运行，九个分数、按路径重算的综合分、结构化安全判定、分段序列、骨架与连接片段两个资源、六段生成的解读文本与对话全部接通。实测在本地环境可以完整走通：构造详情响应里同时带九项分数、五条路径各自的重算结果、按所选路径判定的安全结论、三段带颜色标记的序列片段、以及该构造在当前路径下可选的骨架列表。数据库不可达时返回 503 并带排查提示，这一路径也验证过——查询超时会正确触发这个分支。

**前端层已经完成从静态数据到真实数据的切换。** 五个页面的内容全部来自数据库，工程内原有的一整套静态数据模块与其类型定义已经删除，不再存在被页面渲染的硬编码数据。构建器按五步走完选择，最后一步向构建端点发出一次真实计算请求，排序、统计与装配都在服务端完成。仍属临时形态的有四处：选择骨架与选择连接片段都不缩小候选集，因为前者是占位值、后者在构造里全部取样例表第一行；融合序列在未指定骨架时不输出骨架段，只输出真实的连接片段与功能肽两段；连接片段库尚未按应用路径收窄，五条路径拿到同一份列表；肽库浏览器缺搜索与排序控件，列表的「显示更多」只增加单次请求条数而不做真正的分页。另有两处属工程整洁性问题：应用没有兜底路由，访问不存在的路径会落到空白页；工程里留着两个不再被渲染的文件，其中一个是全工程无引用点的样式文件。

**部署层尚未进入正式发布。** 本地开发链路的完整跑通已经验证，正式发布需要先构建前端产物并把产物复制到发布目录再上传，这一步在当前时点还没有执行过。

## 八、未决事项与风险

**骨架绑定是推断值而非管线产出，这是当前最实质的一处风险。** 496 条构造的骨架外键全部指向占位记录，真实绑定不存在。产品选择的处理是如实标记绑定来源：默认不编造骨架、不输出融合序列，只输出真实存在的两段；调用方显式指定一条真实骨架时按该骨架装配，并把绑定来源标为「按请求推断」并附说明。因此界面上需要避免把推断的骨架呈现成已验证的选择，这个标记在列表行与详情里都存在。

**待签字方向的呈现方式需要团队决定。** 抗炎与抗黑素沉积在库里有数据但状态未定，抗炎方向的设计文档本身也写明不能按「已就绪」呈现。产品照实输出状态，但界面上是作为候选展示并加显著标记、还是默认隐藏，属于产品决策而不是实现决策。附带一个问题：这两个方向的排名字段虽有值但状态未定，按排名展示可能造成误导。

**综合分的权重口径需要与管线维护方对齐。** 服务端把溶解度与热稳定性纳入了受路径调制的分量，理由是产品为每条路径定义了这三个权重档，而这两个指标此前从未被使用，导致三档权重里有三分之二是空转。这个口径与管线里现有的实现不完全一致（管线只调制了一个分量，原因是乘数键不匹配），因此在两边口径统一之前，服务端输出的综合分与管线重新计算的结果会对不上。另外这个口径本身也未与管线负责人确认过。

**否决门是三项还是四项需要确认。** 服务端按三项实现（毒性、溶血、免疫原性），依据是管线第二轮明确的三项检查与解读模块自身的统计逻辑；而早期需求文档写的是四项汇总，旧界面里也提到过聚集倾向作为否决项。当前的界面按服务端声明的标记如实呈现，改门数只需要改服务层里的一处定义。

**免疫原性的双通路没有合并。** MHC-I 与 MHC-II 是两条独立通路，当前方案并列输出而不合并成单一免疫原性数值，并且 MHC-I 只覆盖 117 条、MHC-II 覆盖 186 条，两者皆空 198 条。是否需要合并、按什么规则合并，需要有依据的判断，不适合由接口层自行决定。

**远程连接是单点依赖。** 后端完全依赖到那台工作站的网络连通性，该地址走的是组网隧道，开发机与工作站的隧道任一端断开服务即不可用。接口层已经把「数据库不可达」与「查询失败」区分开，让界面能给出准确的失败原因，但这只是让故障可读，不改变依赖关系本身。

**两处口径来源需要向数据方确认。** 材料形态这一列是从散文里提取的人工归类，八个簇都已填写但仍有两条留有余地，需要团队逐条确认。另外 MHC-II 的强结合子界线取的是该工具的通行用法（排名前 2%），而管线上原本只是把它当作测量值携带、不设阈值，这个阈值是服务端引入的，属于平台常量而不是工具或路径口径。
