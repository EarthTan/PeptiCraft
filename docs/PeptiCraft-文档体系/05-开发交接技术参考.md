# 05 开发交接技术参考

本卷面向后续接手的开发人员与 AI Agent，内容是精确到文件、字段与取值的交接信息。它假设读者会修改代码，因此不重复叙述设计理由——理由在 01 至 04 卷里。

## 一、仓库布局

仓库根目录 `iGEM-website/` 下有六个业务目录，各自的职责不重叠。

**`app/`** 是前端单页应用，前端专用。源码在 `app/src/`，构建产物在 `app/dist/`。这个目录自带独立的 git 仓库。

**`service/`** 是后端 FastAPI 服务。源码在 `service/app/`，数据库迁移脚本在 `service/sql/`，数据导入与自检脚本在 `service/scripts/`，环境配置在 `service/.env`（模板为 `.env.example`）。

**`data/`** 是参考层数据的原始文件，是骨架与连接片段两张表的导入来源。

**`iGEM-platform-main/`** 是既有的数据管线，不是待建的服务。它包含四个方向的 `select / scoring / assemble / run` 四件套、建表脚本、运维面板、以及结果导出文件。本仓库保存的是管线代码与建表脚本，**预测模型本体不在这个仓库里**，它们位于另一个代码库，以本地 HTTP 服务的形式被管线调用，各服务占用固定端口。

**`docs/`** 是文档目录，其中 `docs/PeptiCraft-文档体系/` 是本套文档。同目录下另有三份更早的材料，与本套文档的分工在 00 卷里说明。

**`publish/`** 是正式发布用的静态产物目录。

## 二、后端分层与文件清单

分层的约束是硬性的：`routers` 只做参数校验、调用服务、序列化；`services` 承载全部阈值、权重与业务判断；`repositories` 只做 SQL 与行到字典的转换；`models` 定义响应契约。改动时先判断该改哪一层，越层的改动会重新引入阈值漂移。

| 文件 | 职责 |
|---|---|
| `app/main.py` | 应用装配、CORS、两个异常处理器、生命周期探针 |
| `app/config.py` | 环境变量与设置 |
| `app/db.py` | 连接池、会话设置、`DatabaseUnavailable` / `QueryFailed` |
| `app/services/reference.py` | **唯一的事实来源**：五条路径、九个工具元数据、四轮保留与四轮排除管线、四个方向展示信息、材料形态与证据等级 |
| `app/services/scoring.py` | 九项分数装配、六个分量与权重池、综合分、安全判定、`VETO_GATES` |
| `app/services/constructs.py` | 列表与详情装配；`assemble_row` 是「用哪条骨架、哪条连接片段装配」这一判断的唯一落点 |
| `app/services/assembly.py` | 融合序列拼接、分段、占位骨架识别 |
| `app/services/build.py` | 构建器的排序与统计：候选集合的界定、跨方向排序、裁决计数，以及两个装配目标的解析与说明文案 |
| `app/services/scaffolds.py` | 骨架读入与形状转换 |
| `app/services/linkers.py` | 连接片段读入与形状转换；两张表的字段差异只在这里归一 |
| `app/services/analysis.py` | 解读文本生成的协议与模板实现、对话 |
| `app/repositories/enrichment.py` | `peptide_enrichment` 读取、工具名常量 |
| `app/repositories/constructs.py` | `constructs` 读取 |
| `app/repositories/catalog.py` | 方向计数、肽数统计、覆盖统计 |
| `app/repositories/scaffolds.py` / `linkers.py` | 参考层读取 |
| `app/models/*.py` | 响应契约，字段名与前端类型一致 |

`app/db.py` 里有两组会话设置，语义不同不要混用。每个连接在创建时统一标记只读并施加查询超时；而关闭顺序扫描与位图扫描这两项**只在访问 `peptide_enrichment` 时施加**（`cursor(force_index=True)`），因为对大表强制走索引有益，对 496 行的 `constructs` 反而更慢。

构建组（`app/routers/build.py`）：

| 方法 | 路径 | 参数 | 说明 |
|---|---|---|---|
| GET | `/api/build` | `direction`（可重复，或逗号分隔，至少一个）、`route_id`（缺省取第一条路径）、`scaffold_id`、`linker_id`、`limit`(1–500，默认 50)、`offset` | 按路径与两个装配目标裁定候选集合并逐条装配融合序列；响应含 `counts`、`totals` 与两个来源说明 |

`/api/build` 是唯一一个**做组合而不是报存量**的端点，别处都在回答「某条已存的构造是什么样」，它回答「选定路径、方向、骨架与连接片段之后，候选变成什么样」。它与 `/api/constructs` 有三处不可互换的差别。第一，候选取自 `channel='top'`：底部通道是阴性对照臂，行是真的、分是真的，但它是用来做比较基准的，把对照标记排进候选里会让两者都难读；`scoring` 计算权重池时读的也正是 `top` 通道，构建器排的序必须是候选所属的那个分布。第二，**排序覆盖全部候选之后才切分页**：一条记录的综合分只取决于它所在方向的权重池，而池是独立于请求读取并按方向缓存的，因此行的分值不会因为请求范围变窄而移动，先排全量再切片是正确顺序而非权宜，也才让 `offset` 有了意义——在浏览器内对单页排序则从来没有过。第三，**每行各自带绑定状态**：指定骨架时全批都是 `inferred`，不指定时各行回落到自己存档的绑定，于是同一响应里可以有的行有融合序列、有的行没有。

两个装配目标的作用面是同一处，都不改候选集合。骨架与连接片段改变的都是每条候选被拼成什么序列、以及卡片上的融合长度；`linker_id` 是后加的那个，加它的理由是装配的三个组成部分里只有它还钉死在定值上——`constructs.linker_id` 全部指向样例表第一行 `GGGGS`，那是装配脚本「取第一条可用行」的结果而非设计选择。指定 `linker_id` 时全批用同一条，不指定时各行回落到自己存档的那条，此时**同一响应内各行可以不同**。两种来源的说明文案分开给出（`binding_note` 与 `linker_note`），因为两个决定是分别做的：一次构建可以骨架取自存档、连接片段取自请求，合写成一段就必须描述一条半存半取的记录。解析只做一次并传给每一行，否则一次构建会对远端机器发起与候选数同量的查询。

`counts` 的四个计数与 `ranked` 覆盖的是**整个匹配集合**，不是返回的那一页。两者的差别正是这一页以前无法不显示的那个数字：按页统计读到的是切片落在哪里，而不是候选集合的形状。`without_composite` 记录在该路径下算不出综合分的候选，它们排在末位而不是按零参与排序——方向的权重池只有一条观测时没有可供加权的离散度，此时算不出综合分，与「分很低」是两回事。超过 `CANDIDATE_CEILING`（2000）的方向会直接报错而不是截断，因为被悄悄截短的排名读起来仍然像完整排名。

| GET | `/api/scaffolds` | `route_id`、`category` | 列表形状，不含序列与专利变体 |
| GET | `/api/scaffolds/{id}` | — | 详情，含序列变体、实验、监管注册、`unavailable_fields` |

## 六、数据语义不变量

以下每一条都有对应的错误先例，改动相关代码时应把它们当作断言。

1. **九项分数全部可空，空不等于零。** 空表示未评估。响应同时给 `score_meta[field].assessed` 与 `assessed_flags`，界面把空渲染为「未评估」而不是 `0.00`，也不给不通过的徽章。全库免疫原性（MHC-I）空缺 379 行、有值 117 行。
2. **极小非零值不得渲染成 `0.00`。** 全库有三百多个这样的值，集中在 `cpp` 与 `solubility`。格式化函数在数值足够小时回退到有效数字。
3. **`ranking_only` 的分数不得按概率呈现。** 抗炎与抗黑素两个方向的全部构造都是这个语义。列表行上也带该标记，因为卡片上会显示功能分。
4. **MHC-II 的正负方向与所有其它门相反。** `higher_is_better = true`，通过条件是百分位排名**高于** 2.0。任何写「高于限值即越限」的呈现代码在它上面会说反。该门当前是软信号，不否决。
5. **免疫原性门槛随路径变化，不得写死。** 读 `safety.immunogenicity_threshold` 或路径配置，不要用字面量 0.50。
6. **当前 496 条构造的骨架绑定全部是占位值，但服务不得假定这一点永远成立。** 这 496 行的 `backbone_id` 全部指向同一行占位记录，其名字含 `PLACEHOLDER` 且序列为空。服务判断一个绑定可否用于装配的依据，是 `backbone_id` 关联到的行有没有真实氨基酸序列：有则绑定为 `verified` 并输出完整融合序列，只有标记字符串或空序列才判为 `placeholder` 并拒绝输出融合序列。判断集中在 `assembly.is_placeholder_backbone` 一处，装配与绑定上报共用它，因此不会出现一处当成真序列、另一处当成占位的情况。显式传 `scaffold_id` 时绑定标为 `inferred`，该参数优先于已存绑定。构造的 `backbone_id` 指向 `backbone_proteins`，与策展库 `scaffold_library` 是两张不相通的表，两者的编号体系不同。
7. **`constructs.scores` 按方向异构。** 全表 26 个键，无一行拥有全部键；四方向共用 6 个键，其余为方向专属。按缺键判断「数据不完整」是错的。
8. **`constructs.delivery_scores` 是旧四键口径**（`topical` / `nanocarrier` / `microneedle` / `injection`），与五条应用路径不存在可逆映射，不对外输出，只在肽明细接口里作为存档返回。
9. **`constructs.full_sequence` 是标签串**（形如 `4RepCT|GGGGS|<肽>`），不是氨基酸序列，不得直接输出。
10. **`constructs.linker_id` 全部指向 `linkers` 表第一行**（`GGGGS`），因此构造表上看不到连接片段的选择差异；正式条目在 `linker_library`，响应里用 `source_table` 区分。构建器与构造详情可以显式指定 `linker_id` 覆盖它，指定后融合序列改用该条，构造自身的存档值不变。解析构造自己的 `linker_id` 时必须只查 `linkers`，不能先查策展库：这个外键指向样例表，若策展库里存在编号恰为数字的条目，先查策展库会把构造真正指向的那一行遮住。`linkers` 与 `linker_library` 的列名有两处不同（前者是数值 0/1 的 `rigidity` 且无档位文本，后者是文本档位加 `rigidity_index`），归一集中在一处，供两条读取路径共用。
11. **聚集倾向不在 `peptide_enrichment` 里。** 按 `tool='aggrescan'` 查询返回零行，它只存在于 `constructs.scores.aggrescan_a3v`，由管线在装配阶段实时计算。
12. **`temstapro` 与 `sodope` 只在 `peptide_enrichment` 里。** 只读 `constructs` 会以为这两个指标从未运行，实际两者各有 20,248,885 行且 496 条构造全部有值。
13. **对照通道是对照组。** `channel=bottom` 的行是真实的、带完整分数的，用途是提供基线而非作为候选。
14. **方向状态由数据推导，不要在前端写死。** `ready` 要求该方向存在 `passed` 状态的构造；抗炎与抗黑素因此是 `wip` 而不是 `empty`。

## 七、启动、调试与已知陷阱

后端的启动方式是在服务目录下以模块形式运行本地 HTTP 服务，默认 8000 端口；前端在应用目录下启动开发服务器，默认 5173 端口，`/api` 代理到后端端口。

**陷阱一：连接串回落到本机实例。** 开发机上本机地址的 5432 端口另有一套 PostgreSQL 在监听，里面没有本项目使用的角色，连接会报角色不存在。项目里几处默认连接串写的都是本机地址（那是给工作站自己用的），在开发机上不加覆盖地运行会静默落到错误的实例。服务的连接配置必须显式指向远程地址，`.env` 里的 `IGEM_PG_ALLOW_LOCALHOST` 应保持为禁止。判断是否连对：`/api/health` 返回的 `database.server` 应显示 PostgreSQL 16.15 与该库名。

**陷阱二：后端不开启代码热重载。** 改动后端代码之后必须手动重启进程。旧进程占着端口时先找出占用该端口的进程再结束它，否则新进程起不来而旧进程还在提供旧代码——这种情况下的症状是「改了代码但行为没变」。

**陷阱三：查询超时。** 连接统一施加查询超时（默认 60 秒）。对 `netmhc_score` 这类上亿行的表做不带条件的 `count(*)` 会直接触发超时并返回 503，而不是慢。需要行数时读统计信息而不是精确计数。

**陷阱四：前端依赖代理。** 前端代码里只出现 `/api` 相对路径，开发环境的转发由构建工具配置承担，目标地址可由环境变量覆盖。绕过开发服务器直接打开构建产物会导致接口全部 404。

## 九、验证方式

改动之后按三层验证，三层的失败含义不同：数据层失败说明映射断了，接口层失败说明契约漂移了，界面层失败说明呈现与数据不一致。

**数据层用一组断言检查映射的完整性**，放在 `service/scripts/` 下。要断言的事有四类：496 条构造是否全部能关联到肽、以及肽是否全部能关联到肽级分数；九项分数里每一项的非空条数是否与服务端输出一致；构造行里存在但未被任何接口使用的键（各方向的专属功能分键是主要一批）是否被显式记录，而不是默默丢弃；参考层的路径收窄计数是否与数据集的标签计数吻合（五条路径应为 2 / 4 / 2 / 4 / 2）。这套断言同时充当数据库结构的回归测试，库结构变动时能立刻发现。

**接口层用自动生成的 OpenAPI schema 与前端 TypeScript 类型逐字段比对。** 这个比对是机械的，因为前端类型保留了后端的蛇形字段名，任何一处改名都会直接暴露而不需要经过命名转换。比对之后对每个接口取一条真实记录，人工核对响应中的数值与直接查询的结果一致；其中由服务端计算的两项——综合分与安全判定——必须能用独立计算复现，前者可以靠响应里返回的分量值、权重与乘数手工复算，后者可以靠逐门的实测值与阈值复算。

**界面层是启动后端与前端后逐页走查。** 落地页看统计数字是否与接口一致；肽库看列表字段、筛选与展开是否都取到真实数据；构建器要重点确认每一次选择是否真的进入了结果——路径与方向决定候选集合与排序，骨架与连接片段决定装配出的序列而不改变候选集合，这一处曾经出过选择完全不进入结果的缺陷；结果页看九项分数、安全裁决与序列分段是否齐全；骨架详情页看字段填充情况，特别是那些声明齐全但在数据集里不存在的字段是否被列进「不可用」提示区，而不是渲染成空白卡片。

**改动后的最小自检顺序**：先访问健康检查确认数据库连通与库名正确；再取一次参考数据，确认方向计数为 170 / 65 / 154 / 107 且状态为两个 `ready`、两个 `wip`；然后取一条构造详情，确认九项分数、五条路径的综合分、安全门明细、三段序列片段齐全；最后打开前端逐页走查。

## 十、已知的实现不一致与遗留点

以下几处是当前代码里确实存在的问题，记录在此以免后续被当成正确实现来模仿。

**一处死代码且取值有误。** `app/repositories/enrichment.py` 里的 `FUNCTIONAL_SCORE_BY_DIRECTION` 常量没有任何引用点，且其中两个取值与真正生效的实现不一致：它把抗菌方向的功能分键写成 `imfp_lg_AMP`（实际是 `amp-esm`），把抗黑素方向的语义写成 `probability`（实际是 `ranking_only`）。服务实际使用的是 `app/services/scoring.py` 里的 `FUNCTIONAL_SCORE`，已与运行中的响应逐方向核对一致。这个残留常量正是分层约束想要避免的重复定义，应当在后续改动中清除。

**展示元数据与实际评分键不一致。** `app/services/reference.py` 的 `DIRECTION_META` 里，抗菌方向的功能预测器写的是「iMFP-LG 的 AMP 通道，用 AMPlify-ESM 交叉核对」，而实际参与排名与展示的功能分键是 `amp-esm`，展示名为 AMPlify。方向的展示描述与实际口径不符，需要统一。

**两套类型定义并存。** `app/models/common.py` 的注释提到字段名与 `app/src/types/index.ts` 一致，但前端现有的类型定义在 `app/src/api/types.ts`，旧路径已随静态数据层一并删除，注释所指的位置已经不存在。

**前端的遗留点。** 构建器原先是取回该方向的构造列表在浏览器内按综合分排序、不发计算请求，现已改为调用 `/api/build`，排序与统计都在服务端完成，这一步的输出是每条候选装配好的融合序列。仍在的两处是：肽库浏览器没有搜索框与排序控件，列表的「显示更多」只增加单次请求条数而不做真正的分页（偏移量恒为零）；应用没有兜底路由，访问不存在的路径会落到空白页。工程里另有两个不再被渲染的文件，其中 `App.css` 全工程无引用点。

**一个组件在渲染过程中被定义。** `LibraryPage.tsx` 在自己的选项组件内部取图标组件，静态检查把它标为「在渲染过程中创建组件」。它不持有状态，因此当前没有可观察的后果；真正的代价是每次渲染都会得到一个新的组件身份，一旦将来持有状态就会被重置。修法是把图标解析移到模块层级。构建器的面包屑原先也是这种写法，已改为普通函数调用。

## 十一、本地回退数据源

远端数据库是一台在工作站上、经由隧道访问的实例，该工作站不总是开着。数据库不可达时整个服务连同界面一起失效，恰好是开发最需要它可用的时候。为此服务增加了一层本地回退：`app/sqlite_backend.py` 用一个小型 SQLite 文件承担同样的查询，仓储层不作复制，只把仓储实际用到的 Postgres 构造逐条翻译成 SQLite 等价写法。

回退由配置项 `IGEM_DB_BACKEND` 控制，取三个值。`auto` 是默认值：服务在首次取数前对远端做一次探测，探测失败即改用本地库并把失败原因记下来。`postgres` 只连远端、永不回退，部署时使用，避免数据库故障被悄悄掩盖。`sqlite` 只读本地库、完全不碰远端，测试与离线开发使用。运行中途连接断开的情况也被覆盖：首次探测成功之后连接失效，同样会切到本地库，切回远端需要重启进程。

本地库由 `service/local/fixture_local.sql` 生成，文件缺失时服务按需构建，也可以手动重建，命令是 `python service/scripts/build_local_db.py --force`。它装的是四条手工构造，用途是让各条代码分支在同一次运行里都可到达。`con_9001` 的骨架绑定是占位值，不得输出融合序列；`con_9002` 的骨架绑定带真实序列，必须输出完整融合序列（骨架 + 连接片段 + 功能肽）；这两条同时让综合分权重池有两条观测可取离散度。`con_9003` 与 `con_9004` 补上第二个方向，其中 `con_9004` 落在底部通道，用于验证构建器只排 `top` 候选；抗菌方向只有一条 `top` 记录，因此它的综合分**按预期为空**，构建器的空值排序顺带被覆盖。`con_9003` 还记录了样例表的第二条连接片段，与另外三条不同，这样「不指定连接片段时各行回落到自己的存档值」是一个可断言的事实而不是一句说明。连接片段库另放三条策展条目，其中一条长度 15，与样例表两条的 5 都不同——不指定与指定的差别因此可以用算术判断，而不只是靠字母区分。夹具里任何一条声明的长度都与它旁边的序列一致——声明的长度与自身序列不符会成为一个陷阱，所有针对它写下的算术断言都会为一个看起来像代码缺陷的原因失败。**这四条构造是夹具数据，不是管线产出，不得当作结果引用。**

回退从不静默发生。服务启动时会打印一条警告，`/api/health` 的 `database.backend` 字段说明当前由哪一侧供数，取 `sqlite` 时另给 `database.fallback_reason` 与一段说明，且 `database.server` 会显示 SQLite 版本而不是 PostgreSQL 版本。判断一个环境在跑真实数据还是夹具数据，读这几个字段即可，不要从数值反推——第六节的各项数字断言，以及第九节「最小自检顺序」里的方向计数，都只对远端库成立。

`service/tests/` 下的三个测试文件在夹具上跑通全部只读端点、构建端点与对话端点，运行方式是 `python -m pytest service/tests`。`test_sqlite_dialect.py` 逐个断言方言翻译的每一种构造，因此仓储里新增一条 SQLite 无法翻译的写法会在此处失败，而不是在运行时的某个接口上。`test_local_backend.py` 通过真实的 FastAPI 应用驱动真实的仓储与服务，只更换数据库引擎，其中两条构造分别断言 `placeholder` 与 `verified` 两条绑定路径；另有断言覆盖构造详情按显式连接片段装配，因为构建器的结果卡片会带着自己用的那条链接到详情页，详情页若忽略该参数就会对同一条候选显示另一条融合序列而不作说明。`test_build.py` 断言构建端点那几条组合决定本身：候选只来自 `top` 通道、排序覆盖整个匹配之后才按 `limit` 切片、每行的绑定状态确实反映了这一次装配用了什么，以及指名连接片段只改序列而**候选集合、分数与排名逐项不变**。

前端另有一个不依赖浏览器的走查脚本 `app/verify/builder-build-check.mjs`。它在 jsdom 里渲染真实的 `App`，用真实的点击走过构建器五步，并把应用的相对 `/api` 请求指向真正运行中的服务——因此断言的是真实响应被组件渲染出来的样子，而不是一份为了让断言通过而写的数据。它需要 `jsdom`，而前端目前没有声明测试工具链，所以依赖以 `npm install --no-save --no-package-lock jsdom` 临时装入；若该脚本今后要长期保留，应当进入 `devDependencies` 并配一条 npm script。它只能回答与逻辑和标记有关的问题，jsdom 没有布局，位置与尺寸它答不了。

本轮同时修正了两处实现缺陷，与骨架绑定无关但同属「声明与实现不一致」。其一，**未指定路径时免疫原性门被整条跳过**：安全裁决原先直接接收请求里的路径参数，该参数为空时按路径取值的免疫原性门不会被加入门列表，于是响应回到 `clear`，而未评估的免疫原性既不在门列表里也不在 `unassessed` 里，读起来像是通过了。综合分一直有「未指定则取第一条路径」的默认，安全裁决没有，两者现已统一到同一默认。其二，**连接片段详情拿不到单元构成**：`LinkerDetail` 声明并渲染 `unit_composition` 与 `priority_reason`，而查询它们的语句从未选出这两列，因此每个连接片段详情都返回空的单元构成。列出该两列之后，`unit_composition` 在 Postgres 侧是 `jsonb`、在 SQLite 侧是 JSON 文本，回退层统一解码为对象，两侧行为一致。
