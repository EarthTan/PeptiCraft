# 06 上线进度与后续工作

本篇记录项目从「依赖远程数据库的动态服务」转为「静态部署加边缘函数」的完成情况，以及从当前状态到正式上线之间剩余的工作。它写给需要判断「现在能不能上线、还差什么、差的东西谁来补」的读者，不重复其他五份里已有的产品设计与技术细节，只在需要判断的地方点到为止。

## 一、这一轮做了什么

项目的部署形态在本轮发生了一次根本改变。此前必须有一个 Python 服务常驻运行，服务连到一台学校工作站的 PostgreSQL，接口的每一次调用都要穿过到那台机器的网络。这条依赖链已经不可用——那台机器是学校资产，不受项目控制，且已离线。因此改造的目标是让项目在**没有任何后端进程、也不访问任何数据库**的条件下完整运行，把原来由服务在运行时计算的部分全部前移到一次性的导出环节。

改造后的形态是：数据在部署前一次性导出为静态文件，前端直接读取这些文件；只有聊天一项因为要处理用户的自由提问而无法预先生成，它由部署平台上的一个边缘函数转发给大模型，模型密钥只存在于该函数的环境变量里，浏览器接触不到。

这个方向的选择有一个前提值得说明清楚。导出的产物不是把数据库里的表原样转成 JSON，而是**调用后端服务自己的接口函数、让它们返回什么就存什么**。原因是这个项目里每一个阈值、权重与判定都集中在服务层一处，2026 年 9 月 17 日的审查记录过同一份安全阈值被抄写过四份、其中一份与路径定义冲突而使一条压在收紧阈值上的构造被显示为通过全部检查。如果导出脚本绕过服务层直接写 SQL 自行拼装，那就是同一处缺陷的第五份副本，并且会以静默的方式上线。因此导出的每一个字节都是服务自己的输出，静态文件与接口响应逐字节相同，这是这套文件可信到可以对外发布的唯一依据。

## 二、当前状态

三件事已经完成并通过验证。

**数据导出**。脚本位于 `service/scripts/export_static.py`，产出七十余个文件，覆盖参考数据、全部构造的列表行与详情、每条构造在五条应用路径下的解读文本、骨架与连接片段两库、以及构建器所需的候选排序。体积估算按真实库规模推算约 8.5 MB、约一千五百个文件，相对 Cloudflare Pages 免费额度的两万文件上限占约百分之八，单个文件最大约十 KB，远低于二十五 MB 的单文件限制。

**前端直读静态文件**。新增的数据层与既有的取数层并行工作，二者由同一个入口分派，五个页面的代码没有任何改动。这套数据层在设计上有一条硬约束：**不在浏览器里复制任何阈值、权重或判定**。它只做两件事，从已排好序的列表里取出一页，以及把三段已经导出的氨基酸序列拼接成融合序列。前者不含口径，后者是字符串连接、不含任何判定。综合分随应用路径变化、安全判定随路径的免疫原性门槛变化，因此这两者在导出时按路径各算一遍落盘，而不是在浏览器里重算。

**大模型接入**。模型被给定一条构造的完整记录并被要求解释它，而不被要求产出任何数字。这条规则由三层机制保证：给模型的记录用文字写成而非原始 JSON，因为模型会把 JSON 里的空值读成「缺数据」，却会把数字 0 读成「分数是零」——后者是一个虚假断言，而「未评估」与「零」的区别正是九项分数契约存在的理由；六条禁令写进系统提示词；任何失败——未配置密钥、超时、空回复、报错——都降级回原有的确定性回答，并在响应里如实标注是模板而非模型。原有的六段固定解读文本继续走模板，因为它们不是提问而是每条构造都值得说的固定内容，让模型每次措辞不同会使同一构造在两个读者面前出现不同结论。

部署配置、缓存策略、单页路由回退与部署文档已就绪。

## 三、这一轮修正的三处缺陷

这三处是在自查与复核中发现并修复的，记在这里是因为它们都属于「看起来没问题、实际会出错」的类型，且各自的成因都与部署形态的改变直接相关。

**静态文件会静默遮蔽真实服务。** 导出目录放在前端的资源目录下，而开发环境的构建工具会把一切静态文件优先于代理返回。因此开发者在本地看到的是上一次导出留下的快照，而不是正在运行的数据库的当前内容；更严重的情形是，一个配置了远端接口地址的正式构建也会被快照遮蔽，而界面无从察觉。修法是引入一个开关，其判定顺序为：显式设置优先，其次是配置了远端接口地址时静态层让位，最后才是按是否为开发环境判断。这样开发期走的仍是真实服务，需要验证静态路径时可以用环境变量显式打开。

**导出记录的缺项与搜索口径不一致。** 构造列表的搜索覆盖四列——肽序列、来源、登录号与来源版本——但导出的列表行原本只带序列。后果是在部署后的站点上按登录号搜索，服务端会返回若干行而静态站点返回零行，且两个答案单独看都不像是错的。现在列表行补齐了这三列，并有测试守��这条契约。

**数字在两条路径上的写法不同。** 服务端用 Python 的格式串输出事实块里的每一个数字，边缘函数用 JavaScript 输出同一批数字。两者的舍入相同，但记数法在两个位置不同：Python 在小于 1e-4 或大于等于 1e6 时切换到科学记数法，JavaScript 自身的默认转换不在这些位置切换。后果是模型引用的某个数字在页面上找不到——而「模型引用的每个数字都能在页面上找到」正是事实块存在的唯一理由。修法是边缘函数显式实现与 Python 相同的记数法规则，并把两边的输出都对同一张用例表校验。用例表刻意包含两种记数法各自的区间，因为在固定记数法范围内写错的记数法切换不会在任何检查里暴露。

另有一处修正属于同一类：查询参数里只指定了连接片段而未指定骨架时，静态层需要回落到该构造存档记录的那一条，否则序列级别的分歧不会被察觉——夹具上表现为五十九 aa 与五十四 aa 的差别。

## 四、验证方式

三套检查，全部离线运行，不需要数据库也不需要服务常驻。

后端测试共 115 项，其中 113 项通过、2 项跳过。两项跳过的原因是夹具数据恰好不满足被测条件——其中一项需要一条排名字段为空的记录，而夹具四条构造全部有排名——属于测试前提而非缺陷。前端的类型检查覆盖三个项目，新增的第三个项目专门覆盖边缘函数：该文件是仓库中唯一在生产环境运行、却不在浏览器里运行的 TypeScript，此前从未被构建流程检查过。

静态数据层的走查共 82 项断言，全部通过，且不需要任何后端在运行。这一套针对的是既有两条走查都覆盖不到的地方：它们都假设有服务可用，而静态部署没有服务。走查以 HTTP 方式提供导出目录，用前端自己的数据层读取，其中一项断言把界面拼接出的序列与服务端产出的样例逐个氨基酸残基比对，确保静态层与服务层拼出完全相同的结果；另一项确认页面的每一次读取都来自文件，一旦有任何一次落到网络上即判定失败。

## 五、上线前必须完成的三件事

**第一件是数据导出，且不能用替代品顶替。** 导出目录里必须是由管线 496 条产出生成的静态文件，而不是四条手工构造的演示数据：导出脚本在以演示数据为源时默认拒绝导出，需要显式加参数才会继续，而界面上的数据源横幅读的是导出产物里记录的来源字段，读出 `sqlite` 时会声明当前展示的是样例而非结果，并且不提供重试按钮——静态文件不会在运行中改变，重试在这里会是一个假的承诺。这一步已经完成：2026-10-15 在本机数据库上导出，`manifest.json` 记录的来源字段为 `postgres`，产出覆盖 496 条构造、8 个蛋白簇的骨架库与 15 条连接片段，并且已随仓库入库，队友 clone 之后不必自己做一遍导出。数据若再发生变化，重新执行：

```
cd service && python scripts/export_static.py --out ../app/public/data
```

然后核对它打印的文件数与体积，以及 `manifest.json` 里记录的来源字段是否为 `postgres`。这一步同时会第一次在真实数据上验证导出耗时——数百条构造、每条要按五条路径算综合分与安全判定，可能需要数分钟。

**第二件是配置模型密钥并实跑一次。** 边缘函数需要三个环境变量：接口地址、密钥、模型名。三者都应在部署平台的环境变量设置中配置，其中密钥绝不能进入版本库。不配置也能完整上线，聊天会退化为模板回答并在界面上如实标注，这是一个受支持的部署状态而非故障。配置之后应当实跑一轮，确认回答里引用的数字与页面上显示的一致，并确认超时或报错时降级路径工作正常。目前的三层测试全部使用注入的调用方式、不发真实网络请求，因此真实链路的端到端行为尚未验证。

**第三件是连接片段库缺少应用路径维度。** 策展库十五条每条带名称、序列、刚度等级、复合单元构成与文献出处，但**没有一条标注它适用于哪条应用路径**，而骨架库有这一维度。后果是界面上选择某条连接片段时，系统无法把它收窄到当前应用路径，与骨架库的行为不一致；构建器因此在五条路径上给出同一份连接片段列表。补法需要为十五条逐条判定适用的路径，这需要按用途而非按结构判断，因此应由团队完成而不是由实现推断。此外值得一并确认的是这十五条策展条目的原始出处——它们是从产品设计稿的数据源落库的，而该设计稿随前端静态数据层一并删除后已不在仓库里，库中现存条目是唯一存世副本。

## 六、上线之后的边界

有几件事部署形态决定它们不再随运行时变化，需要在使用时知情。

数据是快照。站点上的每一个数字都来自导出那一刻的数据库，不会自己更新。数据库里新增了构造之后需要重新跑一次导出并重新部署。这不是缺陷而是这个形态的定义，但它意味着「数据是不是最新的」这个问题在上线后由「什么时候重新导出」回答，而不是由系统自动保证。

重跑预测不在系统能力范围内。分数是管线离线算好落库的死数据，任何一项预测工具的重新运行都属于管线侧的工作，不是部署或界面的事。

会话历史有上界。界面把整个对话记录发给后端，只有最近若干轮会到达模型。这是为了避免一次请求携带无限文本，代价是读者问了很多轮之后，模型可能已经想不起最早问过什么。这个取舍是合理的，但读者应当知道。

聊天端点目前没有鉴权也没有限流。问题长度与单条消息长度都有上限，但请求频率没有限制。这一点应当在部署平台的控制台里配置，而不是依赖应用层防护。

## 七、需要团队决定的事项

以下几项不是技术选型，而是需要有人拍板的产品与口径决定。它们在上一轮就已记录，部署形态的改变没有解决其中任何一项。

构造到骨架的绑定规则是其中最实质的一处。496 条构造的骨架外键全部指向一条占位记录，其序列是一个标记字符串，长度为零，因此目前无法为任何构造输出真实的融合序列。真正的骨架在策展库里，与构造表用的是两套互不相通的标识体系，名字也不重叠。要打通需要决定「哪个功能方向配哪条骨架」这条规则，而这条规则属于产品判断，不属于实现。

其余几项：抗炎与抗黑素两个方向数据齐备但状态未签字，在界面上是显著标记还是默认隐藏；综合分的权重口径需要与管线维护方对齐；否决门是三项还是四项；免疫原性的两条通路是否合并、按什么规则合并；材料形态的人工归类逐条确认。

## 八、本篇的核实方式

文中每一个数字都来自实际执行而非估计：文件数与体积来自以演示数据实跑导出的结果再按真实库规模换算，测试项数来自测试运行输出，断言数来自走查输出，额度占用按 Cloudflare Pages 公布的免费额度与实测文件体积计算。

一项未能核实：导出脚本尚未在真实库上运行过，因此真实数据下的导出耗时、以及真实库中是否存在会触发脚本失败的边界数据（例如超长序列、缺失的来源字段），都还未知。这一项在真实数据导出时一并确认。
