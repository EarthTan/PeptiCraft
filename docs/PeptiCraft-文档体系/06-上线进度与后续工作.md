# 06 Release Progress and Remaining Work

This document records the completion status of the project's conversion from "a dynamic service depending on a remote database" to "static deployment plus edge function", and the work remaining between the current state and formal release. It is written for readers who need to judge "whether it can go live now, what is still missing, and who will supply what is missing"; it does not repeat the product design and technical detail already contained in the other five documents, touching on them only where a judgement needs them.

## 1. What This Round Did

The project's deployment form underwent a fundamental change in this round. Previously a Python service had to run continuously, the service connected to the PostgreSQL on a school workstation, and every call to the API had to cross the network to that machine. This dependency chain is no longer available — the machine is school property, not under the project's control, and is offline. The goal of the conversion was therefore to make the project run completely under the conditions of **no backend process and no database access**, moving everything the service used to compute at runtime forward into a one-time export step.

The converted form is as follows: data is exported once as static files before deployment, and the frontend reads those files directly; only chat cannot be pre-generated, because it has to handle the user's free-form questions, and it is forwarded to a large model by an edge function on the deployment platform, with the model key existing only in that function's environment variables and never reachable by the browser.

The choice of this direction has one premise worth stating clearly. The exported artefacts are not the database tables converted to JSON as they stand; rather, **the backend service's own API functions are called, and whatever they return is stored**. The reason is that in this project every threshold, weight and judgement is concentrated in one place in the service layer, and the review of 17/9/2026 recorded the same safety threshold being copied in four places, one of which conflicted with the route definition and caused a construct resting on a tightened threshold to be displayed as passing all checks. If the export script bypassed the service layer and wrote SQL to assemble the output itself, that would be the fifth copy of the same defect, and it would go live silently. Therefore every byte exported is the service's own output, and the static files are byte-for-byte identical to the API responses, which is the sole basis on which this set of files is trustworthy enough to be published externally.

## 2. Current State

Three things are complete and verified.

**Data export.** The script is located at `service/scripts/export_static.py` and produces more than seventy files, covering reference data, the list rows and details of all constructs, the interpretive text for each construct under the five application routes, both libraries of scaffolds and linkers, and the candidate ranking required by the builder. The size estimate, scaled from the real library's size, is about 8.5 MB in about 1,500 files, roughly eight percent of Cloudflare Pages' free-tier limit of twenty thousand files, with the largest single file at about ten KB, far below the twenty-five MB per-file limit.

**The frontend reads static files directly.** The new data layer works in parallel with the existing data-access layer, the two are dispatched by the same entry point, and the code of the five pages was not changed at all. This data layer has one hard constraint in its design: **it replicates no threshold, weight or judgement in the browser**. It does only two things: take one page from a list that is already ordered, and concatenate three already-exported amino-acid sequences into a fusion sequence. The former contains no scheme; the latter is string concatenation and contains no judgement. The composite score changes with the application route and the safety verdict changes with the route's immunogenicity threshold, so both are computed once per route at export time and written to disk, rather than recomputed in the browser.

**Large-model integration.** The model is given a construct's complete record and asked to explain it, and is not asked to produce any number. This rule is ensured by three layers of mechanism: the record given to the model is written in words rather than as raw JSON, because the model would read a null in JSON as "missing data" but would read the number 0 as "the score is zero" — the latter is a false assertion, and the distinction between "not assessed" and "zero" is exactly the reason the nine-score contract exists; six prohibitions are written into the system prompt; and any failure — no key configured, timeout, empty reply, error — degrades to the original deterministic answer, with the response honestly marked as a template rather than the model. The original six fixed sections of interpretive text continue to go through the template, because they are not questions but fixed content worth saying about every construct, and making the model phrase them differently each time would give two readers different conclusions about the same construct.

Deployment configuration, caching strategy, single-page route fallback and deployment documentation are in place.

## 3. The Three Defects Fixed in This Round

These three were found and fixed during self-check and review, and are recorded here because they all belong to the type "looks fine, actually goes wrong", and the cause of each is directly related to the change in deployment form.

**Static files silently mask the real service.** The export directory sits under the frontend's asset directory, and the development environment's build tool returns all static files in preference to the proxy. So what a developer sees locally is the snapshot left by the previous export rather than the current content of the running database; more seriously, a formal build configured with a remote API address is also masked by the snapshot, and the interface has no way to notice. The fix was to introduce a switch whose decision order is: an explicit setting takes precedence, then when a remote API address is configured the static layer gives way, and only then the decision is made by whether this is a development environment. In this way the development period still goes through the real service, and the static path can be turned on explicitly with an environment variable when it needs to be verified.

**Exported records are missing items that the search covers.** The construct list's search covers four columns — peptide sequence, source, accession number and source version — but the exported list rows originally carried only the sequence. The consequence was that, on the deployed site, searching by accession number returned several rows from the server but zero rows from the static site, and neither answer looked wrong on its own. The list rows now include these three columns, and a test guards this contract.

**Numbers are written differently on the two paths.** The server uses Python's format strings to output every number in the fact block, and the edge function uses JavaScript to output the same batch of numbers. The rounding is the same, but the notation differs at two points: Python switches to scientific notation when the value is below 1e-4 or at least 1e6, whereas JavaScript's own default conversion does not switch at these points. The consequence is that a number the model cites cannot be found on the page — and "every number the model cites can be found on the page" is precisely the only reason the fact block exists. The fix is for the edge function to implement explicitly the same notation rules as Python, and to validate both outputs against the same case table. The case table deliberately includes the intervals of each of the two notations, because a wrong notation switch written inside the fixed-notation range would not be exposed by any check.

One further fix belongs to the same class: when the query parameters specify only a linker and no scaffold, the static layer needs to fall back to the one on the construct's archived record, otherwise a sequence-level discrepancy goes unnoticed — on the fixture it appears as a difference between fifty-nine aa and fifty-four aa.

## 4. Verification Approach

Three suites of checks, all run offline, requiring neither a database nor a resident service.

The backend tests number 115 in total, of which 113 pass and 2 are skipped. The two are skipped because the fixture data happens not to satisfy the condition under test — one of them needs a record whose ranking field is empty, and all four fixture constructs have a ranking — which is a test precondition rather than a defect. The frontend type check covers three projects, and the newly added third project specifically covers the edge function: that file is the only TypeScript in the repository that runs in the production environment but not in the browser, and it had never been checked by the build process before.

The static data layer walkthrough has 82 assertions in total, all passing, and needs no backend running. This suite targets what neither of the existing two walkthroughs can cover: both assume that a service is available, whereas a static deployment has no service. The walkthrough serves the export directory over HTTP and reads it with the frontend's own data layer; one assertion compares the sequence assembled by the interface with the sample produced by the server residue by residue, ensuring that the static layer and the service layer assemble exactly the same result; another confirms that every read by the page comes from a file, failing as soon as any one of them goes to the network.

## 5. Three Things That Must Be Completed Before Release

**The first is the data export, and no substitute may take its place.** The export directory must contain static files generated from the pipeline's 496 outputs, not the four hand-built demonstration constructs: the export script refuses to export by default when the source is demonstration data, requiring an explicit parameter to proceed, while the data-source banner in the interface reads the source field recorded in the export artefacts and, on reading `sqlite`, declares that what is displayed is samples rather than results, and offers no retry button — static files do not change while running, and a retry here would be a false promise. This step is already complete: exported on 2026-10-15 against the local database, with the source field recorded in `manifest.json` as `postgres`, the output covering 496 constructs, a scaffold library of 8 protein clusters and 15 linkers, and already committed to the repository, so a teammate who clones it need not perform the export again. If the data changes again, re-run:

```
cd service && python scripts/export_static.py --out ../app/public/data
```

Then check the file count and size it prints, and whether the source field recorded in `manifest.json` is `postgres`. This step will also, for the first time, verify the export duration on real data — several hundred constructs, each requiring the composite score and safety verdict to be computed for five routes, may take several minutes.

**The second is to configure the model key and run it once for real.** The edge function needs three environment variables: the API address, the key and the model name. All three should be configured in the deployment platform's environment variable settings, and the key must never enter the version repository. A complete release is possible without configuration: chat degrades to template answers, honestly marked in the interface, and this is a supported deployment state rather than a failure. After configuration, one round should be run for real, confirming that the numbers cited in the answers agree with those displayed on the page, and that the degradation path works on timeout or error. The current three layers of testing all use injected calls and issue no real network requests, so the end-to-end behaviour of the real chain has not yet been verified.

**The third is that the linker library lacks the application route dimension.** Each of the fifteen curated entries carries a name, a sequence, a rigidity tier, a composite unit composition and a literature source, but **not one of them marks which application route it applies to**, whereas the scaffold library has this dimension. The consequence is that when a linker is selected in the interface, the system cannot narrow it to the current application route, which is inconsistent with the scaffold library's behaviour; the builder therefore presents the same linker list on all five routes. The remedy requires deciding, for each of the fifteen, the applicable route, which requires judging by use rather than by structure and should therefore be done by the team rather than inferred by the implementation. In addition, it is worth confirming together the original provenance of these fifteen curated entries — they were loaded into the library from the data source of a product design draft, and that draft, deleted along with the frontend's static data layer, is no longer in the repository; the entries now in the library are the only surviving copy.

## 6. Boundaries After Release

Several things, by the nature of the deployment form, no longer change with runtime, and must be known when the platform is used.

Data is a snapshot. Every number on the site comes from the database at the moment of export and does not update itself. After constructs are added to the database, the export must be run once more and the site redeployed. This is not a defect but the definition of this form, yet it means that the question "is the data up to date" is answered after release by "when was it last re-exported" rather than guaranteed automatically by the system.

Re-running predictions is outside the system's capabilities. The scores are dead data computed offline by the pipeline and stored in the library; re-running any prediction tool is work on the pipeline side, not a matter for deployment or the interface.

Session history has an upper bound. The interface sends the entire conversation record to the backend, but only the most recent several turns reach the model. This is to avoid carrying unbounded text in a single request, at the cost that after a reader has asked many turns, the model may no longer recall what was asked earliest. This trade-off is reasonable, but the reader should know it.

The chat endpoint currently has neither authentication nor rate limiting. There are upper limits on question length and on single-message length, but no limit on request frequency. This should be configured in the deployment platform's console rather than relying on application-layer protection.

## 7. Matters Requiring a Team Decision

The following are not technical choices but product and scheme decisions that need someone to decide. They were recorded in the previous round, and the change in deployment form has not resolved any of them.

The rule binding constructs to scaffolds is the most substantive of these. The scaffold foreign keys of all 496 constructs point to one placeholder record whose sequence is a marker string of length zero, so at present no construct can be given a real fusion sequence. The real scaffolds are in the curated library, which uses a different and unconnected identifier system from the construct table, with no overlap in names either. Connecting them requires deciding the rule "which functional direction goes with which scaffold", and that rule is a product judgement rather than an implementation one.

The remaining items: whether the anti-inflammatory and anti-melanogenic directions, whose data is complete but whose status is not signed off, should be prominently marked in the interface or hidden by default; the weight scheme of the composite score needs to be aligned with the pipeline maintainers; whether the veto gates are three or four; whether the two immunogenicity pathways should be merged and by what rule they are merged; and the manual classification of material forms confirmed entry by entry.

## 8. How This Document Was Verified

Every number in this text comes from actual execution rather than estimation: the file count and size come from an actual export run on demonstration data and then scaled to the real library's size, the test counts come from test run output, the assertion counts come from walkthrough output, and the quota usage is calculated from Cloudflare Pages' published free quota and the measured file sizes.

One item could not be verified: the export script has not yet been run against the real library, so the export duration under real data, and whether the real library contains boundary data that would make the script fail (such as over-long sequences or missing source fields), are both still unknown. This item will be confirmed together with the real-data export.
