# Software

## PeptiCraft Platform

### Intro

PeptiCraft is a web platform for designing recombinant fusion proteins. A candidate molecule is three segments joined in order: a functional peptide that carries the biological activity, a scaffold protein that supplies the mechanical and material properties, and a short linker that holds the two apart so each folds correctly. The platform exists because those three are usually chosen separately, each by a different tool with its own input format, its own output scale and its own threshold, and because the choice of one segment changes what the other two should be. A different peptide alters the hydrophobicity and charge of the whole fusion protein and therefore its aggregation tendency; a different scaffold changes the chemical environment the peptide sits in and therefore its apparent activity; a different linker changes the relative orientation of the two ends. This is a joint selection problem over a combinatorial space, not three independent optimisations.

The platform reduces that space to something a team without protein-engineering training can act on. It holds a pre-computed library of 20,248,885 peptides of 1 to 30 residues, scores from twelve predictive tools covering that library completely, and 496 assembled constructs that survived a four-round selection pipeline. The user states what product form they are trying to make; the platform derives which scaffold fits that form, which linker suits the design, and returns ranked candidates with a safety verdict, a composite score, the full fusion sequence and a per-candidate explanation of where each number came from. Nothing is predicted at request time. Every figure on screen was computed offline, stored, and is read back with the threshold and provenance attached.

The design premise worth stating early is that safety is not a score. Peptide toxicity, haemolysis and immunogenicity are evaluated as hard veto gates: a candidate that exceeds any one of them is removed and does not participate in any weighted compensation. The alternative convention — folding safety into a weighted total so that a strong antioxidant score can offset a haemolysis signal — keeps candidates in the list whose real problems only surface after several weeks of wet-lab work. Three further premises follow from the same reasoning: a metric that was never evaluated is reported as not assessed rather than as a pass or as a zero; a score that can only be read as a ranking is never presented as a probability; and the route a product will be used on changes the screening, because the same candidate can be acceptable under one route and vetoed under another.

### User need / use case

The users this platform is built for share one trait: the product form is clear and the protein-engineering capability is absent. Three groups motivated the design. Student and competition teams have a defined theme and a delivery deadline, need a real candidate they can discuss in a few weeks, and have no compute capacity to run eighteen predictors themselves. Early-stage researchers have already chosen an application direction and need a defensible shortlist before committing experiments, which makes them care about traceability and transparent parameters rather than about the number of tools. Independent formulators and small brands already hold a product form — a mask, a serum, a hair treatment, an injectable filler — and need to add a functional ingredient in a way that can be defended, on a budget that does not stretch to a full computational and verification cycle.

The concrete failure this addresses is fragmentation. Designing one functional peptide means facing, simultaneously and independently, an antioxidant predictor, a toxicity predictor, a haemolysis predictor, an immunogenicity predictor, a thermal-stability predictor, a soluble-expression predictor and a cell-penetration predictor. Each takes a different input format, returns a number on a different scale, and applies a different decision boundary. Using them together means writing the glue yourself and handling the failures that duplicate sequences cause. For a team without a computational background this is already a wall, before any biology is discussed.

A worked example follows a small team building a medical dressing. They want an antioxidant function to address oxidative stress in chronic wounds, and they do not know which peptide to start from or which protein can be spun into a fibrous dressing. They open the Builder and select the wound-dressing route. Two things happen automatically: the delivery mode is bound to the route's contact interface and is not something they choose, and the scaffold pool narrows to the four clusters that route admits. The interface also states that this route's immunogenicity gate is tightened to 0.35 against 0.50 for the mask and topical routes, because a breached barrier puts the construct in direct contact with tissue fluid and that is the same exposure band as injection rather than the intact-skin band. They select the antioxidant direction, confirm one of the four scaffolds, choose a linker, and request the build. The response returns candidates ranked by composite score under that route, each carrying its assembled fusion sequence, plus counts of how many candidates cleared every gate, how many sit within 10% of a boundary, and how many were vetoed — counted over the whole matched set rather than over the page displayed. Opening one candidate shows the safety verdict first, then the nine scores against their thresholds, then the sequence in three colour-coded segments, then six generated paragraphs covering expression strategy and risk. From the sidebar any single number can be interrogated in natural language against that construct's real data. What leaves the session is a sequence, an expression plan, and a list of experiments that still have to be done.

### Key Features

**Construct Builder.** A five-step guided flow: route, function, scaffold, linker, results. The route determines the scaffold pool, the three weight tiers, the immunogenicity gate and the route's extra non-vetoing checks. Function is a multi-select over the four directions; directions whose status is empty cannot be selected. Scaffold candidates come from the chosen route and can be filtered by material form. Linker candidates carry name, residue length, rigidity class, sequence and literature provenance. The result step issues one real server-side computation and returns candidates ranked by composite score, each assembled with the chosen scaffold and linker, together with the safety-verdict counts. Any candidate links into the result view carrying the pair it was built with, and the pair can be changed there to compare.

**Safety as verdict, not as score.** The safety panel reports per-metric measured value, threshold, direction, whether it was assessed, and whether it is a veto gate, and rolls up to a verdict with four possible values: all gates clear, at least one exceeded, nothing exceeded but at least one within 10% of its boundary, or nothing assessed at all. That last value exists so that an unmeasured gate is never rendered as a pass. Vetoed candidates display the specific metric that failed rather than a generic message, because the three failure modes carry different next steps.

**Composite score recomputed per route.** The composite is a derived ranking value, not a prediction, and it is recomputed for each of the five routes because each route carries a different weighting profile. Every response returns the normalised value of each component, the weight it received, the multiplier it received and the size of the pool the normalisation was computed over, so any composite score can be reproduced by hand from a single response without querying the database or reading the source.

**Honest semantics carried in the response contract.** All nine scores are nullable, and every null is accompanied by a boolean flag saying whether the metric was assessed, so a caller never has to guess whether an absent field means unmeasured or measured-zero. Each score carries a semantics tag distinguishing readable-as-probability from ranking-only, and the tag is present on list rows as well as on detail views, because list rows display the score. Very small non-zero values fall back to significant-figure formatting rather than rounding to `0.00`, which matters for the several hundred values in the cell-penetration and solubility columns that are small but carry signal. The MHC-II gate carries an explicit higher-is-better flag, because it is the one gate whose direction inverts — a low percentile rank means strong binding and therefore higher risk — and any presentation logic that assumes "above the limit means exceeding" states the opposite conclusion on that gate.

**Two assembly targets, reported separately.** The scaffold and the linker can each be specified per request, independently, and either can be omitted, in which case that part falls back to the value stored on the construct row. Neither target changes the candidate set, the ranking or any score; both change only the sequence each candidate is assembled into and the fusion length reported alongside it. Their provenance is reported in two separate notes, because one build can take its scaffold from the request and its linker from the stored row, and a single merged sentence would have to describe a half-stored record.

**Scaffold library with evidence grading.** Eight protein clusters and sixteen patent sequence variants, each with real amino-acid sequences, source patent, applicant, product form, regulatory status and an evidence level graded E1 to E5 — from purified-protein or cell-free work, through cell, animal and controlled clinical work, to regulatory review and post-market safety data. The level records the highest tier that can be verified for the protein, not a completion score, and each record carries an explicit evidence-limitation field for the gap between that tier and the new use. Material form — lyophilised sponge, self-assembled hydrogel, injectable gel, film, fibre, sheet, solution — is presented as a curated extraction rather than a source field, and the interface labels it that way.

**Curated linker library.** Fifteen entries with literature provenance, unit composition and a five-step rigidity scale from fully flexible to fully rigid, exposed alongside a six-row placeholder table so that both sources are distinguishable in every response.

**Evidence-graded generated text.** Six generated blocks per construct — safety reading, functional peptide origin and composition, linker and assembly, expression and handling, comparison within direction, risk list — each carrying a list of the response field paths it cites, and the response carrying a generator marker so template-rendered text is never presented as model output. The chat endpoint and the text blocks share one generator, currently a deterministic template implementation behind a protocol that a language-model implementation can be registered against without touching the routes or the response models.

**Provenance and fallback made visible.** The service is read-only against the database and will fall back to a packaged SQLite fixture when the remote instance is unreachable, which is the normal state of a workstation that is not always powered on. The fallback never happens silently: the health endpoint reports which backend is answering and, when the fixture is answering, why the fallback engaged. A caller who needs to know whether it is looking at real data reads that field.

### Quick Start

PeptiCraft is used from a browser and requires no installation. The whole workflow happens in the Construct Builder, which takes five steps and produces a ranked candidate list with assembled sequences. What follows is the path through it.

**Step 1 — state the product form.** On the landing page, the five application-route cards are the entry point. Choosing one is the single most consequential decision in the workflow, because the route determines the immune-exposure band, the developability weighting, and which scaffolds are available. Wound dressing and injectable filler carry the strictest immunogenicity gate at 0.35, because a breached barrier and a needle both put the construct in direct contact with tissue or with the immune system; mask patch and topical film sit at 0.50; hair care is at 0.60, since the hair shaft is keratinised dead tissue with no blood supply. Selecting a route also narrows the scaffold pool automatically and binds the delivery mode, which is why it is not asked for separately.

**Step 2 — choose what the construct should do.** One or more of the four functional directions can be selected. Each card shows its real construct count and status, and directions with no data are not selectable. The two directions marked work-in-progress are shown rather than hidden, and their functional scores can only be read as rankings, so their candidates are shortlists for wet-lab validation rather than leads.

**Step 3 — confirm the scaffold.** The candidates are the clusters the chosen route admits, and the list can be filtered further by material form — lyophilised sponge, self-assembled hydrogel, injectable gel, film, fibre, sheet or solution formulation. The interface states plainly that this choice does not narrow the candidate peptides, because every stored construct carries a placeholder scaffold binding; what the choice changes is the sequence each candidate is assembled into. The first scaffold under the route is selected by default, so the step can be accepted as it stands.

**Step 4 — choose the linker.** Fifteen curated entries are listed with residue length, rigidity class, sequence and literature provenance. The one meaningful distinction is rigidity: a flexible unit lets the functional peptide swing freely off the scaffold surface, a rigid unit holds it away, and the tradeoff is whether the peptide's active site needs unobstructed access to its target. This choice also does not change the candidate set — it changes the assembled sequence. The library is not currently narrowed by route, so all five routes see the same list, and the interface says so.

**Step 5 — build.** The request returns candidates ranked by composite score under the selected route's weighting, each carrying its full fusion sequence and fusion length, plus counts of how many candidates cleared every gate, how many sit within 10% of a boundary, and how many were vetoed. Those counts cover the entire matched set rather than the page displayed, so they describe the shape of the candidate pool rather than where the page happens to stop. No composite score at all is possible for one direction, because a single observation in a direction's pool gives no spread to weight by; those candidates sort last rather than participating as zeros, which is not the same as scoring low.

**Reading a result.** Opening a candidate brings up four views. The construct view leads with the composite score, the rank and the aggregation propensity, followed by the safety gate panel, then the sequence in three colour-coded segments — scaffold in blue, linker in green, functional peptide in bold orange, with any segment whose sequence is unavailable drawn grey rather than drawn as residues — then a comparison table within the direction and six generated paragraphs covering expression strategy and risk. The peptide view shows the peptide's source, length, all nine tool scores, and locally computed sequence properties: molecular weight, net charge, cysteine count, and aromatic and hydrophobic fractions. The scaffold view shows the current binding alongside the alternatives, and switching between them re-renders the same candidate on a different scaffold instantly. The linker view shows unit composition and literature provenance. A fixed sidebar on the right answers questions against that construct's real numbers — why a score has the value it has, whether the candidate still holds under a different route, or how it compares against others under the current one.

Two further pages are reachable without going through the builder. The library browser holds everything already computed, filterable by direction and by the route a candidate was screened under; expanding a row shows the same safety and score panels the result view uses, which is why the two cannot disagree. A scaffold's own page carries its source patent, its sequence variants, the routes that admit it, its experimental evidence and its regulatory registration status, including an explicit list of fields this dataset does not contain — so an absent field is distinguishable from a broken one.

## Development

### DBTL loop

The platform went through four build-test-learn cycles, each of which changed a structural decision rather than a line of code.

**Cycle one: the static-data layer came out.** The five pages originally rendered a hard-coded dataset, and the engineering description already claimed search, filtering and sorting where only filtering existed. The decision was to delete the static data module and its type definitions outright rather than migrate them, so that no page could quietly keep rendering a constant. Every value on every page now traces to a table column, and the frontend's TypeScript mirror of the backend response models deliberately keeps the backend's snake_case field names so that the OpenAPI schema and the frontend types can be compared field by field mechanically, with no naming-conversion layer in between where a rename could hide.

**Cycle two: thresholds were pulled out of the frontend and into one place.** An audit on 2026-09-17 found three defect classes, all of them the same shape: a value copied into more than one place and then drifting. The safety thresholds had been written twice, once in the library page and once in the results page, under a comment claiming the two shared a definition. The immunogenicity gate had been applied globally at 0.50 while the route definitions specified 0.35, 0.50 and 0.60, so a construct sitting exactly on the tightened boundary was displayed as clearing every gate. The generated prose cited a 0.70 acceptance floor for the antioxidant predictor that existed in no tool metadata, leaving a reader unable to find where the number came from. The response was a hard layering constraint — routers validate and serialise, services hold every threshold and every weight, repositories write SQL and nothing else, models define the contract — plus the rule that the frontend performs no threshold comparison and no weighting at all. Composite scores and safety verdicts arrive computed. A threshold now exists in one place, and changing a convention is a backend change.

**Cycle three: the build moved from the browser to the server.** The Builder originally fetched a direction's construct list and sorted it in the browser. Three properties of the correct answer were being violated by that arrangement: a row's composite score depends only on the weight pool of its own direction, and that pool is read independently of the request and cached per direction, so sorting a page in the browser produces scores that move when the request narrows; ranking has to cover the entire matched set before any slicing, which is what makes an offset meaningful at all; and candidates must come from the top channel only, since the bottom channel is the negative-control arm and mixing it into a candidate list makes both unreadable. With a single server endpoint returning the full ranking, the counts cover the matched set rather than the page, and candidates whose composite cannot be computed sort last rather than participating as zeros. A fourth property came out of the same work: each row carries its own binding status, so a single response can contain rows with a full fusion sequence and rows without one.

**Cycle four: two real inconsistencies were found and fixed.** When no route was specified, the immunogenicity gate was skipped entirely — the safety verdict took the route parameter directly, and with it empty the per-route gate was never added to the gate list, so the response came back `clear` while the unassessed gate appeared in neither the gate list nor the unassessed list, reading as a pass. The composite score had always defaulted to the first route when none was given; the two now share one default. Separately, the linker detail view declared and rendered unit composition and priority reason while the query never selected those two columns, so every linker detail returned an empty composition.

The pattern across all four is the same: each cycle removed a class of defect by changing where a decision lives, rather than by patching the instance that surfaced.

Testing runs in three layers, and a failure in each means something different. Forty-four offline tests run against a packaged SQLite fixture and cover three things: that every PostgreSQL construct the repositories write is translated correctly to SQLite, so a query that cannot be translated fails in the test suite rather than in production; that every endpoint returns correctly when driven through the real application against the fixture; and that the build endpoint's ranking and two assembly targets behave as specified, including the assertion that naming a scaffold or a linker changes the assembled sequence while leaving the candidate set, the scores and the ranking identical item for item. A separate browser-free check renders the real application in jsdom, walks the Builder through its five steps with real clicks, and rewrites the application's relative `/api` requests into absolute ones so that every request goes to the real running service — what it asserts is the real response as the component renders it, not a fixture written to satisfy the assertion. It answers three things: whether the page reaches the final step, whether the assembled sequence reaches the DOM, and whether the labels qualifying it — the scaffold's provenance, the linker's, and the scope of the scores — are the ones the service sent. It does not answer questions about layout, because jsdom has no layout engine. The third layer is a manual page-by-page walkthrough with both processes running, checking that the landing page's counts match the API, that the library's fields and filters are populated from real data, that every Builder choice actually reaches the result, that the result view's nine scores, safety verdict and sequence segments are complete, and that fields the dataset genuinely lacks are listed as unavailable rather than rendered as empty cards.

### Software architecture

The system is three components and one database, with data flowing in one direction. A single-page application built with Vite runs in the browser and communicates only over HTTP against an `/api` prefix, which the dev-server proxy forwards in development and the deployment platform forwards in production, so the frontend contains only relative paths and neither cross-origin configuration nor a backend address is a frontend concern. A FastAPI service is the only component that touches the database; it never writes, and it does not run predictors. It does three things: it shapes remote data into the form the frontend needs, it performs the assembly and adjudication that the pipeline left to a compute service — real scaffold binding, fusion sequence reconstruction, per-route composite recomputation and safety adjudication — and it generates the interpretive text and the dialogue. A PostgreSQL 16.15 instance on an Ubuntu workstation holds the data, reached over the network.

The database sits on the workstation rather than beside the service for two reasons. The two largest tables total roughly 165 GB, which does not belong in a migrating service; and the models that produced the data mostly require GPUs and already run on that workstation, so keeping the database next to the inference avoids moving data back and forth. The cost is that the whole service depends on network reachability to that machine, which is recorded as a risk rather than designed away.

The frontend is five pages over five routes, organised into four responsibilities whose boundaries are themselves a constraint. A data-access layer issues requests and normalises errors, binds each endpoint to a named function, and holds the TypeScript mirror of the backend response models. State and side effects run through two custom hooks, one for loading a resource and one for performing an action. The loading hook carries a ticket counter: each request increments it, and a response whose ticket is no longer current is discarded, which is what prevents a slow early request from overwriting a fast later one when filters are changed quickly. Errors are normalised into distinguishable types so the interface can state an actual cause instead of a generic failure. Shared display components hold the three panels the library and result views have in common — the safety gate list, the tool score grid, the generated text block — and they are shared for a concrete reason: threshold drift originated in two separate implementations of exactly these panels. Presentation-layer mapping translates backend identifiers into interface elements and computes sequence properties locally. There is no state management library; each page owns its data, pages share no mutable state, and route parameters carry what passes between them. One consequence is that the result view's scaffold preview is driven by rewriting a query parameter, so browser back and forward participate in that state.

The backend is four layers with hard constraints between them. Routes validate parameters, call services and serialise; they contain no SQL and no computation. Services hold all thresholds, weights and business judgement, and write no SQL. Repositories contain SQL and row-to-dict conversion only, with no threshold or convention. Models define the response contract, with field names matching the frontend types. The single purpose of these constraints is that every threshold exists in exactly one place.

The connection pool applies two settings to every connection at creation: marked read-only, and a statement timeout. A second group of tuning settings is applied only where it is declared — sequential and bitmap scans off, forcing index use. That group helps on the 378-million-row score table and hurts on the 496-row construct table, where a list query with no filter should go sequential, so the caller declares it per query and everything else is left to the planner.

Error handling separates two failures into different status codes. An unreachable database — network down, authentication failed, connected to the wrong instance — returns 503 rather than 500, because the database is on another machine, unreachability is transient, and a client retry is reasonable; the body carries an error identifier and a troubleshooting note. A failed query returns 500. The split lets the interface state an accurate cause instead of calling everything a server error.

The interface is nineteen endpoints under `/api`: eighteen read-only and one write. Seven serve reference data, including one endpoint that returns directions, routes, tool metadata, evidence levels, material forms and scaffold categories in a single response so a page open does not produce a waterfall of requests. Six serve constructs — a filterable paginated list, a detail view, the scaffolds available for a construct, the per-tool score rows for its peptide, the generated text, and the chat endpoint. One serves the build described above. Three serve scaffolds and two serve linkers, with list and detail deliberately shaped differently: the scaffold list omits sequences and patent variants so that all eight clusters can be returned at once, while the detail includes them. List endpoints uniformly return items plus total, limit and offset, so the interface can show a total without a second counting request.

The data contract carries several decisions that exist to make misreading impossible. Nulls must be flagged: all nine scores are nullable and every null comes with an assessed flag, so a caller never has to distinguish a missing field from a zero value, both of which are null in JSON. The composite travels with its route and stays reproducible: a single response carries a per-route map whose entries include the three modulated component values, the composite, and every intermediate quantity needed to recompute it by hand. The safety conclusion is a structure rather than a sentence, containing the route's immunogenicity gate, an overall verdict, a per-gate array, the list of unassessed gate keys and the list of vetoed gate keys; each gate entry carries metric, tool, measured value, threshold, threshold provenance, pass or fail, borderline flag, veto flag, and which side counts as exceeding — the last field is necessary because MHC-II is the one gate where "higher than the limit" means the opposite. Threshold provenance is explicit and distinguishes three cases with different blast radii: from the tool itself, from the route's screening profile, and from a platform constant. Changing a tool threshold affects every route; changing a route profile affects one route.

### Data source / Model source

Sequence data comes from ten sources recorded in a manifest table that stores, per source, its version date, file checksum, scan start and end times and row count written. By row count the metagenomic source dominates at 19,154,247 sequences, about 94.6% of the library, which is why the typical length in the library is short: metagenomic fragments are already broken. The remaining nine contribute roughly 1.1 million sequences between them, drawn from UniProt, UniRef90, PDB structure chains, Rfam and RNAcentral clusters, BFD, and several older dated snapshots. Peptide lengths in the database run from 1 to 30 residues, and 95% of the library sits in the 20-to-30 band; the distribution is heavily quantised at integer lengths 20 through 30 because that is where the metagenomic bulk lies. A unique constraint on sequence, source and source version prevents duplicate insertion within a source while letting different sources keep their own copies. A secondary attribute table intended to carry parent headers, taxonomy, PDB chain identifiers, reading frame and source file offsets exists but is empty, so those attributes are currently unavailable; this is a known gap rather than a design choice.

The construct layer is a single table of 496 rows and 744 kB, the smallest business table in the database and the one the product reads from. It holds identity and classification, three foreign keys to peptide, scaffold and linker, a JSON field carrying the aggregate of nine scores, a legacy delivery-score field, and three booleans recording whether haemolysis, MHC-I and MHC-II were assessed. The four directions are distributed 170, 65, 154 and 107, and each row is either in the top channel or the bottom channel. The bottom channel is not filler: it holds the lowest-scoring candidates from the same ranking, and it exists to give later rounds a baseline of known-poor activity against which to confirm the scoring system is actually discriminating rather than sorting noise inside a narrow dynamic range. Bottom-channel constructs go through the same safety gates and the same scoring, so their numbers are comparable. The score JSON is heterogeneous by direction, with 26 distinct keys across the table and no row holding all of them: six are shared and the rest are direction-specific, which is a consequence of four directions using four different models on four different scales rather than an incompleteness. Two legacy fields are named misleadingly and are documented as such — the field that looks like a full fusion sequence contains a three-part pipe-delimited label string rather than amino acids, and the delivery-score field uses a four-coordinate axis with no invertible mapping to the five application routes.

The reference layer is small and is the hardest data in the system, because it was compiled by hand from real patent records rather than produced by a predictor. It exists in two parallel granularities. The older three tables are at the level of individual patent records, experimental groups and experiment details; the newer two are at the level of protein clusters with their patent sequence variants beneath them, and only the newer pair carries the five application-tag columns that are the single place in the dataset where the existence of application routes is recorded. The eight clusters cover recombinant human collagen and its tandem-repeat constructs, a triple-helix-mimetic collagen fragment, a recombinant type XVII collagen fragment, a human-like collagen, a short recombinant silk fibroin fragment, a recombinant spider silk protein, and an engineered spider silk variant. Four clusters reach E5, one E4, one E2 and two E1. The connector library has fifteen curated entries with literature provenance against a six-row placeholder table.

Predictive models are not in this repository. The pipeline calls them as local HTTP services on fixed ports on the GPU workstation, and this repository holds the pipeline's schema, run scripts and result files. Eighteen candidate predictors were evaluated; twelve produce scores covering the full library, counting the antioxidant predictor's three heads separately, while the two immunogenicity predictors are length-restricted and cover partially. The largest result table holds about 378 million rows and 130 GB; the MHC-II table, organised by peptide and allele, holds roughly 147.5 million rows across 131 alleles and 35 GB, and is large enough that even counting its rows exceeds the service's query timeout, so row counts are read from statistics rather than computed exactly.

### AI models, training methods, and parameters

The project trains no model of its own. That is a deliberate position and it needs stating plainly, because a wiki page that described training procedures here would be describing work that did not happen. What the project owns is a set of decisions about how eighteen third-party predictors should be used, when to believe them, and what to do when they disagree with each other. Four of those decisions are substantive enough to count as the project's own modelling work.

**Decision one: thresholds are recalibrated against the project's own library rather than inherited.** The toxicity threshold of 0.38 is not the tool's default. The full 20.2-million-peptide library was scored and the score distribution inspected; the tool's own default admits a set of candidates this library does not support, and 0.38 suppresses both false negatives and false positives on this distribution. This is the one threshold in the system that is a project decision rather than a tool recommendation or a route convention, and it is written into the predictor's own detail record so that it travels with the data. Haemolysis sits at 0.55 from the tool, with the caveat that the tool's median on this library is 0.518, so the decision boundary falls inside the tool's densest region and the grey zone between 0.4 and 0.6 is genuinely unstable. The B-cell epitope threshold of 0.1512 is the tool's default and overflows badly on short peptides — 88% of the library is called epitope — so the continuous score is used for relative ranking and the absolute value is not trusted. The same pattern holds for the allergenicity predictor, whose third-party specificity is 6.1% and which labels 35% of a 20-million-peptide library as allergenic; it is reported and never used as a gate.

**Decision two: functional predictors rank, they do not threshold.** Not one functional predictor in the system is trustworthy as a 0.5 cut. The antioxidant support-vector classifier labels 72.83% of the library positive at 0.5, because it was trained to separate real peptides from random sequence rather than antioxidants from non-antioxidants, and its calibration curve jumps discontinuously at 0.5. The tyrosinase-inhibitor predictor labels 99.48% of the library positive, with a median of 0.927, which means it has no enrichment power at all: selecting its top percentile is selecting from a population that is 99% positive. The radical-scavenging predictor's whole distribution on this library is squeezed between 0.2 and 0.4 and third-party testing puts it near chance. The antibacterial classifier is the only functional predictor that works, and even it has a documented bias toward cationic amphipathic short peptides, which is the same chemistry that makes such peptides membrane-active and therefore toxic. The consequence is uniform across the four directions: candidates are taken by percentile top-K and ranked, never released by a probability boundary.

**Decision three: immunogenicity is two independent pathways with opposite directions, and one of them is a percentile rank.** Running the MHC-I predictor on a single allele makes 97.25% of peptides score exactly zero, which reads as an absence of immunogenicity and is an artefact of the single-allele choice; recomputing across 23 East Asian alleles raises the strong-binder identification rate roughly 4.76-fold, and the 2.70% of peptides that are strong binders at three or more alleles are excluded first. The MHC-II predictor points the other way from everything else in the system: it outputs a percentile rank in which a low value means strong binding and therefore higher risk, so the gate is higher-is-better and the strong-binder boundary is the top 2%. On this library 94.48% of peptides come out as weak binders, because their sequences look more like MHC-II binders than random natural peptides do, which means the tool's binding-level labels have lost their "rare" meaning here and only the percentile rank remains a usable scale — dividing that rank by 100 and calling it a probability would be wrong. The two pathways measure different biology, MHC-I presentation to cytotoxic T cells and MHC-II presentation recruiting helper T cells, and neither substitutes for the other.

**Decision four: composite weights are computed from the data, not configured.** Each developability component is normalised within the candidate pool and oriented so that higher is better everywhere, then weighted by its Winsorized standard deviation — the standard deviation after extreme values are truncated to the 5th and 95th percentiles, so a single outlier cannot dominate a component's weight. The weights are then normalised to sum to one. The effect is that a component with real spread in this pool is automatically up-weighted and a flat component is automatically down-weighted toward zero. When thermal stability sits near 0.4 for every candidate in a direction it carries no discrimination, its standard deviation approaches zero, and its weight goes to zero without anyone deciding to give it 0.2 and thereby waste a fifth of the composite. This is why the four directions have different weights: they are computed, not configured. The antioxidant direction came out at cell penetration 0.31, solubility 0.30, B-cell epitope 0.00, aggregation 0.39, where the epitope weight is zero because that predictor had no rows in the database at the time. The antibacterial direction came out at 0.18, 0.26, 0.27, 0.29 with the epitope weight non-zero because full coverage was present. The anti-melanin direction came out at 0.08, 0.39, 0.23, 0.31, with cell penetration near zero because few top candidates scored above 0.1 on it. Three of the six components — cell penetration, solubility and thermal stability — are modulated by a route multiplier of 1.8, 1.0 or 0.4; the other three participate at 1.0. Any component with no measurement drops out of the sum rather than entering as a zero, and the remaining weights are renormalised so the denominator does not distort.

One correction to the pipeline's own arithmetic belongs here, because it changes what the stored numbers mean. The pipeline defined three delivery multipliers over cell penetration, solubility and thermal stability, but computed them by looking up a weight dictionary whose keys did not include the multiplier names. The solubility and thermal-stability multipliers therefore never took effect, only cell penetration received one, and the composite scores for the four delivery methods came out nearly identical. This is verifiable in the exported result files: across all four directions, microneedle and injection are byte-identical in every row, and nanocarrier differs from injection in only about half. The service keeps the design intent of three modulated components and applies all three multipliers from the route's weight tier, and places the three unmodulated components at 1.0. Its composite is therefore not on the same axis as the stored delivery scores; the old values are retained for reference and not published.

#### Problems

The problems are stated as the pipeline's own audit found them, because a wiki page that described only the working parts would misrepresent the system.

Four predictors are unusable as hard gates, and the reasons differ. The three anti-inflammatory models fail for two different reasons: the iFeature-LightGBM variant and the ESM-2 variant both learn to separate functional-looking peptides from random fragments and cannot separate anti-inflammatory peptides from other functional peptides — classifying anti-inflammatory against anti-inflammatory gives an AUC of 0.423 and 0.546 respectively, which is worse than the 0.5 of a coin — because the negative examples in their benchmark are random fragments, a shortcut that rewards "is this a functional peptide" rather than "is this anti-inflammatory". The iMFP-LG channel has a harder failure: its anti-inflammatory channel has 100% overlap with the project's own test set, which is data leakage rather than a modelling weakness, and it scores random fragments at 0.860 despite never having been trained to distinguish them. The rebuilt tyrosinase predictor pair is absent from the production database entirely, so the anti-melanin direction falls back to the predictor that has no enrichment power. The consequence is that two of the four directions are marked work-in-progress: their data exists, their ranking is reproducible, and the pipeline has not signed off on it. The direction status is derived from data — `ready` requires constructs in a passed state — rather than asserted in the interface, which is why the two un-signed directions display as work-in-progress while holding 154 and 107 constructs.

One predictor is missing where it was expected, and its absence changed a number. The B-cell epitope predictor had no rows in the database when the antioxidant direction ran, and the data-driven weighting did the right thing with that: its weight went to zero and the antioxidant composite contains no epitope contribution. The same predictor is fully present for the other three directions. The number is therefore not a modelling result but an artefact of which tools had been loaded, and it is worth naming as such because a reader comparing the four directions' weights would otherwise conclude that B-cell epitope propensity does not discriminate in the antioxidant direction.

The anti-inflammatory direction has a length ceiling that the proposal did not anticipate. The iMFP-LG training set effectively stops around 25 residues: within the P90+ candidate pool, residues 20 to 25 hold about 96.8% of peptides, residues 26 to 29 hold 1,142 peptides or 0.06%, and residue 30 holds none. The stratified top-K design has a 26-to-30 bucket that is empty. The direction's own top-ranked candidates concentrate at 21 to 25 residues for that reason rather than by merit. A cross-function de-confounding step was designed to subtract the strongest competing function channel from the anti-inflammatory rank, and it degraded from eight channels to six because the rebuilt tyrosinase channels were missing; the resulting signal is negative at the median for both the top and bottom channels, which is a direct symptom of the anti-inflammatory channel scoring generic functional peptides highly.

One tool's bias is severe enough to shape a direction's outcome. Among the antibacterial classifier's top 250 high-scoring peptides, 47% are toxic and 80% are haemolytic, and only 7% clear the safety gates. The final top channel for that direction holds seven constructs out of a hundred and fifty attempted, against 113 for the antioxidant direction. The bias has a chemical explanation — the classifier is good at exactly the cationic amphipathic short peptides that disrupt membranes — and a measured alternative exists, since the iMFP-LG antibacterial channel marks 13.7% of its top 250 as toxic against the classifier's 47%, at the cost of a second model to maintain.

Two developability predictors degenerate on peptides of this length. The thermal-stability predictor's shortest training sequences are several hundred residues, and on 3-to-30-residue peptides its output collapses to a single peak centred near 0.5 with no biological signal; on full-length fusion proteins of several hundred residues it is reliable, with Matthews correlation of 0.60 to 0.91. The soluble-expression predictor measures whether a protein is soluble when recombinantly expressed in E. coli, which is not the same question as whether a free peptide dissolves in water, and the AUC of 1.0 it achieves on this library is circular validation — the labels were generated by the predictor's own 0.5 threshold. Both are usable at the construct level and neither is usable at the peptide level, which is the more consequential of the two facts because the pipeline is a peptide-level pipeline.

The structure track failed on a measurable technical ground rather than on effort. Rounds five through eight of the original design depended on predicted three-dimensional structure, and general-purpose folding predictors return low confidence on silk fibroin, whose sequence is built from short glycine-glycine-any-residue repeats with no natural structural template; the mean pLDDT measured on these sequences is about 0.42, where 1.00 is perfect confidence and above 0.70 is generally considered trustworthy. Solvent-accessible surface area and three-dimensional aggregation computed from a structure at that confidence carry no decision value. The rounds were therefore excluded, which is also why molecular docking does not appear in this project.

#### How we improve

Four directions of improvement are underway, and the current state of each is stated rather than implied.

The immediate one is coverage. The haemolysis predictor's full-library run was a 500,000-peptide sample at the time the antioxidant direction ran and has since been extended; the B-cell epitope predictor was missing for one direction and now covers the library; the MHC-II predictor was integrated from a separate 147.5-million-row table for three of the four directions. What remains uncovered is structural: the MHC-I predictor applies only to peptides of 5 to 15 residues, so it carries a value for 117 of the 496 constructs and the rest are reported as not assessed, and the MHC-II predictor covers 186. At least one of the two has a value for 298 constructs and both are empty for 198. The rule applied throughout is that an unassessed metric eliminates nothing and must be reported as unassessed, and it is written in the same position in all four direction proposals.

The substantive one is rebuilding the anti-inflammatory benchmark. The blocker is the negative examples, not the model representation: a usable anti-inflammatory screen needs negatives that include both experimentally-confirmed non-anti-inflammatory functional peptides and random fragments, and it needs retraining on that basis. The evidence that the representation is sufficient already exists — ESM-2 embeddings reach an AUC of 0.80 to 0.90 on independent clean data — so the work is on the benchmark's construction rather than on the model's architecture. Until that is done the direction stays work-in-progress and its scores are not read as probabilities.

The calibration one is Platt scaling or isotonic regression against wet-lab labels for the two uncalibrated ranking signals, applied to the anti-inflammatory channel and to the rebuilt tyrosinase model. Both are declared uncalibrated, and the rebuilt tyrosinase model's linear model is additionally known to have learned backwards, weighting cysteine as the dominant residue while excluding tyrosine and arginine, which is the opposite of the expected chemistry. Both carry an explicit `human_review_pending` marker and neither is used as a hard gate.

The structural one is separating the three developability questions by the level at which they are answerable. Peptide-level: cell penetration and one-dimensional aggregation, both of which are directly valid here. Construct-level: thermal stability and soluble expression, computed on the assembled fusion protein of several hundred residues where both are meaningful, and labelled advisory because they answer a question about the whole molecule rather than about the peptide. Out of scope: solvent-accessible surface area and three-dimensional aggregation, which need structures the folding predictors cannot supply for these sequences.

Finally, the improvement that is a software decision rather than a modelling one: every composite score returns the normalised component values, the weights and the multipliers, so any ranking the platform reports can be recomputed by hand and any future change to the weighting convention can be evaluated against scores already in the database without re-running the pipeline.

### Safety, security, privacy, and AI limitations

The software's own security posture is simple and worth stating because it is a direct consequence of the architecture. The backend is read-only against the database: every connection is marked read-only and no code path writes. The single write endpoint is the chat endpoint, and it writes nothing — it is read-only in effect and is named for the HTTP verb rather than for a mutation. There is no authentication and no user account system, because the platform collects no personal data, stores no session state and has nothing to protect beyond a read-only view of a research database. The service holds no secrets in the repository; the database password comes from the environment.

Privacy has one substantive dimension and it is favourable. All eighteen predictors run as local HTTP services on the project's own workstation, and no peptide sequence is submitted to a third-party API at any point. The sequences in the library come from public biological databases and from patent records, so there is no personal-data question in the input either. The generated text has a configured large-language-model provider slot, and it is currently set to the template implementation; the marker in every response states which produced the text, so template-rendered prose is never passed off as model output. Should a model backend be connected, the disclosure obligation attaches at the point of connection, not now.

The AI limitations are the substantive ones, and they are of five kinds.

The first is that nothing here is evidence of activity. Every number on the platform is a prediction from a model trained on other data. A high composite score means a construct looks developable under models that have known biases; it does not mean the peptide scavenges free radicals, kills bacteria, suppresses inflammation or inhibits tyrosinase. The platform's contribution is to make the predictions legible and to keep unsafe candidates out, not to replace the assay.

The second is that the models are not equally trustworthy, and the interface says which are which but cannot make them equally trustworthy. Two directions are work-in-progress and labelled as such in the data, in the API and in the interface. The rebuilt tyrosinase model is absent, the anti-inflammatory models are blocked on a benchmark, the tyrosinase-inhibitor predictor has no enrichment power on this library, and the radical-scavenging predictor's distribution is too narrow to rank on. For two of the four directions, the honest statement is that the platform produces a ranked shortlist for wet-lab validation, not a set of leads.

The third is coverage, and it interacts with the veto logic in a way that is easy to miss. The immunogenicity gate is a veto gate, and it is unassessed for 198 of 496 constructs and assessed by only one of its two pathways for many more. A veto gate that was not evaluated eliminates nothing — that is the pipeline's explicit rule — so a construct can be reported as clearing every gate it was measured on while a gate that could have excluded it never ran. The interface reports this as an indeterminate verdict rather than a clear one, which is the correct handling, but the underlying fact is that the safety case for the long-peptide majority rests on toxicity, haemolysis and developability alone.

The fourth is that the composite score is a ranking value with no absolute meaning, and its weights differ between directions and between runs over time. It is reproducible — the response carries everything needed to recompute it — but two composite scores from different directions are not comparable quantities, and a composite from before a weighting-convention change is not comparable to one from after.

The fifth is the one that has to do with what the platform does not contain. All 496 constructs carry a placeholder scaffold binding: the foreign key points to a row whose name is a marker string and whose sequence length is zero, and that row is not one of the eight real protein clusters. Consequently the scaffold segment of a fusion sequence is unavailable by default, the platform reports only the two segments that genuinely exist, and it does not invent a third. When a caller explicitly names a real scaffold, the construct is assembled with it and the binding is labelled as inferred from the request rather than produced by the pipeline, with the note attached. The interface does not present an inferred scaffold as a verified choice anywhere. The missing piece is a rule for which direction pairs with which scaffold, and that rule is a scientific decision the platform cannot make on its own.

Two smaller limitations belong in the same list. The sequence-level secondary attributes — parent sequence, taxonomy, PDB chain, reading frame, source offset — are unavailable because the table that would hold them is empty, so any feature that would need provenance back to a source record cannot be offered. And the remote database is a single point of dependency: the address is reached through a network tunnel, and if either end of that tunnel is down the service is unavailable. The interface distinguishes "database unreachable" from "query failed" so the failure is readable, but that makes the dependency diagnosable rather than absent.
